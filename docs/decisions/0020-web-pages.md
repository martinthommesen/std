### The table list (Contracts 6.1, 6.3)

- **One function for both endpoints** [judgment]. `summaryOf` in `@std/access/table-metadata` gives a table's name (only when `knowsTable`, and not purged), label and `creatable` (the class accepts writes, the generic write limits allow a create, the caller has a create decision that is not never). `tableMetadata` and `tableList` both call it, so a table is listed exactly when its metadata answers 200, with the same three values. Computing every table's full metadata for the list was rejected: it would compute field states and related lists the list does not show.
- **Retired tables** are listed, as their metadata is served (reads still work); purged tables are not.
- **Hidden tables never show**: the list is filtered by the same knowledge rule as `UnknownTable`, so it is byte-identical (apart from `schemaRevision`) when a hidden table is added, renamed or relabeled.
- **Revisions** are checked like the per-table metadata (`checkUnscopedRevision`): an older one is served, malformed is 400, one the database never had 409.
- Not cached, like metadata.

### Related lists (Contracts 6.3)

- For endpoint E, every active reference field whose target is E or one of E's ancestors can point at E's records. For each such field, declared on class D, the candidates are the classes of subtree(D) that the caller knows (`knowsTable`) and where the field is in the caller's visible schema (read `yes` or `perRecord`). A candidate is listed unless one of its ancestors at or below D is also a candidate: the most general table wins, because a parent endpoint lists its descendants' records [judgment]. In practice D itself qualifies whenever any descendant does, since D's readability is computed over the row-visible classes of its subtree; the rule stays general.
- `label` is the table's label and `fieldLabel` the field's effective label on that table (overrides applied), as that table's metadata shows them.
- System references (`created_by`, `updated_by`) are not listed [judgment]: every table has them, so a user's page would list every table.
- Order: table name, then field name.
- Filterability: every listed entry is in the caller's visible schema at its table, so `filter=<field> = "<id>"` resolves there. `authz-paths` sends that request for every related list of every table each caller can open, by bearer token and by cookie.
- Disclosure: a table enters only when the caller knows it and reads the field there, so nothing names a hidden table or field. The visibility rule is redundant with the knowledge rule for hidden tables (a table the caller has no allow on has no readable field), so both are kept; the can-fail run drops both.

### History definitions (Contracts 4.4, 4.5)

- Each entry gets `fields`, keyed exactly like `changes` (the field's current name), with `label`, `type` and `choices` at the entry's `schemaRevision`. Only fields in the entry's `changes`, so a restricted caller's entries hold no description of a field it cannot read [judgment: describing more would tell which fields exist].
- **How R is read.** One statement reads `core.definition_revision` up to the latest entry's revision for the changed fields, the classes of the record's concrete lineage, and the overrides and choices whose `fieldId` is a changed field. Per revision R the latest row at or before R of each definition forms a small `ConfigSnapshot`, and `effectiveField` on the record's concrete class gives the label and type exactly as metadata computed them at R (overrides at R applied). The same lookup as `stale-scope.ts`, without building the whole configuration at R.
- **Choices**: the field's live choices at R, hidden ones included, not narrowed by a child's subset [judgment: an old value may be any key the field had, and the panel needs its label]. A choice deleted before R is not listed; its key shows without a label.
- **Type**: `metaTypeOf` (the metadata form), so a reference or condition field names its table only when the caller knows that table now, by its current name, and a reference's allowed-records condition is left out [judgment: the type is immutable apart from that condition, and naming the table follows today's knowledge, like `changes` follows today's names].
- **Purged fields** (admin-only changes, 3.7) resolve at R like any field; their definition revisions are kept with the tombstone. A field with no revision at R (none is expected) is described as it is now.
- Cost: one extra statement per history read. Its `OR` over `effective ->> 'fieldId'` scans `core.definition_revision` (not measured; open item).

### The allowed-records condition (Contracts 6.5; plan Step 2)

The contracts named "the field's allowed-records condition" (7.4) without defining it. Defined here:

- **A type setting** [judgment]. `allowedRecords` on the reference type (`@std/values/field-type`), a condition AST with field IDs over the target class; absent or null is none. A type setting rather than a new field property, because `core.field.type` is already JSON (no migration, no catalog-load change, no added-property default for release compatibility: a `v0.0.1` type simply has no key), and because it describes what the field may hold, like `targetClassId`. `@std/values` cannot import condition schemas (the package order is values ← conditions ← definitions), so it holds `Json` there and `@std/definitions/allowed-records` decodes it.
- **Checked when stored** under the `filter` profile against the target class as system (`conditionProblems`, all fields, not the editor's view): field IDs exist and, when the condition is new or changed (`newConditions` now includes reference fields whose condition changed), are not retired; operators fit; literals convert; one hop; `me`, `now`. A malformed AST is `invalidCondition`.
- **May change after the field exists** [judgment, as asked]. `type` joined `UPDATABLE.field`; `immutableProblems` refuses any type change but this setting (`sameTypeApartFromAllowedRecords`), so the target, kind and other settings stay fixed. A set upgrade may change it too (`checkExisting` compares types without it). It is not overridable locally on a shipped field in v0.1 [judgment: an override of the whole `type` property would also pin the target and settings; open item].
- **Stale relevance**: a change of it is `settingsChanged`: the stale check compares type JSON with the kind unchanged (`stale-request.ts` already did), and the journal kinds now say `settingsChanged` instead of `typeChanged` when a type keeps its kind.
- **Dependencies** [judgment, as suggested]: `condition_reads` edges from the reference field to each field the condition reads, like stored access-rule and subscription conditions. So a field it reads cannot be purged while the reference field is not retired, and retiring such a field is allowed and reported; the stored condition keeps evaluating the retired field (5.2), so the limit does not silently open.
- **Set files** carry it as access-rule conditions are carried there, a JSON AST with field IDs (`type: { kind: reference, target: <table>, allowedRecords: <AST> }`) [judgment: set files carry no condition text syntax anywhere; adding a text form for one setting would make two formats]. Resolved, planned, installed and upgraded in `definitions/test/allowed-records.test.ts`.
- **Writes**: `checkReferences` passes the field's condition to `WriteAccess.visibleTargets`; `RuleWriteAccess` compiles it with `compileAllowedRecords` over the target relation, in the caller's view (`compileInView`: masked expressions, a never-readable field NULL, hops guarded by target visibility), and ANDs it to the target's visibility in the same statement. Refusal is `InvalidReference`, byte-identical to an unknown ID. Only written values are checked (3.9), so an unchanged readable value is kept, like an unchanged hidden choice key; a value the caller cannot read counts as written, as for the visibility check. `WriteAccess.allowAll` (bootstrap, the system's own loads) does not apply it [judgment: those writes bypass access rules too; imports in Step 3 run as the importing user].
- **Context**: `me` and `now` resolve as for filters (`timeZoneFor("filter")`, the instance zone until users have one).
- **Fails closed**: a condition that no longer checks against the snapshot, or does not decode, compiles to `FALSE` (nothing allowed), like a stored access-rule condition (decision 0008).
- **Picker reads** (`allowedFor=<sourceTable>/<field>`): the source table resolves like an endpoint (`UnknownTable`); the field resolves like a write body's name, readable or writable at the source endpoint for create or update (`UnknownField`, identical to a missing field) [judgment: a picker fills a field the caller writes, which it may not read]; `InvalidRequest` naming `allowedFor` for a malformed value, a field that is not a reference, or an endpoint that is neither the target class nor a descendant [judgment: a descendant narrows the picker to a child class; an ancestor would list records the write refuses, and the condition's fields may not exist there]. The condition is compiled over the endpoint's relation with the endpoint's class (its fields are the target's lineage's, which a descendant has too) and joins `a<n>` aliases, so it never collides with the filter's `f<n>`. It applies to the page and to `count`. A field without a condition adds nothing.
- **Stale scope**: `allowedFor`'s field is in the request's scope on its own table (`staleScope`'s `classByName`, only for tables the caller knows, so a hidden source table adds nothing and the list answers `UnknownTable`).
- **Metadata does not say a condition exists** [judgment]: the picker always sends `allowedFor`, so the flag buys nothing, and the existence of a limit on a field is configuration a caller does not need. `metaTypeOf` builds the reference type from `kind` and `target` only, so neither metadata, the per-table OpenAPI document nor history descriptors carry it.
- **Non-interference**: the picker list and the write check depend on hidden values only through masks, so for Bob a condition on `cost` behaves as if `cost` were empty, and changing a hidden value changes nothing he sees (`allowed-records` test).

### Review round 1

Supersedes the "Cost" bullet under History definitions and the third open item above: the index exists now.

- **Revisions sort as numbers (A1).** The lookup selected `"revision"::text AS "revision"` and ordered by `"revision"`, which Postgres resolves to the output alias, so rows sorted as text and `snapshotAt`'s `findLast` picked revision 9 for an entry at 10 or later. The order now names the bigint column of a qualified relation. `definitionAt` in `catalog/definition-revisions.ts` (Step 1) had the same bug in `ORDER BY revision DESC LIMIT 1` and is fixed the same way. Rule (Contracts 4.4): order by the column, never by its text rendering.
- **An index per lookup branch (A2).** Platform migration 0010 adds `core.definition_revision_field`, a partial index on `((effective ->> 'fieldId'), revision) WHERE kind IN ('override', 'choice')`. It is a `concurrent_index` migration [judgment: `core.definition_revision` grows with every change set, and a concurrent build does not block config changes while `std upgrade` runs]. The statement (`definitionRevisionsStatement`) is a `UNION ALL` of two branches: definitions by ID on the primary key, and overrides and choices by field ID on the new index, the second leaving out rows the first reads. With the index, Postgres 18 also plans the old `OR` as a `BitmapOr` of both indexes; the split keeps each branch's plan independent of how the planner weighs the `OR` [judgment]. ### Schema revisions (Contracts 6.2, 6.4)

- **Sent per request, not per client.** The typed client stays one `HttpApiClient.make` instance (`StdApi`). Its `HttpClient` reads a `Context.Reference` (`RequestRevision`, default none) when each request is built and adds `STD-Schema-Revision` when one is set; a Command wraps its request in `atRevision(revision)`. A client per revision was rejected: it rebuilds the API client for every page and spreads the header logic over Commands. The default (no header) is safe because the contract lets a request omit it, and only start-up's `auth/me` and sign-in send none: they act on no metadata.
- **Which revision** [judgment]. A list page keeps its metadata with the revision its response stated (`TableMeta.revision`, read from the response header with `responseMode: "decoded-and-response"`), and its list requests send that one, so each page sends the revision of the definitions it was built from, not the app's latest. Forms (workstream 2C) follow the same pattern: keep the form's metadata revision and send it with the save. Metadata, target tables and the table list send the latest revision the app has seen (`SignedIn.maybeRevision`, seeded from the header of the `auth/me` or sign-in answer that started the session), sign-out too (it checks only the format). The app's revision only moves forward, except that a `SchemaChanged` refusal's `currentRevision` replaces it (`SawCurrentRevision`), since after a restore the database's revision can be lower.
- **Refresh.** A response stating a newer revision than a page's metadata refreshes that metadata (and the target tables of its filter paths) in the background, keeping the list on screen; the page tells the app (`SawRevision`), which keeps the latest revision and reloads the table list when it is newer than the list's. `SchemaChanged` on a list request refreshes the metadata and then asks again, because a read is safe to repeat; a write must not be repeated by itself (6.4), which 2C's forms handle. The list endpoint never answers `NotAllowed`; the refresh step is per page, so a form page calls its own on `NotAllowed`. A metadata or table-list request whose revision the database never had (`SchemaChanged`, after a restore) is asked again without one.
- **An ended session** (`Unauthenticated` from any page request) goes to the sign-in page and returns to the page afterwards (0018 left this open).

### Navigation and routes

- The tables come from `GET /api/v1/meta/tables` once signed in: a "Tables" navigation (Foldkit UI `Nav`, `aria-current` on the open table) beside every signed-in page, and the home page's list with labels and names. The table list never names a table the caller cannot open, so neither does the app.
- Routes: `/tables/:table` (the list; table names hold dots, which the router accepts), `/tables/:table/records/:id` (the record's form; a placeholder until workstream 2B's form lands, so row links already have their final address). `/tables/:table/new` is left for the form workstream. A direct address of a table the caller cannot open gets the not-found page, from the metadata's `UnknownTable` (identical for a missing table).

### The list page

- **Columns** [judgment]. The list layout when metadata serves one with fields the caller can read; otherwise a default selection: the display field, then the other active fields in metadata order, without types that do not fit a cell (long text, json, condition, password, secret), at most six. (Metadata lists fields by ID, so the default order is not the declaration order; a list layout fixes the order.) The request asks for exactly these fields (`fields=`), with `labels=true` and `count=true`.
- **Cells** tell apart what record JSON tells apart (6.6), marked with `data-cell`: a value; `null` (empty, with "Empty" for screen readers); a field in `withheld` ("Restricted", a dashed badge with the accessible text "Restricted: you are not allowed to read this value", never empty); an absent key that is not withheld ("Not delivered"). Choices show their label by key, hidden ones included; references show `labels`, or the UUID when no label is permitted; auto-numbers are text; booleans "Yes"/"No"; password and secret "Set"/"Not set"; date-times the UTC instant ("2026-10-22 08:15:30 UTC"). The first column links to the record's form.
- **Sorting** by a column header button: ascending, descending, then the default order (by ID, as the server orders without a sort). One key at a time from the UI; the address may hold several. Not offered for password, secret, json and condition, which the server cannot sort; the header carries `aria-sort`.
- **Paging**: keyset with the server's `nextCursor`; "Previous" goes back through a stack of the cursors of the pages seen. Page sizes 5, 10, 25 (default), 50, 100 [judgment]. An answer to an earlier request (a page counter) is ignored.
- **The address keeps the list** [judgment]: `?filter=<the condition AST as JSON>&sort=<field IDs, "-" for descending>&limit=<n>`, written with `replaceUrl` whenever the applied filter, sort or page size changes, read on load and on back or forward. Field IDs rather than names, so a reload or a shared link survives renames; the AST rather than the text syntax, because the builder's state is the AST and the API's text is printed from it at request time. Cursors are not kept (a reload starts at the first page). A malformed filter, or one the builder cannot show, is not applied, and the page says so; unknown or unsortable sort fields are dropped.

### The filter builder

- **The builder's state mirrors the AST** (`Group` for `and`/`or`, `Negation` for `not`, `Condition` for an atom, field IDs in paths), so a stored AST loads into it and prints back unchanged, and its own state is what is applied. Values are held as typed and converted at "Apply"; a value that does not convert keeps the filter from being applied and shows its problem on the condition.
- **Operators** are the filter profile's (`OPERATOR_KINDS` and `operatorFitsKind` of `@std/conditions/profile`: every atom but `changed`), labelled for the type ("is before" for dates, "is less than" for numbers).
- **Values and controls** (Foldkit UI): Select for fields, operators, units, value sources and single choices (labels shown, keys sent; hidden choices offered and marked, as 5.2 allows them in conditions); Input for text, numbers, UUIDs and references (a reference picker is workstream 2B's next part); Textarea for `in`/`notIn` lists, one value per line; Checkbox for booleans, choice sets and "Not"; Date Picker for dates; Date Picker plus an `HH:MM` Input for date-times. A comparison may compare with a value, `me` (references to `core.user` only), `now` (date-times), a date relative to today (dates and date-times) or a time relative to now (date-times); `inPeriod` takes a unit and an offset (0 the current period, -1 the previous).
- **Literals in canonical JSON** (6.5), converted with `@std/values`: integers as numbers, big integers and decimals as digit strings (`0012.50` becomes `"12.50"`), dates `YYYY-MM-DD`, date-times as instants, UUIDs in lowercase, text after the write conversion (trimmed, NFC; whitespace-only is refused with the hint to use "is empty"), and every literal checked with `convertLiteral`, as the server checks condition literals. Needles are sent as typed (the server applies steps 1 and 2 of 5.5).
- **Time zones** (Contracts 5.7) [judgment]. The browser does no time-zone or calendar arithmetic: relative values and `inPeriod` go to the server as `rel`/`inPeriod` and are resolved there in the filter profile's zone (the instance zone until users have a zone preference, decision 0008), so the web app needs no Temporal polyfill. A date-time literal is entered as a date and a time in UTC, labelled "(UTC)", because the browser knows neither the user's nor the instance zone and must not use the device's; list cells show date-times in UTC for the same reason. The Date Pickers' "today" mark is today in UTC. When metadata or `auth/me` carry the user's zone, date-time entry and display can move to it.
- **One hop** (5.10): picking a reference field whose target the page has no metadata for asks for it (the builder's `RequestedTable`; the page loads it once); "Field of <reference>" then offers the target's fields. A target the caller cannot open (`UnknownTable`) offers no hop. The condition engine's `ClassView` in the browser (`tableClassView`) is keyed by table name, since metadata names targets by name, never by class ID; the engine uses class IDs only as lookup keys, so the printer and parser work unchanged.
- **What the builder does not show** [judgment]: constants, field-to-field comparisons, `myGroups`, `changed`, `previous`, paths of more than one hop, date-time literals with seconds. A stored condition using them is not applied, with a notice (not silently changed). System fields (`id`, `class`, `created_at`, ...) are not offered: metadata does not describe them, and their synthetic IDs are the server's; adding them needs metadata to list them.
- **Loading a stored condition is one function**: `applyStoredFilter(page, Option<Expr>)` in `page/table-list/update.ts` (fields by ID). It requests the target tables of the condition's paths and waits for them, loads the condition into the builder, applies it to the list (printed with names at request time) and writes the address; a condition the builder cannot show is not applied, with a notice. The address uses it today; saved filters (exposed through metadata later, with an AST and its text form) only need to call it.

#### Routes and pages

#### The form page's Model (`page/record-form/model.ts`)

- `metadata`: the endpoint's metadata with the revision its response stated (`TableMeta`, as list pages); every request built from it sends that revision (Contracts 6.2).
- `record`: the record as read (`labels=true`); `classMetadata`: the concrete class's metadata, loaded when `record.class` differs from the endpoint.
- `edits`: the user's inputs by **field ID** (`FieldInput`: `Text`, `Choice`, `Flag`, `Day`, `Instant`, `Reference`, `WriteOnly`); a field without an edit shows its stored value and is never sent.
- `maybeEditsFrom`: after a reread under edits (a conflict reload, or a reread after the metadata moved), the record the edits were made on, so the view marks the fields someone else changed.
- `staleChanges`: the `changes` of a `SchemaChanged` refusal of a save, until a save succeeds.
- `serverErrors` (by field ID, until the field is edited), `isShowingProblems`, `submission` (`Idle`, `Saving{generation}`, `Saved{isVisible}`, `Unchanged`, `Failed{WriteError}`), `deletion` and `deleteDialog`, `pickers` and `datePickers` (by field ID), `targets` (picker targets' metadata), `relatedLists`, `history`, `maybeToday`.

#### Fields and controls [judgment]

- **Sections**: the form layout's sections (Foldkit UI Fieldset with a legend); fields before the first section form an unlabelled one. Without a layout: the display field, then the other active fields in metadata order. Two sections follow a layout's: "Other required fields" (required, no default, not auto-numbered or read-only, left out of the layout: without them a create could never succeed) and, when editing, "Retired fields" (retired fields holding a value, read-only). Other fields a layout leaves out are not shown: the layout is the admin's choice.
- **Which description**: through a parent endpoint the form shows the endpoint's fields (a body can name nothing else), described by the concrete class's metadata once the page has it (its labels, choice subset and rules apply to the record), with the endpoint's names. A link "Open as <class>" goes to the record's own table.
- **How a field shows** (`fieldShowOf`): `Restricted` for a field in `withheld` (the list's dashed badge, with the full sentence for screen readers; no control, never sent, never empty); "Not delivered" for an absent one; read-only for read-only and auto-numbered fields, retired fields, fields whose `write.create` or `write.update` is `no` for the form's mode, and references whose target the caller cannot open (metadata `target: null`: the label or UUID as text); editable otherwise, `perRecord` included (the server decides). On a create an auto-number says "Assigned when the record is saved."
- **Controls** (Foldkit UI): Input for text, integer (`inputmode=decimal`), big integer and decimal (typed as their canonical strings; big integers and decimals stay strings), UUIDs and the time of a date-time; Textarea for long text, and for json and condition values as JSON text, parsed with `@std/values/json`'s strict parser, whose refusal shows on the field; Checkbox for booleans; Select for choices (labels shown, keys sent, "None"; a hidden choice offered only when it is the stored value, marked "(retired)", and kept when unchanged; a stored key no longer offered shows as "<key> (no longer offered)"); Date Picker for dates; Date Picker plus a time Input, both labelled UTC, for date-times (the browser knows neither the user's nor the instance zone and never uses the device's, Contracts 5.7; a date without a time is midnight; seconds and milliseconds are kept when typed and shown only when not zero); Combobox for references (below). Labels carry "(required)" and the input `aria-required`; help text and the client's and server's problems form the control's description (`aria-describedby`, a polite live region), with `aria-invalid` on a problem.
- **Condition fields** use the JSON editor, not the filter builder [judgment]: the builder needs the condition's table's metadata and its target tables and is built to apply a list filter; no shipped or helpdesk field is a condition field (`core.access_rule.condition`, `core.subscription.condition` and saved filters' conditions are `json`), so the JSON editor serves Step 2, and the server checks a condition value against the caller's view (`invalidCondition`). Reusing the builder is an open item.
- **`core.field.type`** (an admin's metadata shows it `perRecord`) is a json field and gets the JSON editor like any other, as metadata allows; the engine refuses every type change but `allowedRecords` (`DefinitionInvalid`, shown with its message). No special case in the generic form.
- **Password and secret** (write-only): "Set." or "Not set." from `{"set": bool}`; an uncontrolled password input ("<label>: new value", `autocomplete=new-password`), never prefilled. What the user types becomes `Redacted` in the Message at once and stays `Redacted` in the Model and in the save Command's `secrets` argument (DevTools shows `<redacted:write-only value>`); `Redacted.value` is called only where the request body is built (`sentBody`). Emptying the input forgets the edit. A set secret offers "Clear the stored value" (sends `null`) and "Keep the stored value". The input gets `value=""` whenever no typed value is held, which empties it after a save.

#### Validation, the body and saving

- **Client verdict** [judgment]: on "Save", and live after a failed attempt, `validateRecord` (`@std/definitions/record-schema`) in create mode with the endpoint's metadata, or in update mode with the concrete class's metadata, `{ class, values }` of the record as read and `through` the endpoint when the class differs (decision 0017). Without the class's metadata (the caller cannot open that table) the client finds nothing and the server decides. Before that, an input that cannot be put into its JSON type (a whole number that is not one, JSON that does not parse, a time that is not one) is a problem of its own. A typed password or secret is judged as a stand-in string (`WRITE_ONLY_STAND_IN`): the codec refuses only an empty string, which is never sent, and text that is not well-formed Unicode, which only the server checks; so the value is never unwrapped outside the request.
- **The body** (Contracts 6.7): only fields with an edit that the form shows as editable; an update sends a field only when its JSON differs from the stored value (compared in jsonb order; a value typed in another form, `12.5` for `12.50`, is sent and the server finds it unchanged), a cleared field as `null`; a create sends a field only when it differs from what the create stores without it (the default, else empty), so untouched fields are absent and a cleared default is `null`. With problems, focus moves to the first field with one and nothing is sent. Saving an existing record with nothing changed says so and sends nothing.
- **Saving**: `POST` for a create, `PATCH` with `If-Match: "<version>"`, both at the form's revision. A save in flight disables the button and ignores another click, and only the answer with its generation counts. Success replaces the record (labels kept for unchanged references, the picked label for a changed one), clears edits, problems and stale marks, says "Saved.", reloads the history if it was loaded, and reports the response's revision (`SawRevision`; a newer one refreshes the metadata). A record the caller can no longer see after the save (`{id, version}` only, Contracts 3.9) shows "Saved. You can no longer see this record."
- **Refusals**, all keeping the input and none resubmitted: `ValidationFailed` on the fields (names mapped to field IDs); `VersionConflict` says someone else saved first, at version n, that the changes are kept and not saved, and offers "Reload the record, keeping my changes" [judgment: the user decides; the reread keeps the edits and marks each edited field someone else changed ("Someone else changed this to: …. Your value is kept."), and the next save sends `If-Match` with the new version, so the user overwrites only what they looked at again]; `SchemaChanged` names the changed fields, keeps the input, offers "Reload the definition" (below) and sends `SawCurrentRevision` to the app; `InvalidReference` on its field (identical for a missing, hidden or not allowed target); `UnknownField` on its field; `NotAllowed` (with a background metadata refresh, Contracts 6.4); `NotFound`; a change set's refusals (`DefinitionInvalid` and the rest of `changeSetErrors`, `SchemaBusy`, …) with their message, which names definitions, never values; no answer.
- **Rereads**: when new metadata arrives at another revision ("Reload the definition", a background refresh, a `SchemaChanged` read), the page rereads the record at that revision, so its value names match the metadata's after a rename, keeping the edits (by ID, sent under the new names); a reread of another version under edits sets `maybeEditsFrom`. A reread older than the record a save returned is not shown. A read refused with `SchemaChanged` refreshes the metadata and asks again (a read is safe to repeat).
- **Delete**: "Delete" opens a Foldkit UI Dialog ("Delete this record?"); its "Delete" sends `DELETE` with `If-Match` once (another confirmation while it runs does nothing); success goes to the table's list; `VersionConflict` ("Someone else changed this record. Reload the record before deleting it."), `Referenced`, `NotAllowed` and the rest are shown.

#### Hooks for stale forms (workstream 2C)

- The form's revision is `metadata`'s (`TableMeta.revision`); every save, read and search of the page sends it.
- Edits live in `edits` by field ID, so they survive renames, and `buildBody` names them with the metadata of the moment; edits of fields the new metadata no longer has stay in `edits` and are not sent (the view can list them).

#### Stale forms (Contracts 6.4)

- **The form reloads by itself after `SchemaChanged` on a save** [judgment: the contract says the UI reloads metadata; making the user click "Reload the definition" first added a step with only one possible answer]. The refusal's changes are kept (`staleChanges`, merged with an earlier refusal's until a save succeeds), the endpoint's metadata is reloaded at the form's revision (the server serves the current one), and the record is reread at the new revision so its value names are the new ones. When a background refresh already brought the form to the refusal's current revision, nothing is reloaded and the form is outdated at once. The "Reload the definition" button stays for a reload that failed.
- **No save while the definitions or the record reload** (`isReloading`): a body is never built from new metadata and an old record (whose value names may be the old ones), or the other way round. The button is disabled; a click does nothing.
- **`Outdated`**, a new `Submission` state: the form shows the new definitions with the input that still applies and waits for the user. It says "Nothing was saved …", lists what changed per field (the label in the new metadata, else the name the server gave, with the change in words: renamed, retired, removed, its choices changed, now required, …) and marks each changed field ("Changed since you opened this form: …"). Only a save (or another refusal) leaves it; the form never resubmits by itself.
- **What happens to each edit** [judgment, asked to decide between keeping it visible but excluded and dropping it with a message]. Both, by whether the form can still send it:
  - **Kept in its control** when the field is still offered for input and the input still fits its type. A value that no longer validates (a choice now hidden or outside the subset, a tighter setting, a field now required) stays and is flagged by the client's verdict, which holds the save back (focus moves to it) until the user fixes it. Reason: the user's work is never thrown away while it can still be saved; dropping a long text because a maximum length shrank would be hostile. A choice no longer offered shows in the select as "<label> (retired)" or "<key> (no longer offered)", so the select can show what the user picked.
  - **Dropped, with a note**, when the form can no longer send it: the field is gone (purged, or no longer readable), retired, read-only or not writable for the caller, of a type the input no longer fits (`TypeChanged`), or withheld or no longer delivered by the reread record. Reason: such an edit can never be sent, and keeping it invisible in the Model would make the body depend on state the user cannot see. The note names the field (its label as the user last saw it), why, and what the user had entered, so they can carry it elsewhere; a password or secret is never shown. The notes show in a live region above the actions, and on the field while it is on the form, until a save succeeds.
  - The reconciliation runs when metadata arrives at another revision (with the endpoint's fields; the class metadata follows) and again when the record is reread under edits (`reconcileWithRecord`: restricted, not delivered, read-only). A background refresh (a newer revision on an answer, or `NotAllowed`) runs it too, without touching the save's state.
- **A newer revision on any response**: besides the record, a save and the history (which did so already), a picker's search and a related list's page now carry the response's revision and refresh the metadata in the background, keeping the input. A history read refused with `SchemaChanged` reloads the metadata and is asked again once it arrives (a read is safe to repeat); a delete refused with `SchemaChanged` or `NotAllowed` reloads the metadata and is not sent again.
- **Rename then re-create**: nothing in the browser resolves names. The save names fields as the form's metadata does and sends that metadata's revision until the form reloads, so the server resolves `foo` at R, refuses with `fieldRenamed`, and writes nothing. After the reload the edit (kept by ID) is on `bar`, and the next save names `bar`.

#### Admin pages: roles, user roles and access rules (plan Step 2, Includes)

- The generic list and form pages serve `core.role`, `core.user_role` and `core.access_rule` like any table; the navigation and the address offer them only to callers the table list and metadata name them for (the administrator). The navigation now groups tables by namespace when there are several [judgment: an administrator's list mixes `core.*` platform tables with app tables; a heading per namespace keeps them apart without naming tables specially].
- **Required fields the server sets** [judgment]: the client's verdict no longer holds a write back for a `Required` field the user cannot write in that mode (`write` is `no`: a definition's `owner_layer` and `state` are required and set by the server). Before this, no definition could be created through the form. The server still decides.
- **Definition creates leave out what defaults** (server): a generic `POST` to `core.access_rule` without `name` was refused as "not a valid definition", although `name` is optional and the form leaves an empty optional field out (6.7). `name: null` joined the create defaults; a kind whose name is required still refuses a body without one.
- **Clear errors for the JSON fields** [judgment]: the JSON editors refuse text that is not JSON on the field (the strict parser's message). For JSON of the wrong shape, the server now answers a create body its kind's draft refuses with `ValidationFailed`: `Required` or `InvalidValue` per column it can blame, found by decoding the draft with every issue reported and mapping each issue's first path segment back to its column (an access rule's `target` to `fields` when the target is `fields`). The message says what the column takes (written out for an access rule's `actions`, `role_ids`, `fields`, `target`, `effect` and `condition`; a generic sentence otherwise) and never carries the refused value (Contracts 3.8). The form shows each on its field. A body no column is to blame for keeps the `InvalidRequest`; an empty body on any definition table names its missing required columns (`platform-tables` now expects `ValidationFailed` for it and for a forged access rule). Validating access-rule shapes in the browser was rejected: it would copy the definition schemas' rules into the generic form.
- **What the engine refuses per record** (`definition-limits.ts`) [judgment]: metadata states write limits per table and field, so a field definition's `type` is `perRecord` for every field, although the engine refuses every type change but a reference's `allowedRecords`. On `core.field` the form shows `type` read-only unless the stored type is a reference, and says before sending that only `allowedRecords` may change (`sameTypeApartFromAllowedRecords`, the engine's own check). A set `required` (it may only become true) and an absent `number_prefix` (auto-numbering cannot be switched on) are read-only. The server still refuses with `DefinitionInvalid`. This replaces the earlier choice above ("No special case in the generic form"): the task requires the form not to offer what the engine refuses, and the rule set is small and named by table. An access rule's `fields` is already `update: no` in metadata. Per-record write states in metadata would be the general fix (open item).
- References on these tables use the pickers (`core.user_role.user` and `.role`; `core.access_rule.table_id` searches `core.class`).

### Review round 1

#### The app's root and the list page (findings B1, B7, B8, B9, B12)

- **Root answers belong to their session** (B1; closes the open item "Root-level answers tied to their session" above). `SignedIn.sessionId` numbers the session within the app's run; `SignedOut.nextSessionId` carries the counter across sign-out and sign-in, as `nextPageId` carries page numbers. `LoadTables` and `SignOut` take the session's number and every answer names it (`SucceededLoadTables`, `FailedLoadTables`, `FailedAuthentication`, `SucceededSignOut`, `FailedSignOut`); the app acts on an answer only in the signed-in session with that number. Before, a late table list of user A replaced user B's catalog (A's table names in B's navigation until the next revision), and a late `Unauthenticated` or sign-out answer of A's session signed B out. `auth/me` needs no number: it is asked only while no session exists, one request at a time, and its answer counts only in `CheckingSession`. Page answers were already tied to their page across sessions.
- **The position moves only when the page loads** (B7). `cursors` is the stack of the page on screen; "Next" and "Previous" put the stack they ask for in `maybePendingCursors`, which becomes `cursors` when that page loads and is dropped when it fails. "Page N", "Previous", "Try again" and the next "Next" therefore act on the rows shown. A new filter, sort or page size still starts from `[None]` at once, since the old position means nothing for it.
- **A refresh that changes the sort restarts paging** (B8) [judgment]. When refreshed metadata drops a sort key (the field is gone, or can no longer be sorted by: `reconcileSort`), the page resets its cursors (a cursor of the old order would be refused, `InvalidCursor`, on every retry) and reloads the list from the first page in the new order. It reloads once the metadata and every target table have settled (`isReloadDue`; answers in the old order are ignored from the reset on), so a path filter prints with the target's current names; a filter still waiting for its tables does the reload when it is applied. Before, the sort changed silently and the rows stayed in the old order.
- **What the definition drops leaves the address** (B9). A sort key dropped as above, and a filter that no longer prints (`withoutLostFilter`: a field it names is gone, here or on a target), are removed from the address with `ReplaceListUrl`, so the field IDs and literal values of a dropped condition do not stay in the URL. A refresh now also checks that the applied filter still prints and, if not, drops it with its notice and reloads from the first page; before, a background refresh left it applied (and in the address) until the next request.
- **A list always has a column** (B12) [judgment]. A table without a list layout, without a display field and with only fields that do not fit a cell asked for `fields=` (empty), which the API refuses. `listFieldsParameter` asks for `fields=id` then (`id` is an envelope member: the server accepts the name and returns `values: {}`), and the list shows each record's ID as its only column ("ID"), linking to the record's form. The record form's related lists build their `fields` from `listColumns` too (`columnNamesOf` in `page/record-form/update.ts`) and should use `listFieldsParameter` and the same ID column.
- **The records section is busy while records load** [judgment]. The section carries `aria-busy="true"` whenever a request for records is under way (first load, reload, paging, the reload a refresh makes due), `false` otherwise, as the table already did for its rows. A reload of an empty list keeps "No records match." on screen inside the busy section rather than replacing it with "Loading records…": the list keeps what it showed during every reload (rows stay too), so the page does not flicker, and the busy section says the text is not the answer yet. Before, an empty list's reload looked exactly like its answer to tests and assistive technology. The browser helper `waitForList` already treats the placeholder as settled only outside a busy section, so it needed no change. Test: `page/table-list/scene.test.ts` "marks the records busy while an empty list reloads, and settled once it is answered" (section's `aria-busy` fixed at false: "Expected element matching region "Records" to have attribute aria-busy="true" but received "false"").

#### The record form (findings B2-B7, B10, B11, and B12 for related lists)

Code: `apps/web/src/page/record-form/{model,message,command,update,view,fields-view,panels-view,picker-search}.ts`. Tests: `apps/web/src/page/record-form/{picker-search,picker-story,related-story,stale-story,story,scene,command}.test.ts`.

- **Edits made while a save is in flight survive it** (B2). `Submission.Saving` keeps the edits the save was built from (`sentEdits`) and the revision it was sent at. On success only the edits equal (Effect structural equality, so a password's `Redacted` compares by value) to what was sent are cleared; an edit made or changed since stays, on top of the saved record, reconciled with it as after any reread (a field the saved record withholds or shows read-only drops its edit with a note). The saved record's reference labels come from the sent edits, not the later ones. Rejected: disabling the inputs while saving (it loses nothing, but blocks typing for a round trip on every save). A create's are kept too (next bullet).
- **A create's page becomes the new record's form** (B2 for creates) [judgment]. On a create's success the page switches itself to editing the created record (`mode` `Edit`, the record as the create returned it, at the revision the create was sent at), keeps the edits made while the create was in flight exactly as for an update (cleared only where equal to what was sent; password and secret inputs stay `Redacted`), reconciles them with the update limits (a field writable only on create drops its edit with a note) and with the created record, and sets up related lists and controls; then it moves to the record's address with `replaceUrl`. The app keeps a form page whose table and record match the route (`isSameForm`), so the address change keeps this page instead of opening a fresh one, and the edits are there to save. Rejected: handing the edits to the app's root to seed a new page (a second path for the same state, and a fresh page rereads what the create just returned). A create whose record the caller can no longer see shows "Saved. You can no longer see this record." on the same page.
- **Save waits for a record read under the current metadata** (B3) [judgment]. The page keeps the revision the record was read (or saved) at (`maybeRecordRevision`; every change of the metadata's revision asks for the record again under a newer `generation`, so an answered read is always at the current revision). ### Review round 3

#### Races as rules (findings R3-1, R3-2)

Three rounds found races between renames and requests in flight, each fixed where it was found. This round replaces those per-path fixes with two rules that the form follows everywhere, and a property test that checks both rules.

- **Rule 1: one reconciliation gate.** `reconcileEdits` in `page/record-form/update.ts` is now the only code that judges the edits. Before, five places each did their own reconciliation: the form's metadata, the concrete class's metadata, a record read, a save's answer, and a create turning into an edit. Now all five store what arrived and call `reconcileEdits`. The gate is `canReconcile`: a create always passes. An edit passes only when the record on screen was read (or saved) at the metadata's revision (`isRecordOutdated` false). Behind the gate nothing is judged, and the next successful read under the current metadata reconciles once, with everything that arrived in between. When the gate is open, the edits are judged first against the definitions they were last judged with (`reconciledFields`, kept in the Model) and the definitions now, then against the record as those definitions show it. Because `reconciledFields` is kept, a dropped field's note keeps the label the user saw even when the reconciliation was deferred. One consequence for stale forms: after a `SchemaChanged` refusal, edits are no longer dropped (with notes) when the new metadata arrives. They are dropped when the reread under it arrives. Save stays disabled until then, as before.
- **Rule 2: identities that live as long as the page** [judgment].
  - **Related lists.** Each related list gets an ID from the page's `nextRelatedListId`, which is never reset or reused while the page lives. Lists are an array in metadata order. Every message of a list carries `listId`. Every request carries the list ID and the request's number: `generation` for pages, and the new `metadataGeneration` for the related table's metadata. An answer counts only when both match. A renamed back-reference keeps its list and its ID (carry-over as in round 2). A removed list's ID is gone with it, and a list made again gets a new ID.
