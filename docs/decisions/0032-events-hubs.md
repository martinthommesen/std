# 0032. Events, hubs and TMF688

Status: implemented in workstream 3H against the Step 3 contracts. This checkout contains the generic API and outbox worker, but not workstreams 3T/3I's TMF621 mapping. The TMF621 and aggregate-array integrations described below remain integration work, not conformance claims.

## Storage and registration

- [judgment J1] The generic `POST /hub` selects its table with `resource` in the registration's query, for example `resource=acmeAsset&eventType=RecordAttributeValueChangeEvent&name=Example`. Contracts 12.2 requires a table for the generic hub but does not specify how the fixed route selects it. `resource` is consumed before the remaining query is parsed with the generic API's TMF630 parser. Attribute names are resolved against the registering identity and must be always-readable throughout the selected subtree. Pagination and projection directives cannot be predicates. TMF attribute predicates compare text case-sensitively; the explicit `condition` extension preserves the field’s configured comparison.
- The registration is one local `core.subscription`, created in one change set. It has the registering identity, all operations, a checked subscription condition, and nullable `hub` JSON containing the callback, API, resource, topic, event types, original query, named field IDs and public origin.
- [judgment J2] Registration requires the protected `events.subscribe` permission, granted to `admin` explicitly, not implicitly by role name. HTTP changes reauthenticate the session inside the configuration commit. Owners can retrieve/delete their hub; an unconditional platform subscription read decision grants administrator access. Delete tombstones the subscription through the existing `delete` operation, retaining delivery foreign keys and audit history. It does not erase pending deliveries; they cease to be served.
- [judgment J3] The limit is ten successful registrations per identity in the preceding minute, including subsequently deleted registrations. The count is checked under the existing exclusive configuration lock, so concurrent registrations cannot both spend the final slot. `429` has `Retry-After: 60`; E29 already accepts this TMF deviation. Failed attempts consume no slot. Active hubs are additionally capped at 20 per identity and 10 per identity/callback hostname by default; `STD_HUB_MAX_ACTIVE_PER_IDENTITY` and `STD_HUB_MAX_ACTIVE_PER_HOST` configure positive limits, read and validated once by `HubSettings.layer` at HTTP startup; malformed configuration prevents startup. Hostnames compare without their final DNS dot. The same configuration lock serializes these checks, and unregister frees active capacity. Permission is checked before parsing the selector; hidden and nonexistent tables give the same response.

## Delivery and authorization

- Hubs use the existing `external` effect: prepare in a request transaction, call outside every transaction, then commit fenced `done`. Claims, lease deadlines, crash recovery, exponential backoff and dead letters remain the worker's. `Idempotency-Key` is the change ID. The payload is never written into the delivery row.
- [judgment J4] The public ID follows Contracts 12.1's precise rule: UUIDv5 with the change ID as namespace and the event type as name. It is stable across retries and hubs and matches the ID of the same event read through a resource topic. The workstream brief also suggested including the hub ID; that would give history and each hub different IDs, so the explicit contract rule is used. Client-topic events preserve their supplied event ID; their `EventCreateEvent` notification gets a separate derived ID.
- Current roles and permission are loaded for each attempt. Inactive identities, revoked permission, invisible images, unavailable trigger fields and unsafe query fields terminate `done` with `last_error = notAuthorized`, without a listener request. Client events additionally recheck current read access to their topic in the preparation transaction.
- Images come from the existing history reconstruction, never the current row. Updates check trigger readability on both images. Create/delete have no trigger beyond visibility; delete carries only `id`, `href`, `@type`. Attribute changes contain only readable changed values, including explicit null for removal. [judgment J5] Every active rule that writes a field contributes its `condition_reads` dependencies; source readability is traversed transitively, with cycles visited once. Inactive rules contribute nothing. Unknown historical values fail closed.
- The worker's optional external `authorize` and pure `render` hooks are the integration points for mapped APIs. They execute before the preparation transaction closes. Existing external handlers need neither hook. Record handlers retain their existing transaction and fencing behavior.

## Callback transport

- Contracts 12.2's HTTPS requirement wins over the brief's fallback policy: HTTP is accepted only for a loopback host. Credentials, fragments, control characters and backslashes in URLs are refused. The request uses the original path and query, including encoded bytes and dot segments; it appends nothing.
- [judgment J6] Every attempt resolves DNS, rejects any non-public result by default, and pins the connection to an approved address. TLS still verifies the original hostname. Loopback, private, link-local, unspecified, carrier-grade NAT, multicast and IPv4-mapped IPv6 destinations are refused. `STD_HUB_ALLOW_PRIVATE_ADDRESSES=true` opts an installation into private callbacks; it does not enable HTTP to a non-loopback address. Link-local ranges and cloud metadata addresses (including Alibaba 100.100.100.200), their mapped forms and deprecated IPv4-compatible IPv6 encodings remain denied even with the opt-in, which is logged when the transport starts. Literal destinations and localhost are checked at registration under the same policy. IPv6 transition mechanisms (6to4, Teredo and NAT64) and IPv6 documentation ranges remain denied with the opt-in, so embedded IPv4 cannot bypass the metadata block. Tests opt in and use a local listener only.
- [judgment J7] The ten-second timeout covers DNS, connection and response consumption. A response is limited to 65,536 bytes. No redirects are followed; only 2xx succeeds. Node's HTTP transport is used inside an Effect adapter so its lookup callback can pin the checked IP without changing TLS identity. Interruption aborts the request. Failures contain fixed reasons, never the URL, a listener body or credentials.

## TMF688

- `/tmf-api/event/v4` is checked against both `pins.json` and the pinned swagger. The shared API definitions are new files under `packages/api/src/v2`; generic hub paths are reflected from the shared generic definition's prefix.
- [judgment J8] `core.event_resource` is the common ordinary-record parent of `core.event_topic` and `core.event`, allowing one top-level hub subscription to receive both kinds of notification. Client topic/event operations use the record service as the caller. The client's arbitrary event body is a single JSON field and receives that field's ordinary mask. No extra rights are granted to all authenticated users.
- Read-only `record:<collection>` topics are derived from visible standard tables. [judgment J9] Their lifecycle is journaled in the configuration transaction using a deterministic internal UUID and the normal change/outbox format. The public ID remains `record:<collection>`. Thus a rolled-back schema change emits nothing and one virtual topic retains per-record ordering. Current access to the represented table is required. Client topic names reserve the `record:` prefix to distinguish the namespaces.
- Client topics have ordinary create/change/delete notifications. A posted client event emits `EventCreateEvent` to top-level hubs and the original client event to hubs on that client topic. Resource topics list the same authorized rendered changes as generic hubs, newest first; `eventTime` reflects each rendering while event IDs and committed content agree. Posting an event or deleting a resource topic is `405` (existing E24).
- [judgment J10, revised in round 3] Lists implement the pinned API's offset/limit and first-level fields plus scalar attribute filters combined with AND; repeated values and comma alternatives use OR. Both event lists are newest first and support `after`, either a readable public event ID or the opaque continuation supplied in `Link: rel="next"`. The initial `offset + limit` is at most 1,000. Requests scan further keyset batches until the visible, filtered window fills, the source ends, or 1,000 raw candidates have been considered. A scan-limited page, including an empty one, carries a next link. Clients must follow that link; a short page is final only without one. The link resets the already-consumed offset (and carries any unconsumed offset). It retains filters, limit and fields. This follows decision 0025's Link signaling with a documented bounded-scan extension to TMF630 paging (TMF630 v5.0.0 Part 1 §3.1.5); it never invents a total. `X-Result-Count` is always the number returned. `X-Total-Count` is emitted only when an initial scan reaches the end, unless `count=false`; client-topic unfiltered totals count authorized raw rows even when the payload mask suppresses their representations. Continuation pages omit totals. Unknown, malformed, expired and mismatched `after` values are 400. Topic/hub enumeration retains its separate bounded offset policy. Client JSON/array filters remain E16. Hub projections retain `callback` because the pinned Hub schema requires it.
- [judgment J12] `core.event_cursor` stores one-hour opaque UUID tokens, bound to the identity, topic and normalized filters. The position stays in the database so an exhausted scan never exposes an unreadable change or record ID, even in base64, and a continuation works across server instances and restarts without introducing a deployment secret. Issuing a continuation reclaims up to 100 expired tokens using the expiry index. Authorization is re-evaluated when following it. These are derived paging positions, not application records.
- [judgment J13] New saves store complete before/after non-secret field-ID images in `core.change_image`, in the change's own transaction. We choose per-change images rather than periodic checkpoints: the save pipeline already holds both images, so reconstruction and trigger checks use one indexed query and at most two image-bearing entries regardless of the record's age; workers use exactly the same path. This trades additional JSON storage for no checkpoint replay, no checkpoint/default boundary ambiguity, and bounded reads for long-lived tickets. Password/secret fields are excluded before serialization and current rules still mask every image. History from before this release, including old writers during the roll, uses a single set-based history reduction after the image probe: SQL returns at most three entries (create, accumulated previous, requested), preserving original field-origin/default and gap semantics. There is no version-count refusal and no per-entry network loop. The first save by the new release immediately gives that version the constant-cost path; it does not depend on backfilling images at finalize.
- [judgment J14] A request fully renders at most 100 resource candidates; after that, resource payloads contain only authorized `id`, `href` and `@type`, retaining the event envelope and event-type filtering. Client lists similarly return identity-only events beyond 100 returned representations. These are valid TMF688 Event representations (TMF688 v4.0.0 Event model); clients can GET the event for its complete authorized payload. Historical visibility and trigger-source authorization are always evaluated, even for identity-only output. The independent 1,000-candidate scan bound caps authorization/reconstruction attempts; the payload budget caps full representations and never turns a valid list into a 400. Legacy reduction may still scan the named record's pre-image history inside its one SQL query; new saved versions do not.
- Request schemas enforce the profile's required members, reference identities, and date-time syntax. `eventTime` defaults to receipt time. The upstream typo `timeOcurred` does not replace the contract's `timeOccurred`.
- TMF errors are constant, value-free Error bodies. Validation/media errors are `400`; unavailable operations are `500`; the pinned operation controls whether a missing resource or conflict can be returned. The documented top-level `GET /hub/{id}` extension remains available even though the swagger omits it. The HTTP test client validates TMF688 responses against the pinned swagger, including declared statuses; E29 and that GET extension are explicit cases.

## Upgrade and scope

- [judgment J11] Migration 0018 adds only a nullable `core.subscription.hub` column and declares `expand`. Core set version 3 adds the permission and data classes. Old subscription JSON without `hub` continues to decode. No new definition kind, dependency kind or field type is introduced. An older worker cannot serve these hubs and leaves their deliveries unclaimed. The existing producer's `min_worker_version` applies; Step 3 still upgrades offline. Admission/finalization policy and opaque preservation of future properties remain the explicitly deferred Step 5 work of Contracts 8.8/decision 0030.
- No TM Forum member document is copied here. Sources are Contracts 12, decisions 0021/0026 and the already-vendored Apache-2.0 TMF688 swagger.
- TMF621 mapping-specific triggers/status variants and aggregate array projections require 3T/3I, absent from this starting commit. They must use the same hooks, include every mapped source in trigger checks, and add their own proving tests before their matrix rows are marked tested. Nothing here claims those integrations or the whole Step 3 gate complete.

## Review round 2

Migrations 0019–0021 add derived resource/client event lookup tables, a concurrent `(record_class_id, occurred_at DESC, id DESC)` index and a restartable UUID-keyset backfill. These lookup entries describe existing changes rather than new logical records; the backfill intentionally writes no record history. New entries commit with their change or client event. Single-event requests use indexed lookup keys and then apply the normal read policy. Resource pages seek independently in each concrete class's index and merge a bounded window; they cache field origins per class for that request.

Event-type exclusions finish with `last_error = filtered`, independently of `notAuthorized`; predictable exclusions are removed before inserting deliveries. Synthetic topic UUIDs are computed once per immutable snapshot, only when a topic needs them. Resource-topic condition evaluation uses `InstanceSettings.timeZone`. Query-field permissions are rechecked across the whole subtree at commit.

The TMF688 contract checker rejects undeclared paths and methods, except the explicit top-level hub GET extension, and permits 429 only for hub POST routes. TMF621 notifications remain pending; the matrix now describes the implemented delete identity payload accurately and the attribute-change test asserts its id and href.

## Review round 3

Migrations 0022–0026 are additive expand migrations. 0022 adds `change_image`, opaque paging positions and the expiry index; 0023 adds an immutable, extension-free UUIDv5 SQL expression for the three fixed record event names; 0024 builds its expression index concurrently over existing `core.change` rows; 0025 concurrently indexes the client event-ID change-field expression; 0026 concurrently indexes lookup maintenance by record ID. The fixed UUID namespace plus each fixed event name fits SHA-1's single block, so the SQL function needs no extension or mutable database state. Its UUIDv5 results are tested against the application's implementation for all kinds; it is an identifier, not a security hash. The expression index is built during expand, so old-writer changes remain searchable throughout the roll. The extra index/storage write cost buys indexed point reads without a finalize-time prerequisite.

A missing resource/client lookup key falls back to these bounded indexed `core.change` lookups only while 0021's ledger row is absent or incomplete; that ledger state is read once per point/event-ID-cursor request. Normal list keysets do not depend on lookup backfill. Migration 0021 has separate bounded resource and client UUID-keyset phases, persists the client phase in its cursor, skips keys already present, and counts missing keys in both tables before marking itself complete. Interrupted batches roll back with their progress; a resumed runner completes only what remains.

`core.client_event` is maintained by the fixed save-pipeline image step, covering TMF688 and generic record creates, updates and deletes. A failed lookup insert rolls back the record, image and change together. [judgment J15] Lookup, image and cursor tables are derived implementation data, not logical records: maintaining them directly avoids fictitious record history/deliveries and recursion into the save pipeline. `DataMigration` now documents this exception while retaining the batching, resumability and exact `remaining` requirements. Record mutations in data migrations still use the save pipeline.

The condition persistence check uses `Effect.die` for its true parser invariant. Page generator names, the bounded `recordsWindow` name/span/documentation, and resource-event options now describe their actual operations. The new tests cover old histories over 1,000 versions, constant image reads and worker reconstruction, filtered/hidden/unauthorized scans with opaque continuations, identity-only budget output, newest client rows beyond 1,000, row-based completeness, both save paths and rollback, pre-finalize lookup fallback, interrupted backfill, metadata encodings, normalized host caps and startup config failures.
