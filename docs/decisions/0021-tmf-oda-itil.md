# 0021. TM Forum, ODA and ITIL compatibility

Status: proposed, 2026-10-22 (re-plan, branch `ws/plan-tmf-oda-itil`). It awaits Martin's answers to the open decisions below. Docs only: plan Steps 3 to 5, Contracts 10 to 14, `docs/servicenow-mapping.md`, `docs/workstreams.md`.

## The requirement

Martin, 2026-10-22: strict TM Forum, ODA and ITIL compatibility on everything, as a hard requirement. His decisions, binding for this plan:

1. **APIs, both layers.** (a) STD's own generic API (records, metadata, change sets, auth, history) is reworked to follow the TMF630 REST API Design Guidelines: resource naming, `fields`, filtering, `offset`/`limit`, `X-Total-Count`/`X-Result-Count`, sorting, merge-patch and JSON Patch, polymorphism (`@type`, `@baseType`, `@schemaLocation`, `@referredType`), `href`/`id`, the error format, hub/listener notifications. (b) Standard TMF Open APIs ship as mappings onto STD tables and are validated in CI with TM Forum's Conformance Test Kits (CTKs).
2. **Scope for v0.1:** TMF621 Trouble Ticket over ITIL incident and problem, with the helpdesk rebuilt on it; TMF632 Party, TMF669 Party Role and TMF672 User Roles and Permissions over STD's users, roles and access rules; TMF688 Event and the hub/listener pattern on the outbox; TMF638 Service Inventory and TMF639 Resource Inventory as the ITIL CMDB; TMF641 Service Order and TMF622 Product Order for change enablement and service request management.
3. **ODA:** STD is packaged as real ODA Components, with specifications listing exposed and dependent APIs, security and events, and CI deploys them on the open source ODA Canvas.
4. **Timing:** `v0.0.2` ships the generic UI as planned; the new plan applies from the next step, which also rebuilds the helpdesk.

### TMF630 REST API Design Guidelines

- v4.2.0 is the production version (Forum Approved May 2021) and is labelled "Available to all"; v5.0.0 is pre-production, with most parts "coming soon", and needs a TM Forum membership ([v4.2.0](https://www.tmforum.org/resources/specification/tmf630-rest-api-design-guidelines-4-2-0/), [v5.0.0](https://www.tmforum.org/resources/specifications/tmf630-rest-api-design-guidelines-5-0-0/); confirmed by the round 1 review; the pages refuse automated access, so whether v4.2.0's download needs a free login is [unverified]; a login is not a membership). Seven parts: naming, CRUD, filtering and notifications; polymorphism and extension; hypermedia; lifecycle and tasks; JSON Patch for arrays; JSONPath; JSON Schema patterns ([DIR] entry for TMF630).
- **Baseline.** The v4.2.0 text is the verified baseline: workstream 3G reads it and enters every normative rule into the requirements matrix (Contracts 15), where it still applies to v5. This re-plan could not fetch it, so Contracts 10's first draft reads the rules from Part 1 R14.5.1 of 2015 ([PDF](https://projects.tmforum.org/wiki/download/attachments/43253967/TMF630_REST_API_Design_Guidelines_Part_1_R14.5.1.pdf)) and from what applies them, and marks those rules [unverified] until the matrix row is checked against v4.2.0: the v5 OpenAPI documents (TMF621 v5.0.1 above all, [OAS](https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-Trouble_Ticket-v5.0.1.oas.yaml)), the [TMF621 v5.0.1 user guide](https://tmf-open-api-table-documents.s3.eu-west-1.amazonaws.com/OpenApiTable/TMF621_Trouble_Ticket/5.0.0/user_guides/TMF621_Trouble_Ticket_userguide-v5.0.1.pdf) and its [conformance profile](https://tmf-open-api-table-documents.s3.eu-west-1.amazonaws.com/OpenApiTable/TMF621_Trouble_Ticket/5.0.0/conformance/TMF621_Trouble_Ticket_v5.0.1_conformance.pdf).
- What those show: `{apiRoot}/tmf-api/<apiName>/v<major>/<resource>` with singular lowerCamelCase resources; `id` and `href` required in responses; `@type` required on every object in v5 (`Extensible`), with `@baseType` and `@schemaLocation`; `EntityRef` (`id` required, `name`, `@referredType`, `href`); `*RefOrValue` as `oneOf` with an `@type` discriminator; query parameters `fields`, `offset`, `limit`, `before`, `after` (opaque cursors), `sort` (`-` reverses), `filter` (JSONPath); `X-Total-Count` and `X-Result-Count` on list `200` responses (no `206` in v4 or v5); PATCH with `application/merge-patch+json` (mandatory), `application/json-patch+json` (optional) and `application/json-patch-query+json`; the `Error` resource (`code`, `reason` required; `message`, `status`, `referenceError`); hubs (`POST /hub` with `callback` and `query`, `GET` and `DELETE /hub/{id}`) and listeners (`POST /listener/<eventName>`); the event envelope (`eventId`, `eventTime`, `eventType`, `event: {<resource>: …}`, `correlationId`, `domain`, `timeOccurred`, …). The comparison operators (`.gt`, `.gte`, `.lt`, `.lte`) and the OR forms (`a=x,y`, repeated parameters) were seen only in the 2015 text and are marked [unverified for v5] until checked against v4.2.0.

### Conformance Test Kits

- **Distribution.** Each directory page links its kit, reference implementation, OpenAPI document, Postman collection and conformance profile in [S3], downloadable without a login (for example [tmf621-v5.0.0-ctk-1.0.1.zip](https://tmf-open-api-table-documents.s3.eu-west-1.amazonaws.com/OpenApiTable/TMF621_Trouble_Ticket/5.0.0/ctk/tmf621-v5.0.0-ctk-1.0.1.zip)). TM Forum re-released the kits "in a dockerized format" in January 2026 and changed their proxy settings in May 2026.
- **What a kit is.** A `docker-compose.yaml`, `run.sh`, `config.json` (`url`, optional `headers`, `payloads` per resource and method) and a public image (for example [`tmforumorg/tmf621-v5.0.0-ctk`](https://hub.docker.com/r/tmforumorg/tmf621-v5.0.0-ctk)) holding a Cypress suite; it writes mochawesome reports (`reports/index.json`). The TMF621 kit's sample report has 44 tests ([instructions](https://www.tmforum.org/wp-content/uploads/2026/02/TM-Forum-Open-API-conformance-testing.pdf)).
- **CI pitfalls.** The TMF621 image's entrypoint runs `npm start || true`, so that container exits 0 when tests fail (observed for TMF621's kit only); the runner trusts no kit's exit code and decides from the report (Contracts 11.1). Version labels differ: the TMF621 OpenAPI document is v5.0.1 while its kit is `tmf621-v5.0.0-ctk-1.0.1`; the pin records both. `run.sh` calls `xdg-open`, so CI runs the compose service directly. The kit calls `DELETE /tmf-ri-admin/v1/clear-all-data` and ignores a 404.
- **Licence.** The kit scripts carry Apache-2.0 headers, but the bundle has no licence file and the directory's licence field is empty; older kits (2018 to 2021, [tmforum-rand](https://github.com/orgs/tmforum-rand/repositories)) are RAND "Notice": copyable, not modifiable ([RAND-LICENSE](https://github.com/tmforum-rand/RAND-LICENSE)). **Plainly: running the kits in public GitHub Actions needs no login or membership (all eight pinned kits download, confirmed by the round 1 review) and nothing visible forbids it; whether they may be redistributed is unverifiable from what TM Forum publishes.** So CI downloads them by pinned URL and digest and never commits them.
- **Certification** is a paid membership benefit; running the kits is not ([process](https://www.tmforum.org/conformance-certification/process-overview/), [Q&A](https://www.tmforum.org/how-can-i-get-my-api-implementation-to-be-conformant-to-tm-forum-open-api-specifications/)).

### ODA Component specification and TM Forum's golden components

- **Version.** `oda.tmforum.org/v1`, generally available since December 2024 and unchanged from v1beta4; the Canvas CRD serves v1beta2 (deprecated) to v1, with v1 as storage version and a conversion webhook ([release notes](https://github.com/tmforum-oda/oda-canvas/blob/main/release-notes/ReleaseNotes.md), [CRD](https://github.com/tmforum-oda/oda-canvas/blob/main/charts/oda-crds/templates/oda-component-crd.yaml)). The conceptual model is IG1171 ODA Component Definition v5.0.0 ([IG1171](https://www.tmforum.org/resources/best-practice/ig1171-oda-component-definition-v5-0-0/)).
- **Schema.** `componentMetadata` (`id`, `name`, `version`, `functionalBlock`, …); `coreFunction` and `managementFunction` (`exposedAPIs`, `dependentAPIs`); `securityFunction` (`canvasSystemRole`, `componentRole[]`, exposed and dependent APIs, `secretsManagement`); `eventNotification` (`publishedEvents`, `subscribedEvents`). An exposed API has `name` and `specification[]` (`url`, `version`, `apiType` `openapi`, `mcp` or `a2a`), plus `id`, `apiSDO`, `implementation`, `path`, `port`, `required`, `gatewayConfiguration` ([v1 example](https://github.com/tmforum-oda/oda-canvas/tree/main/feature-definition-and-test-kit/testData/productcatalog-dynamic-roles-v1/templates)).
- **Golden components.** 35 golden specifications live in [TMForum-ODA-Ready-for-publication](https://github.com/tmforum-rand/TMForum-ODA-Ready-for-publication) (no licence file; the PDFs are RAND), also on tmforum.org's [components map](https://www.tmforum.org/oda/directory/components-map). TMF632 is exposed by TMFC028 Party Management; TMF669 and TMF672 by TMFC035 Permissions Management (with v4's `permission` and `userRole`); TMF638 by TMFC008 Service Inventory (which requires TMF633 as a dependent API); TMF639 by TMFC012 Resource Inventory; TMF641 by TMFC007 Service Order Management; TMF622 by TMFC003 Product Order Delivery Orchestration; TMF688 by TMFC061 Work Order Management (hub and listener only). **None of the 35 examined golden specifications exposes TMF621 or TMF724.** Golden specs mostly name v4.0.0 APIs, and all 35 declare TMF669 `partyRole` as their security API.
- **Component conformance.** TM Forum certifies components against a golden specification for members: the manifest ID must match and every mandatory exposed and dependent API must be present and conformant ([conformance](https://www.tmforum.org/oda/directory/conformance); the TMFC008 conformance profile in the repository above). A component with fewer APIs cannot be certified as that TMFC; directory pages list "mandatory Open APIs certified" and "full mapping" tiers below full conformance ([TMFC008](https://www.tmforum.org/oda/directory/components-map/production/TMFC008)).

### ODA Canvas

- Apache-2.0 ([LICENSE](https://github.com/tmforum-oda/oda-canvas/blob/main/LICENSE)). Install Istio, then the `canvas-oda` Helm chart (stable 1.2.5, March 2026; `main` at 1.2.6-rc7), without `--wait`, which deadlocks on post-install hooks ([installation](https://github.com/tmforum-oda/oda-canvas/blob/main/installation/README.md), [chart index](https://tmforum-oda.github.io/oda-canvas/index.yaml)). The chart brings cert-manager, the CRDs, Keycloak, the component, API (Istio by default; Kong or APISIX), identity-config, dependent-API, secrets (Vault, optional) and other operators, a conversion webhook and a TMF639 resource inventory ([Chart.yaml](https://github.com/tmforum-oda/oda-canvas/blob/main/charts/canvas-oda/Chart.yaml)).
- **Deployment.** The component operator splits a Component into `ExposedAPI`, `DependentAPI`, `PublishedNotification`, `SubscribedNotification`, `SecretsManagement` and `IdentityConfig`, each reconciled by its operator ([operators](https://github.com/tmforum-oda/oda-canvas/tree/main/source/operators)).
- **Security.** The Keycloak identity operator creates one client per component, adds `canvasSystemRole` as a client role for the Canvas, and takes component roles statically or dynamically by listening to the component's TMF672 `PermissionSpecificationSet` API (preferred) or TMF669 `PartyRole` API (to be deprecated) ([TMFOP003](https://github.com/tmforum-oda/oda-canvas/blob/main/source/operators/TMFOP003-Identity-Config/README.md)).
- **Requirements.** Kubernetes 1.22 to 1.30; kind is "used in all the GitHub action automated testing"; Istio (docs 1.16.1, CI 1.26.3); 4 cores, 16 GB RAM, 50 GB disk minimum.
- **In GitHub Actions.** TM Forum's own [workflow](https://github.com/tmforum-oda/oda-canvas/blob/main/.github/workflows/trigger_tests.yml) installs kind (node 1.30), cloud-provider-kind, Istio and the Canvas on `ubuntu-latest` and runs the BDD features in about 30 minutes; about half of recent upstream runs failed and some ran for hours (sampled 2026-10-22, [runs](https://github.com/tmforum-oda/oda-canvas/actions/workflows/trigger_tests.yml)). A public runner has 4 vCPU, 16 GB RAM and 14 GB disk ([runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). **Plainly: it fits, slowly and flakily; it belongs in a nightly and release-candidate workflow, not on every PR.**
- The Canvas BDD kit ([feature-definition-and-test-kit](https://github.com/tmforum-oda/oda-canvas/tree/main/feature-definition-and-test-kit), Cucumber, Apache-2.0) tests the Canvas (install, upgrade, exposed APIs, roles), not an API's conformance; the golden-component CTK (in the Ready-for-publication repository) needs a live Canvas and downloads the API kits.

### ITIL

- **Edition.** ITIL (Version 5) launched in phases from January 2026; ITIL 4 runs in parallel until its modules are sunset on 31 December 2027; both have 34 practices, and all six practices relevant here sit in the Practice Manager modules ([PeopleCert FAQ](https://www.peoplecert.org/help-and-support/faq-itil), [ITIL Version 5 explained](https://www.peoplecert.org/news-and-announcements/itil-version-5-explained)). The practice guides are behind PeopleCert Plus membership.
- **Concepts STD implements, in its own words.** An incident is an unplanned interruption or quality reduction of a service; a major incident is handled with its own procedure; a problem is a cause or potential cause of incidents; a known error is a problem that has been analysed but not resolved; a workaround reduces the impact while no resolution exists; problem management runs identification, control and error control; change enablement assesses risk, authorizes changes and manages the schedule, with standard (pre-authorized), normal and emergency changes and a change authority; service request management fulfils pre-defined requests, often with approval; service configuration management keeps configuration items and their relationships ([change enablement](https://www.axelos.com/certifications/itil-service-management/itil-practices-manager/itil-4-specialist-plan-implement-and-control/itil-4-practitioner-change-enablement/), [2023 practice refresh](https://www.peoplecert.org/news-and-announcements/2023/itil-4-management-practices-2023); definitions of problem, known error and workaround as reported by [InvGate](https://www.invgate.com/guides/problem-management), a secondary source). Priority from impact and urgency is established practice, not something the current guides are known to prescribe [unverified]; tools make it configurable. ITIL describes practices, not tool states [unverified, guides not read].
- **Licensing.** Commercial products reproducing ITIL material need a PeopleCert licence; marks need the acknowledgement "ITIL® is a registered trademark of the PeopleCert group" ([third-party licensing](https://www.peoplecert.org/Organizations/Services/third-party-product-licensing-service), [marks policy](https://www.peoplecert.org/-/media/folders-reorganized/legal-documents/qmepo13-marks-usage-policy.pdf)). STD copies no ITIL text.

### TM Forum and ITIL

- TMF621 is a generic ticket for problems, incidents or requests: `ticketType` is free text, its states are an example set, `severity` and `priority` are free strings, and it has no impact or urgency and no mention of ITIL ([OAS](https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-Trouble_Ticket-v5.0.1.oas.yaml)).
- TMF724 Incident Management (v4.0.0) is TM Forum's ITIL-shaped incident API (impact, urgency, priority, diagnose and resolve tasks) but network-flavoured (states raised, updated, cleared) ([OAS](https://github.com/tmforum-apis/TMF724_IncidentManagement/blob/main/TMF724_Incident_Management_API_v4.0.0_swagger.json)). TMF656 Service Problem Management (v5.1.0) models service faults, not ITIL problem control: no known error or workaround ([OAS](https://raw.githubusercontent.com/tmforum-apis/TMF656_ServiceProblemManagement/main/TMF656-Service_Problem_Management-v5.1.0.oas.yaml)). No TMF API models known errors, workarounds or change authority.
- TM Forum's eTOM and ITIL material predates ITIL 4 (GB921 "Using eTOM and ITIL Together", R15; [suite](https://www.tmforum.org/resources/suite/gb921-using-etom-and-itil-together-suite-release-15-0/)).
- So STD maps ITIL onto TMF621 itself: ITIL states onto TMF621's example states, impact onto `severity`, urgency and the other ITIL attributes onto characteristics, the ITIL class onto `ticketType`. ServiceNow's TM Forum-certified TMF621 does the same with `ticketType` Case or Incident and severity onto priority (`docs/servicenow-mapping.md`).

## Architecture

### One enforcement point, three API surfaces

The record service stays the only place that reads and writes records, enforcing access rules, masks, history, the outbox and stale checks (Contracts 2 to 6). Above it sit three surfaces, each a thin adapter:

| Surface | Path | Contracts | Shapes |
| --- | --- | --- | --- |
| Generic API v2 | `/api/v2` | 10 | every table, TMF630 shape, STD names and classes |
| TMF Open APIs | `/tmf-api/<apiName>/v<major>` | 11 | the nine pinned APIs over shipped classes |
| Generic API v1 (frozen) | `/api/v1` | 6 | removed in `v0.1.0` |

Events for all three come from the outbox (Contracts 12); ODA packages the server as one Component (Contracts 13); ITIL behavior is shipped configuration (Contracts 14). Nothing in this design adds a second evaluator of access rules, so every Contracts 3 test keeps its meaning and is run through the new surfaces.

### The generic API rework and compatibility

What changes for clients (Contracts 10.1, 10.7): paths (`/api/v1/tables/{t}/records` → `/api/v2/{t}`), the record shape (envelope → flat resource with `@type` and EntityRefs; definition names → lowerCamelCase API names; `labels` → EntityRef `name`), lists (envelope with `nextCursor` and `count` → array with `X-Total-Count`, `X-Result-Count` and a `Link` header), write responses (`DELETE` 200 with a body → 204), errors (`{_tag, …}` → TMF `Error`), sign-in (`auth/*` → `session`). Unchanged: the save pipeline, `If-Match`, `STD-Schema-Revision` and `SchemaChanged`, the cookie and CSRF rules, value shapes.

Options for the existing clients (`v0.0.1`, `v0.0.2`, the release-compatibility CI step, the web app):

1. **Versioned paths with a deprecation window (recommended).** v2 is added beside v1 in Step 3; v1 is frozen and carries `Deprecation` and a successor link; the web app, the quickstart and the typed client move to v2 in Step 3; v1 is removed in `v0.1.0`. The release-compatibility step keeps proving that the previous release's quickstart runs unchanged at every step, because by the time v1 goes (`v0.1.0`), the previous release (`v0.0.4`) already speaks v2. TMF630 itself versions APIs by major version in the path, so this is the standard's own way. Cost: two route sets for two steps, and the authorization suites run on both.
2. **Hard break in Step 3 with a migration note.** Cheaper by one route set, but the release-compatibility step would need an exception for `v0.0.2` → `v0.0.3`, the one transition where the API changes most, and the web app would have to switch in one PR.
3. **Keep v1 after `v0.1.0`.** A non-TMF API in the first public release contradicts the requirement.

### Polymorphism and the class hierarchy

STD's class hierarchy is TMF630's polymorphism: `@type` is the concrete class, `@baseType` its parent, `@schemaLocation` the caller's schema of the concrete class (Contracts 10.2). A create through a parent collection may name a subclass in `@type` (10.5), which widens Contracts 2.2 item 5 for v2 only. In TMF APIs, shipped classes render the TMF type their mapping names, and local child classes render their own name with the TMF type as `@baseType`, which is TMF's extension pattern (11.1). For TMF621 the ITIL class goes into `ticketType` and `@type` stays `TroubleTicket`, because TMF clients and the kit post `TroubleTicket` [judgment]. TMF639's resource subtypes are real child classes, so `@type` there is the class.

### TMF filtering and the condition AST

Every TMF filter becomes a condition AST (Contracts 5.2) before anything runs: `a=v` → `eq`, `a=v1,v2` → `in`, `.gt`/`.gte`/`.lt`/`.lte` → `gt`/`ge`/`lt`/`le`, dotted references → one-hop paths, `@type` → `class`, all ANDed with the `condition` text parameter (10.3). So TMF filters inherit the visible-schema resolution (3.4), masking (3.5), the SQL compiler and the differential test (5.9); `tmf-filter-equivalence` proves the translation. TMF mappings add value translation (a TMF status to a set of STD states, `severity` to `impact`) before the AST is built. JSONPath (`filter`) is refused in v0.1, because the AST has no array semantics.

### TMF PATCH and the save pipeline

Merge-patch is exactly STD's update body (6.7: absent unchanged, `null` clears), plus RFC 7396 merging inside json fields. JSON Patch is applied to the caller's readable image and turned into an update body, with reads of unreadable sources treated as unknown names (3.4). Names are resolved and the stale check (`SchemaChanged`) runs first, at the request's revision; then the root lock, visibility and the version check; only then is the patch (or the json merge) evaluated, against the locked version, so a `test` or `copy` can never see a state older than the one it writes over, even without `If-Match` (Contracts 10.5). The rest of the pipeline is unchanged: access checks on both states, validation, hooks, history and deliveries. The generic API keeps `If-Match` required; TMF APIs make it optional because their clients and kits send none (10.5, 11.1). Arrays that hold STD records are aggregate parts of the parent (Contracts 11.1). A part's owner reference is read-only after create; every write of a part, through any surface, locks its owner chain outermost first; and each touched owner is finalized once per transaction, after the outermost save and before commit, with its own version, change entry and derived state. So a resource's ETag, history and events change in every transaction that changes any part of it, and an owner is never re-saved while it is on the save stack.

### Hub/listener, subscriptions and the outbox

A hub registration is a `core.subscription` (Contracts 4.6) whose identity is the registering user, created through a change set, gated by the `events.subscribe` permission (12.2). Its `query` becomes the subscription's event-type list and condition. Each matching save writes a delivery row in its transaction, as for every subscription; the Step 3 worker authorizes and renders the event for the API and the identity at delivery time, and POSTs it to exactly the registered `callback` URL, retrying with backoff and dead letters. Authorization covers the event's existence, not just its payload: each event type is sent only when the identity can read the fields that triggered it on both images, and a derived trigger field (a TMF status, a rule-computed priority) counts only when all its sources are readable too (Contracts 12.1). This gives TMF listeners what the outbox already guarantees: no event for a rolled-back save, per-record version order, at least once, and a stable `eventId` derived from the change ID. TMF688 adds topics over the same subscriptions and `core.event` records for client-posted events (12.3). Config changes produce events too: a subscription may name the `role` or `accessRule` config kind, and the change set's own transaction writes its deliveries (Contracts 4.6). An access-rule change also bumps the version of each role it names, so every event about a role follows that role's own version order. This is what lets the Canvas mirror STD's roles into Keycloak with rollback and per-role order guaranteed.

### Parties, roles, permissions and ODA security

- **STD stays the policy decision point.** Every record, field and permission decision is STD's access rules (3.2) on the caller's effective roles. TMF672 is a projection of those rules and roles, writable only where the projection is lossless (11.3); `CheckPermission` is explain mode.
- **The Canvas identity provider authenticates and assigns.** Keycloak issues tokens; STD validates them (13.4), maps the subject to a `core.user` through the external identity mapping, and adds the token's client roles that name live STD roles to the user's effective roles. STD publishes its roles to the Canvas through TMF672, and the Canvas mirrors them into Keycloak client roles (13.3). So role assignment can live in Keycloak, while what a role may do stays in STD.
- **TMF632 and TMF669 are business data.** Individuals, organizations and party roles (customer, supplier) are records in `core`; party roles grant no access. A user is linked to its individual, so tickets and orders name parties (`relatedParty`) and users consistently.
- **Why not let ODA decide.** ODA's roles are coarse (per component client); STD's rules are per record and field, with conditions and masks. Moving decisions out would break the non-interference guarantee and every Contracts 3 test.

### ODA packaging

One STD Component per install (Contracts 13), a custom component: STD's value is one data model with foreign keys and one rule set, which ODA's per-component data ownership would split; and none of the 35 examined golden specifications exposes TMF621, so STD could not be certified as a golden component in any packaging. Splitting along golden boundaries (TMFC028, TMFC035, TMFC008, TMFC012, TMFC007, TMFC003) later would need federated references (a reference whose target lives behind another component's API) and the v4 API versions those golden specs name. Each exposed API can still be individually certified by TM Forum. Upgrades stay offline on Kubernetes too: the chart's pre-upgrade hooks stop the server and worker before `std upgrade` runs, and a failed migration leaves them stopped. Installs run `std upgrade` in a post-install Job, because pre-install hooks run before a bundled database exists, and init containers hold the servers until it has finished (Contracts 13.1).

### ITIL as configuration

The ITIL practices are shipped configuration in the `helpdesk` and `cmdb` sets: choices for states and codes, record rules for the priority matrix, state transitions, required fields and cross-record effects, access rules for roles such as the major incident manager (Contracts 14). That keeps them overridable per install (Contracts 8) and testable through every surface. It needs four record-rule action kinds, which workstream 3A adds (14.1). Change and request behavior is specified as transition tables, approval invalidation, cancellation rules and concurrent outcomes in Contracts 14.4, not by reference to ServiceNow.

### Evidence: the requirements matrix

"Strict" needs a gate, not a recommendation. Every normative requirement of each pinned specification (TMF630 v4.2.0 and its v5 changes, each Open API's conformance profile, OpenAPI document and kit cases, the ODA Component CRD, and Contracts 14's ITIL behaviors) is a row in `docs/conformance/`, mapped to an existing test or to an exclusion Martin accepted. A CI check fails on a row naming a missing test or decision, and each step's release gate fails on a `pending` row or an exclusion that is undecided or rejected (Contracts 15).

Contract changes from the round 1 review:

26. **Aggregate parts** (Contracts 6.5, 11.1). A reference may be declared `aggregate`; every write of a part, through any surface, locks the owner chain first, and each touched owner is finalized once per transaction (version, change entry, derived state) after the outermost save. Recommendation: accept; without it, a generic write to a note or order item would change a TMF resource without changing its ETag or emitting its event, and derived parent state would need recursive saves.
27. **Config subscriptions** (Contracts 4.6). Subscriptions may name the `role` and `accessRule` config kinds, with deliveries written in the change set's own transaction, and an access-rule change bumps the version of each role it names. Recommendation: accept; the Canvas's dynamic role sync needs it, and it keeps rollback and per-role order (the alternative, per-rule order for rule-driven role events, would be an exception to the 4.7 ordering promise).

Contract changes from the round 2 review:

28. **Aggregate ownership** (Contracts 6.5, 11.1). Owner references are required and read-only after create, so a part never moves (a move is a delete and a create, which finalizes both owners); owner chains have no cycle and at most 3 levels; operations touching several aggregates lock them by root ID. Recommendation: accept; movable parts would need two-owner locking on every update.
29. **`data` migrations** (Contracts 1.9, 1.10, 3.1, 8.5). A new migration kind that writes records through the save pipeline as the system user, run by `std upgrade` after set loads, with a ledger `state` (`running`, `applied`) that server start and `doctor` check. Recommendation: accept; the party backfill needs it, and the alternative (backfilling lazily on first use) leaves users without individuals for an unbounded time.
30. **Events stricter than reads** (Contracts 12.1). A listener gets no event triggered by a derived field (a rule-computed priority, a TMF status) unless it can read every source, although the same user can read the derived field through the API and its history. Recommendation: accept; an event's existence tells a listener exactly when a hidden source changed, which a read of the current value does not.
