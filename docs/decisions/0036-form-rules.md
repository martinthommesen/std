# 0036. Form rules and binding form-state verdicts

Status: accepted for workstream 3C, 2026-10-23. Requirements: Contracts 3, 4.10, 5.8, 5.10, 6.3, 14.1–14.3; decisions 0020 and 0034. The glossary records the three domain concepts: form rule, proposed record and form-state verdict.

A form must show the derived proposal under the caller's permissions before it saves. The record service must accept a write that violates only a form rule. Keeping these as a separate definition kind and a non-persisting task resource makes that separation explicit; a client-side copy of helpdesk logic would drift from shipped and locally overridden record rules.

## Definition model

`formRule` is stored in `core.form_rule`. Its immutable identity, owner and lifecycle follow other definitions. It has `classId`, `fieldId`, `name`, `order`, `active`, nullable `condition`, `property` (`required`, `readOnly`, `hidden`, `choices`) and `value` (a boolean, or choice keys for a choice restriction). A null condition always holds. Set files declare `formRules`, naming the table and field; resolution stores stable IDs. Rules attach to ordinary stored classes, as record rules do. Validation checks the target lineage, identifier, uniqueness and the `formRule` condition profile, including the refusal of quantifiers. Optional `clearHidden` notices configure a caller-authorized clear of a hidden boolean; an optional `message` supplies guidance. Dependencies protect its class, target field and condition fields from purge.

**J1 [judgment]: composition.** Active, non-retired rules are inherited from all ancestors, globally ordered by order then ID. Each matching assignment replaces the previous form-only value of that property. Schema-required, schema-read-only, auto-number and access restrictions remain effective. Conditional requirements apply to fields the form can show and edit; form-only hidden/read-only fields are omitted from the write body. Local overrides can replace `active`, `clearHidden`, `condition`, `message`, `order` and `value`; the set owns the target field and property. A removed shipped rule is deactivated, like a record rule. These choices make local replacement explicit without changing API validation.

**J2 [judgment]: storage and rollout.** Migration 0030 is additive/expand and creates the platform table, checks, deferred references, trigger and live-name index. Core's set version advances from v4 to v5 with the class and field definitions. Existing migrations stay frozen; doctor's catalog is regenerated. Helpdesk v3 is still the unreleased Step 3 set, so its version remains 3 and the tested v2→v3 upgrade partition adds form rules as finalize behavior. Step 5 must register `formRule` as a new feature before mixed-version admission; this change does not claim to implement those fences.

## Form-state task resource

`POST /api/v1/checkFormState` takes `{ table, id, revision, values }`: the table's collection name, null ID/revision on create, or an existing record's UUID and positive revision on update, and a partial values object in API attribute names. References in the request are EntityRefs as on other writes. It returns `{ schemaRevision, revision, fields, values, messages }`, with field states (including choice restrictions and caller-authorized clear instructions), configured messages and canonical values keyed by API attribute name. Returned references are UUID values, rather than resource representations. Write-only values are never returned.

The shared `@std/api` schema documents the route and builds the typed client. The handler authenticates the normal bearer or cookie session, checks the stated schema revision over the table's full field selection before translating names, and calls the record module. Unknown tables/fields and hidden ones follow the existing error rules. Cookie requests require `STD-Client: web`, and all answers are `no-store`.

Existing visibility is checked before the supplied record version is disclosed. Existing-state and proposed-state record/field permissions use the save pipeline's same SQL predicates; proposed-state checks run over a one-row relation of candidate values. Change detection is shared with saves. Only derive rules run, as the caller and with supplied-field provenance; no guards, invariants, number assignment, persistence, history or outbox work runs. Access refusal returns no simulation. Fields on the proposed and previous images, and preloaded reference targets, are masked independently. Metadata substitutes empty for never-readable condition fields and simplifies before delivery. The returned states name only readable fields.

**J3 [judgment]: update consistency.** The task reads without a row lock and repeats existing visibility/version checking before returning. A changed or deleted root invalidates the whole answer; monotonically increasing versions prevent a changed-then-restored record from passing. This keeps preview traffic from blocking saves in STD's READ COMMITTED request transactions. A write after the final check is caught by the eventual save's version check. An unchanged update skips derive execution just as saving does. Metadata changes trigger the existing stale-request scope and a form/record refresh preserving edits by ID.

**J4 [judgment]: request granularity and unavailable context.** The browser evaluates only what it knows. Before it has the server's derived proposal, derived fields are unavailable; local constant/short-circuited conditions can still decide. Unsupported profile constructs, missing metadata/data/context, unavailable Temporal support and newer Unicode yield Unknown. It always checks forms that have rules with the task resource, even if a local condition is decidable, because record-rule conditions and derives are deliberately absent from browser metadata. Each form allows one form-state request in flight. Edits during it replace the queued proposal in the Model; its completion discards a superseded success or refusal and starts only the latest proposal. This coalesces rapid typing without a debounce interval and avoids duplicating server derives. When metadata already rules out editing, a viewer requests no write simulation and shows no pending field placeholders. Metadata can also say `perRecord`; it does not carry the record-level update decision. For those forms the initial empty proposal uses the existing task resource and update-access evaluator: when existing-state update access is refused, it returns the stored, caller-masked values with every readable field read-only and a neutral viewing notice. It runs no derives, form rules or hidden-field corrections, and rechecks visibility and version before returning. Non-empty proposals still receive the normal access refusal. The browser renders those states as values and omits Save; attempted edit and Save Messages issue no further check or write. This avoids a new permissions endpoint or public response field while keeping record access authoritative on the server. A request key includes values, metadata revision, record ID and version. Time-sensitive rules are evaluated at each proposal check; the form does not schedule clock-only rechecks. The eventual write still uses its own server time. Generation numbers identify proposals and the occupied request slot on both success and failure. This does not rely on Foldkit interruption: `interrupt: true` registers a Command, but only an explicit `LoadFormState.Interrupt` would interrupt it, and interruption cannot undo server work already started. Only proposal, metadata or record changes invoke the preview Step; picker highlighting and calendar navigation do not. Pending/failed verdicts block Save, while controls retain input during a refresh or failed refresh; pending status text stays outside the live region. A persistent announcement changes only when the verdict changes field restrictions, choices, refusals or guidance; it stays unchanged during typing and an equivalent verdict. Refusals include a retry action. Check refusals belong to the check lifetime, independently of save results; only refusals carrying field errors reveal validation problems. Unknown local requirements have the same pending placeholder as other unknown properties. Passwords remain Redacted; only `{ set: true }` enters a form-state proposal for a typed write-only field; the resolver accepts its presence without decoding a substitute credential, since form conditions can test their emptiness only. The real credential is unwrapped only when building the write request.

The public interface was considered in two forms: a callback that lets the record module translate HTTP names, and a canonical proposal passed directly to it. The canonical proposal keeps transport naming at the HTTP edge and needs no new translator seam; the record module owns derivation, masking and permissions.

## Helpdesk v3

**J5 [judgment]: shipped browser behavior.** `v3/forms.yaml` marks description required until its metadata/SQL flags can move together; locks priority, note author, computed dates, imported status history/type and free-text priority/severity labels; requires resolution code and notes in resolved/closed states, hold reason on hold, workaround for a known error in every state, and root cause for fixing/resolved/closed problems. Editable requested/expected resolution dates remain inputs. These are form rules, not API guards; description and note-author server requirements already imposed by decision 0034 remain separate record rules. The compose smoke opens the first incident in the list for both admin and agent and keeps the zero-failed-request assertion. It also opens a colleague's incident as agent and requires read-only values, no Save and no access-error notice; opening a readable record is not an attempted edit. The incident layout includes `internal_cost`, like the ticket layout: decision 0034 J7 preserves the sensitive-field restrictions, with no rule hiding it from administrators. Access rules remove it from agents' metadata and verdicts. The reference check was GB1008 ODA Governance, Security & Privacy Architecture Principles v2.0.0, §6.2.8, pp.35–36 (the document's version heading, despite its local filename); its confidentiality principle supports permission-based disclosure and imposes no separate incident-layout prohibition. No member text is copied here.

**J6 [judgment]: major-incident correction.** The shipped hidden rule carries `clearHidden` and its notices. Form-state checks both existing and proposed field-write permission for the false value and returns whether clearing is allowed, including schema/form read-only restrictions. The generic form applies the clear through its ordinary edit operation, keeps the pending false edit even while hidden, and rechecks the resulting proposal. A caller without permission retains the value and sees the configured notice naming the mismatch filter. Notices derive from the current verdict and pending corrections, disappear when the rule stops applying, and reset after save/reload. The correction never runs in the record service and never modifies an API write.

**J7 [judgment]: problem path and demo.** A shipped choice restriction on the problem status offers New, Assess and Canceled while the previous status is empty or New; its message explains the Assess path. Later stages use their ordinary metadata choices. The broader TMF-permitted API lifecycle is retained. The current fixture, seed command and compose install select v3 together. Seeding v3 uses numeric priorities and common impact/urgency, fills descriptions, supplies resolution details for the resolved demo incident and runs production record-rule hooks. Explicit v1/v2 fixtures still prove historical set and Step 2 browser regressions; the new incident-form browser suite runs the default v3 fixture and covers the current ITIL browser requirements.

**J8 [judgment]: binding edits and configuration.** Choice restrictions and clearing a hidden boolean are small extensions of the form-rule definition, needed to ship the already-required Assess and major-flag behaviors without helpdesk names or choice keys in the generic browser. They use the same inheritance, order, profile, ownership, local overrides and caller masking. The view uses canonical derived values for unedited controls and validation; a proposed-state withheld field is restricted, never empty. A verdict suppresses a hidden/read-only edit once and records the entered value in the existing dropped-edit notice (never a secret); later verdicts do not restore it. An automatic correction only proposes false, and a field whose edit a verdict suppressed cannot be automatically corrected again until save or reload. These causal markers make correction and suppression monotone: between user edits or resets, each field can add a false edit and lose that edit at most once, so self-referencing and mutually dependent visibility rules reach a stable proposal without an arbitrary request limit. Conflicting correction policies stop the automatic correction with a notice. A person may then edit any re-offered control. Schema restrictions are composed once after form assignments and cannot be weakened.

## Round 2 verification scope

The DevTools-restricted-value and restricted-field browser gates run on default v3, explicitly including a successful `checkFormState` answer after editing an owned incident. A v3 stale-check gate retires an edited local field while the form is open, proves input survives the automatic refresh without an automatic save, and then saves the retained edit. Generic admin pages and the child-denial-through-parent case also run on v3.

The v2 copies retain Step 2 behavior that v3 replaces: editable priority and legacy impact choices, history of those choices (`record-forms` and both `shown-values` suites), the original save-time access denial (v3 catches it during form-state), the old list filters/assignee name, and save-time `SchemaChanged` recovery (v3 can detect staleness during a check first). Their assertions remain intact; they are not the shipped privacy gates.

The form-state oracle tests vary a masked value and compare field states, masked values and messages, compare denied-edit error bodies with saves, and prove a derive-added existing-state denial precedes an invalid supplied value. `SaveInput` lives in `save-input.ts`, shared by the save pipeline and proposal rules, without a type import cycle. A required password on a table with form rules proves the presence marker and its emptiness condition without exposing a credential. The pinned password field schema has no length or format settings; this work does not add them. Demo seeding reads the installed helpdesk set version; the seed test independently checks every demo priority against Contracts 14.2's matrix. Migration 0030 has a fixed checksum assertion, and the merged registry is contiguous through 0030. Retired values returned in a verdict are not treated as supplied edits during client validation; the v3 stale-check gate proves the refreshed form can save after its retired edit is dropped. Main's hub and dead-letter definitions and migrations are retained beneath core v5; `git show --remerge-diff` was inspected for the prepared merge and its committed result.

## Round 3 verification scope

A colleague's readable incident returns a successful, masked read-only verdict for an empty proposal, while a non-empty edit remains denied. Story tests prove that the read-only verdict blocks edit and Save Messages without Commands; scene tests prove values, a neutral note and no editable controls or Save. The default-v3 browser case opens the seeded colleague's incident and checks the verdict, rendering and absence of failed responses and browser errors. The compose smoke retains its original first-row scope and adds the explicit colleague case. Invalid form-state envelopes report key paths only, with no submitted values in their error text.
