# 0010 Foldkit tooling: vendored source, agent skills, lint

Status: accepted, 2026-10-21. Workstream 0A (web toolchain), branch `ws/0a-foldkit-tooling`. Follows the choice of Foldkit and Foldkit UI for `apps/web` (AGENTS.md, "Frontend: Foldkit").

## Decisions

- **Vendored upstream source lives in `repos/`.** `repos/foldkit` is Foldkit's repository at `foldkit@0.169.0` (commit `7ee2142`, tree `f9dd0aa`), at the path Foldkit's skills and `FOLDKIT.md` expect. `repos/effect` is Effect's at `effect@4.0.5`, moved from `vendor/effect` with the same tree hash (`208c4ac`). Both are read-only references, never imported.
- **One vendoring tool.** `tooling/vendor.ts effect|foldkit <version>` replaces `tooling/vendor-effect.ts`. It still clones the tag at depth 1 into a temporary directory and fetches only a parentless commit holding the tag's tree, so neither upstream history nor a shallow boundary reaches the shared `.git`. The history it now writes is what `git subtree add --squash` writes: a parentless squash commit of the tag's tree, signed off, with the `git-subtree-dir` and `git-subtree-split: <upstream commit>` trailers, merged into the branch with `git merge -s ours` and `git read-tree --prefix -u`. The earlier Effect layout put the trailers on an ordinary commit, which `git subtree pull` would take as the squash base and mis-merge. With the new layout, `git subtree pull --prefix=repos/foldkit https://github.com/foldkit/foldkit.git foldkit@<version> --squash`, the upgrade Foldkit documents, works. This was tested in a scratch clone: re-pinning to `foldkit@0.168.0` merged cleanly and touched nothing outside `repos/foldkit`. The script is still preferred, because it also rewrites the version record and fetches no upstream history.
- **`check-vendor` covers both trees.** For each tree it checks the record (`repos/<package>-version.json`: repository, tag, commit, tree), the committed tree hash, uncommitted changes, the subtree trailers and the vendored `package.json`. The lockfile must resolve `effect` to the vendored tag. `foldkit` is checked once the web workstream installs it: from then on the lockfile must resolve exactly one `foldkit`, at the vendored tag, so an upgrade cannot leave the subtree behind.
- **`FOLDKIT.md` is Foldkit's, verbatim.** The root `FOLDKIT.md` is `repos/foldkit/packages/create-foldkit-app/templates/base/FOLDKIT.md`, byte for byte. It sits at the root because its `./repos/foldkit` paths resolve from there. Oxfmt and the pre-commit hook skip it, and `check-vendor` fails on any difference and names the copy command. AGENTS.md carries `subtree_prompted: true`, which `FOLDKIT.md` reads, because the subtree is already vendored. STD's own Foldkit rules go in AGENTS.md, and win where the two differ.
- **Skills come from the subtree.** `.agents/skills/{foldkit,generate-program,audit-program}` link to `../../repos/foldkit/skills/<name>`, which Codex reads. `.claude/skills/<name>` link to `../../.agents/skills/<name>`, which Claude Code reads, as for the Effect skills. A re-pin therefore updates the skills too. `skills-lock.json` stays the `skills` CLI's lock for the Effect skills only.
- **`.ignore` lists `repos/`**, as Foldkit's template does, so editors and root-level ripgrep searches skip the vendored trees. Ripgrep still searches a path given explicitly. With the `.ignore` in place, `rg -n "export function defineMessageUnion" repos/foldkit/packages/foldkit/src` prints `repos/foldkit/packages/foldkit/src/schema/index.ts:534:export function defineMessageUnion<`. The same search from the root (`rg -l "export function defineMessageUnion" -g '!docs' .`) prints nothing and exits 1.
- **Nothing else reads `repos/`.** The upstream repositories bring their own `package.json`, pnpm workspace, tsconfigs, Oxlint and Oxfmt configs and agent files. None of them is picked up. `.eslintignore` stops Oxlint, and `.prettierignore` stops Oxfmt, from descending into `repos/`. Without the latter, Oxfmt took `repos/foldkit/.oxfmtrc.jsonc` as a nested config and checked 2,600 Foldkit files under Foldkit's own settings, despite the `ignorePatterns`. Oxlint and Oxfmt `ignorePatterns`, the lefthook exclude and `.gitattributes` (`linguist-vendored`) cover `repos/` too. The pnpm workspace, Vitest project and tsconfig globs never match it.

## Lint scoping

`@foldkit/oxlint-plugin` is pinned to 0.15.3 (the newest release, old enough for pnpm's minimum release age). Its `effect-oxlint` dependency peers `effect ^4.0.0` and resolves to STD's single 4.0.5. `oxlint.config.ts` reads the plugin's `all.json` preset (decoded with Schema, so a change in its shape fails loudly) and does not copy the rule list:

- The plugin is loaded once, in the top-level `jsPlugins`. Rules from a JS plugin are off unless configured, so loading it globally enables nothing.
- One override turns on every preset rule for `apps/web/**`. The preset's own overrides follow it: server entry and `server/` files (`no-nonportable-server-globals` on, `no-impure-call-at-decision-time` off), client and server entry points, and test files. Each of them is re-rooted from `**/` to `apps/web/**/`, so `**/server/**` cannot reach `packages/server`. A preset glob without the `**/` prefix makes the config throw.
- Rules such as `no-module-level-mutable-state` and `no-impure-call-at-decision-time` describe a Foldkit program, not the server or plain packages, so they never run there.
- The plugin needs no type information, so no `oxlint-tsgolint` or `@effect/tsgo` setting changed. Foldkit's scaffold also runs a separate `effect-tsgo patch --oxlint` pass (`.oxlintrc.effect.json`); STD gets the same Effect diagnostics from the patched `tsc`.
- The `foldkit-oxlint-scope` canary (`tooling/test/foldkit-lint.test.ts`, fixture `tooling/canaries/foldkit-lint/counter.ts`) lints one file in a temporary tree whose `oxlint.config.ts` re-exports the root config. At `apps/web/src/` it gets exactly `foldkit/no-module-level-mutable-state` and `foldkit/no-switch-on-message-tag`. At `apps/web/src/*.test.ts` it gets only the second, per the preset's test override. At `packages/server/src/` it gets no Foldkit rule and passes.
- `pnpm check` also runs `tooling/check-foldkit-lint.ts`, which does the same probe with the root config (`tooling/lib/foldkit-lint.ts`). The lint step fails when the plugin is not loaded or its rules stop matching `apps/web`, instead of passing with the rules silently off. The canary checks that the guard fails with a config that does not load the plugin (`tooling/canaries/foldkit-lint/without-foldkit.ts`).
- Both read Oxlint through `--format json`, and run it in a controlled environment. Without `--format`, Oxlint picks its output format from the environment. It uses the one-line `agent` format (`file:line:col: error foldkit(rule): ...`) when it detects an AI agent, GitHub's annotations (`::error file=...,title=foldkit(rule)::...`) under `GITHUB_ACTIONS`, and the graphical format in a terminal. Oxlint 1.88.0 detects an agent from `AI_AGENT`, `CLAUDECODE`, `CLAUDE_CODE`, `REPL_ID`, `GEMINI_CLI`, `CODEX_SANDBOX`, `CODEX_THREAD_ID`, `COPILOT_CLI`, `OPENCODE`, `JUNIE_DATA`, `JUNIE_SHIM_PATH`, `CURSOR_AGENT`, a `.pi/agent` entry in `PATH`, `EDITOR` containing `devin` and `TERM_PROGRAM` containing `kiro` (`apps/oxlint/src/agent_detection.rs`). The first canary parsed lines that start with the file path, so it passed under Claude Code and found no rules on GitHub Actions (run 39758862316), although the plugin was loaded there too.
- The controlled environment (`lintEnvironment`) is an allow-list rather than a list of markers to remove, which would miss the next agent Oxlint learns to detect. It passes `HOME`, `LANG`, `LC_ALL`, `PATH` (without `.pi/agent` entries) and `TMPDIR`, and sets `CI` and `GITHUB_ACTIONS`. Oxlint runs with the calling process's Node. The canary sets every marker above and checks three things: the probe's result does not change, none of the markers reach Oxlint (its default output stays GitHub's format), and the markers do switch Oxlint to the agent format when they get through.

## Version gap

`foldkit` 0.169.0 and `@foldkit/ui` 0.169.0 peer exactly `effect@4.0.0` (and `@effect/platform-browser@4.0.0`). STD keeps one `effect` at 4.0.5 (`check-lockfile`, `duplicatePackage`; the decision to stay on 4.0.5 is in AGENTS.md, "Effect version"). This workstream installs neither package, so the gap is not bridged here. Only the lint plugin is installed, and it accepts any `effect ^4.0.0`. The vendored Foldkit tree carries its own Effect 4.0.0 at `repos/foldkit/repos/effect`. Agents use `repos/effect` (4.0.5) instead, which AGENTS.md says.

## For the web workstream

- Install `foldkit`, `@foldkit/ui`, `@foldkit/vite-plugin`, `@foldkit/devtools` and `@foldkit/devtools-mcp` at the vendored version, with the 4.0.5 peer bridging AGENTS.md describes. This workstream installs neither DevTools package and adds no `.mcp.json`: both need `foldkit` installed and the bridged peer.
- Add `apps/web/AGENTS.md`, pointing to the root `FOLDKIT.md` and the root `AGENTS.md`, so agents that start in `apps/web` find both.
- Add the template's `.mcp.json` `foldkit-devtools` entry (`repos/foldkit/packages/create-foldkit-app/templates/base/.mcp.json`), adapted to run through pnpm (the package's `foldkit-devtools-mcp` bin through `pnpm exec`, not `npx`), so the pinned Node and the locked version are used. Add the same server to the Codex MCP config.
- On every Foldkit upgrade, in the same PR: `pnpm exec node tooling/vendor.ts foldkit <version>` and `git commit -s`, then `cp repos/foldkit/packages/create-foldkit-app/templates/base/FOLDKIT.md FOLDKIT.md`, then the matching `@foldkit/oxlint-plugin`. `check-vendor` fails until all three agree with the lockfile.

## Residual risks

- `repos/foldkit` contains Foldkit's contributor instructions (`AGENTS.md`, `CLAUDE.md`, `.claude/skills/{commit,make-pr,...}`, `.agents/`). Claude Code may load a nested `CLAUDE.md` or skill directory when an agent reads files there. AGENTS.md says they do not apply to STD. The project owner can also exclude the nested file with Claude Code's `claudeMdExcludes` setting.
- As for Effect, `check-vendor` trusts the record. Review any diff to `repos/*-version.json`.
- The vendored trees add about 130 MB to a checkout (`repos/effect` 55 MB and `repos/foldkit` 74 MB on disk; the latter includes Foldkit's own Effect copy).
