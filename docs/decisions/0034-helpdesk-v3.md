# 0034. Helpdesk v3: incident and problem management

Status: implemented for 3I-A, 2026-10-23. Contracts 4.9–4.10, 8.2–8.5, 8.8, 11.2 and 14. Builds on decisions 0019, 0021 (34–55), 0022, 0024, 0029 and 0030.

`examples/helpdesk/v3` is the shipped app set, installed with `pnpm std upgrade --set examples/helpdesk/v3`. Version 3 keeps the set ID, ticket/incident class IDs, existing field IDs, choices, layout IDs, access-rule IDs and saved-filter IDs. The set contains no executable business callback. Its behavior is `recordRules:` configuration, so administrators can deactivate shipped rules and add local rules. It contains no licensed TM Forum or ITIL text. ITIL® is a registered trademark of the PeopleCert group.

## Shared model and rules

Ticket holds the common description, status, numeric priority, impact, urgency, hold reason, resolution fields, caller and assignee references, channel and the writable TMF-facing fields. Incident adds the major flag, parent incident and problem references. Problem adds known-error, workaround and root-cause fields. `ticket_note.ticket` and `ticket_party.ticket` are aggregate owner references: required, immutable after create, and every part change advances the owner's version. `ticket_specification` is the minimal specification model for 3I-B.

Nine incident derive rules implement the matrix in Contracts 14.2. Each checks its cell and `changed(impact) or changed(urgency)`, and sets priority with `keepSupplied`. Explicit priority therefore wins even when equal to the previous value. The label-clear derives run later and keep explicitly supplied labels. There are six incident and eight problem transition guards, one per source state, on updates. Each refuses exactly the disallowed transitions. Creates can name any valid state, as TMF621 permits; unchanged states are accepted. No API guard requires resolution details, a workaround, a root cause, priority 1 for a major incident, or a browser-only lock.

Hold-reason derives supply `awaiting_vendor` on entry without a reason and clear it on exit. Resolution entry supplies the timestamp unless named in the write; reopening clears it and closing retains it. Ticket status changes set the status-change date. After-rules resolve a major incident's open children with its resolution and return precisely a resolved problem's incidents waiting for that problem to work. They run as the passwordless `std-helpdesk-cascade` service identity (UUID `32187bcc-314f-53f1-9a54-4ae3cabd1598`), reserved by the platform and ensured through the system-user save pipeline on every v3 set load, including unchanged reloads. Its `helpdesk_cascade` role grants incident read/update and only the status, hold reason, resolution and status-date fields needed by these cascades; parent/problem references are readable. It cannot create or delete records, write assignments, or set the major flag. Its reserved ID cannot sign in or authenticate a cookie or bearer session, even after database-owner corruption. Ordinary record clients cannot change its password or activity, delete it, change its role assignments, or grant its role to anyone else. System provisioning repairs these properties with audited saves; doctor reports missing/inactive identities, passwords, wrong assignments and other holders of the reserved role. Failed nested saves still roll back the operation. Decision 0022 trusts set-owned rules as configuration: `checkRunAsAuthor` exempts their author check, while local replacements need `rules.run_as` and the runtime author check. No human is granted `rules.run_as` by this set.

## Judgments and implementation choices

- **J1 [judgment]: preserving impact's identity.** A field cannot move to another declaring class. The old incident impact keeps its ID and storage as read-only `legacy_impact`; the common ticket impact is new. This preserves old history and local layout references while making severity available on tickets and problems. No old field is purged. The new incident layout uses the common impact, while an overridden layout remains untouched.
- **J2 [judgment]: numeric choice keys.** New keys `1`–`5` are added to the existing priority field; old keys remain hidden, with their IDs, labels and overrides. Choice keys cannot be renamed. New impact and urgency use string keys `1`–`3`, defaults `3`, required. The migration explicitly preserves old priority, rather than recomputing it from a newly defaulted urgency.
- **J3 [judgment]: assignee.** The v2 `assignee` returns to the contract's `assigned_to` name by its existing field ID. History, filters and local layouts retain the same references. The generic API exposes `assignedTo`.
- **J4 [judgment]: description during upgrade.** The nullable description column remains nullable until a contract-phase constraint migration (Contracts 8.8 RU4). An invariant makes description mandatory on every ordinary create/update, including settled saves; 0018 fills historical gaps without running current rules. There is no description-from-title default. **Follow-up:** metadata's `required` flag and SQL NOT NULL must be switched together after backfill: the current schema planner cannot mark a field required without issuing NOT NULL. This is an explicit remaining schema/metadata gap, not a claim that metadata already says required.
- **J5 [judgment]: bounded text copying.** Contracts 11.2's `name` mapping explicitly requires the first description line truncated to 160 code points, and Contracts 14.4's shipped `ticket` derives require that mapping as configuration. Literal/context/copy/increment actions cannot express it. To implement that existing requirement, add the optional `firstLine` code-point limit to a copy value, within the existing `set` action kind. Only text/longText source and target fields allow it; IDs and other kinds are refused. Positive limits are schema-validated. The existing identifier grammar requires underscore rule names, so contract descriptions such as `clear-priority-label` are shipped as `clear_priority_label`. CR, LF, U+2028 and U+2029 delimit the first line; Unicode code points, not UTF-16 units, count toward the limit. Title uses 160. Existing copies are unchanged and dependency extraction still records the source field. The generated optional `firstLine` properties are documented by the shared `/api/v1` schema. Decision 0025's API consolidation removes the old frozen document and its hash test.
- **J6 [judgment]: resolution choices.** `solved_permanently`, `solved_with_workaround`, `not_solved`, `duplicate`, `not_reproducible` are STD labels, not ITIL-defined codes. Channel defaults are not assumed. Severity, priority and ticket-type labels use long text rather than an arbitrary 160-character cap, since the TMF attributes are free text. The specification resource uses `specification_version`, since `version` is a reserved platform field name; 3I-B maps it to the external attribute.
- **J7 [judgment]: access.** The major manager role gets the existing agent ticket permissions plus write access to the major flag. Agents may read that flag but receive no write grant. Use separate grants, not a deny on the agent role, so a user holding both roles can write. The existing assignment and sensitive-field restrictions remain. **Documented restriction (Contracts 14.2):** managers can set the major flag only on incidents assigned to themselves or nobody. Field-level grants cannot bypass the required record-level update permission without also authorizing other ticket-field writes; expanding that model is an open access-engine item. Ticket parts are readable and writable by agents/managers. **Open security/access item (Contracts 3, 4.9 and 14):** record access predicates cannot follow an owner reference, so agents can still change/delete notes and party links on colleagues' tickets, advancing the owner version and producing events. Implement owner-authorized part writes before claiming parity with ticket assignment restrictions. Note authors are now derived from the acting user on create and immutable on update. Because derives count as the acting user's writes and cannot set schema-read-only fields (4.10), immutability is a shipped invariant; the field metadata read-only flag is a separate follow-up requiring a supported service-assigned field mechanism. Agents can read party/user display names for references, and specifications, without gaining party writes or sensitive user fields.
- **J8 [judgment]: current demo.** This part ships v3 as an explicit install. The default v2 browser/demo fixture and compose choice stay at v2 until 3C adapts its forms and seed expectations. No `apps/web` code changes here.
- **J9 [judgment]: optional-app data migration.** Migration 0018 declares `requiredSet: { name: "helpdesk", minVersion: 3 }`. Before that version is installed it has no ledger entry and is not pending for startup/doctor; the upgrade plan includes it when v3 is requested. The post-set runner then inserts `running`, commits batches and ends at `applied` exactly once. Checks still validate every recorded row even when its prerequisite is absent. There is no applied-to-running transition and no recheck state. This narrow applicability rule is specified in Contracts 1.9. In particular, clearing a v3 status date cannot re-arm migration 18 or overwrite impact.
- **J10 [judgment]: missing historic dates.** Old resolved/closed tickets use their pre-migration `updated_at` as `resolved_at`. All old tickets use it for missing `status_changed_at`. These are deterministic approximations; original history remains the evidence for exact past transitions. A supplied existing resolution timestamp or hold reason is kept.
- **J11 [judgment]: narrow framework corrections.** Aggregate reference types must compare canonically rather than by JSON property insertion order, or an unchanged set reload is refused. The fix still rejects changing aggregate ownership. Generic API metadata renders saved-filter text with API attribute names using the same snapshot and actor that produced the metadata. Translation lives in `records/saved-filter-names.ts`. If an already-visible filter cannot decode or print, the request fails as a defect (500); filters are never silently dropped by translation. Existing caller-visibility filtering still applies before translation.

- **J12 [judgment, revised in round 6]: local rules retain human authority through cascades.** Run-as switches carry the chain's `origin` through every nested save: the first non-reserved actor of the chain (a session user, or an ordinary subscription identity for a chain that starts in an after-commit delivery), kept from the first link even when a later link switches to another `runAs`. A local `after` rule without `runAs` under a reserved service identity reloads that actor's current roles and writes with their `actor_id` and the normal hook cause, so it never gains rights the origin actor lacks. It never inherits the cascade role. Without an origin (a chain with no non-reserved actor), execution remains `NotAllowed` and logs the rule ID. This replaces the blanket refusal: an ordinary local incident rule must not break both shipped cascades or otherwise writable TMF status changes merely because the set uses its reserved identity. Human access failures still roll back the entire operation. Explicit local `runAs` behavior is unchanged. Local subscriptions naming reserved identities fail attempts with a clear `DeliveryFailed` reason and the normal backoff/dead-letter policy, before their effect runs.

Legacy local rules and subscriptions may already name the system user. Whole-snapshot validation compares the old and new run identities: only creation or an identity change to a reserved user is refused. Unrelated edits and v3 set loads remain possible; doctor lists existing offending definitions and their remedy. Runtime refusal remains unconditional.

## Offline upgrade and rolling separation

Round 4 reserves the cascade login (case-insensitively) and UUID before v3 is installed. Record clients cannot create that UUID, take the login, or change the service user's login or name; bootstrap refuses the login too. Only the set loader supplies the explicit `ServiceIdentityProvisioning` service that bypasses these record protections. A system actor alone has no bypass. Local rules and subscriptions cannot select any `SERVICE_USER_IDS` identity, even with `rules.run_as`; the runtime author check also refuses them. Set-owned cascade rules retain their reserved identity. [judgment]

Provisioning and doctor share the active-role condition. For a retired cascade role, doctor explains that it was changed outside STD and directs the operator to restore from backup or follow the reserved-role SQL recovery in the upgrade runbook before reloading v3; provisioning leaves its identity alone until then. A pre-existing human login collision fails with typed `SetIdentityFailed`, including the conflicting user's ID and the remedy: rename that user's login, then reload. Doctor reports the same collision, including before v3 is installed. Reload repairs changed service login/name through audited saves; an unchanged reload adds no changes for the user, individual or role assignment. No additional platform migration is needed.

The machine-readable partition is `examples/helpdesk/upgrade-v3.json`. New class identities, ordinary field types and choice entries are additive definitions. Required/default/read-only properties of new fields are listed separately for finalize, as are the new aggregate owner-reference fields (RU11). Changes to existing defaults, read-only settings, names, layouts, hidden choices, record rules and access rules are behavior. The partition describes a future phase-aware loader; Step 3's loader still applies one set in its existing order.

RU7: apply additive schema during expand only when the old release can read the new definition shapes; activate record rules, access changes, changed defaults and hidden choices only at finalize. RU11: `recordRule`, aggregate ownership and the new copy `firstLine` setting are new features. A mixed release must not create/use them until every admitted process understands them. Step 5 must register their introduction versions and enforce admission. This work does not claim to implement those fences.

The actual v2 → v3 upgrade is offline: stop servers/workers; run the set upgrade and data migration; restart only when the ledger is complete. Migration 0018 is **contract** phase because rewriting old priority keys is not compatible with old app behavior. The physical storage renames (`assignee` → `assigned_to` and incident `impact` → `legacy_impact`) also rely on this offline boundary and cannot run while v2 processes are admitted. Migration 0018 itself performs no DDL. Schema additions belong to set loading, not a destructive platform migration.

## Deterministic v2 → v3 mapping

| v2 | v3 |
| --- | --- |
| incident/ticket IDs, numbers, class, state, resolution notes, assignment and business fields | preserved |
| priority critical/high/moderate/low | `1`/`2`/`3`/`4` |
| incident impact high/medium/low or empty | common impact `1`/`2`/`3`/`3`; original retained as legacy impact |
| plain ticket without impact | common impact `3` |
| no urgency | `3` from the new required field's default |
| on_hold without reason | awaiting_caller, reflecting the v2 waiting-on-caller state |
| absent description | old short description |
| absent status-change timestamp | pre-migration updated_at |
| resolved/closed without resolution timestamp | pre-migration updated_at |
| choice/layout overrides | kept by stable ID under Contracts 8.4; the Step 2 converged override remains converged |

Batches select missing descriptions/status dates, old priority keys or a non-null legacy impact whose value has not yet been copied, in record-ID order. Every update goes through the system user's record save pipeline with history and outbox hooks, without applying newly shipped business rules to historical records. Cursor and saves commit together. `remaining` uses the same predicate and must be zero before the ledger becomes applied. An injected failure after one committed batch proves resumability and the no-duplicate rerun. A real-process kill of the shared runner remains covered by `data-migration-interrupted`.

## Handoffs

Browser-lock the TMF-writable timestamp/history/type fields as appropriate. Update the default fixture, seed and compose install to v3 together with the browser tests. Do not implement these as API guards.

**3I-B TODOs:** Map TMF621 `note.author` so an unchanged array resubmitted with its rendered authors does not attempt a forbidden author edit. Historical notes imported in user mode receive the importer as author: this is acceptable only when that attribution is intended; preserving historical attribution needs an explicit, audited system-import path before such imports are supported. The 1,000-incident migration proof checks every incident in the record store and preserves its history; the acceptance clause "every incident readable through TMF621" remains 3I-B's responsibility. Plain `helpdesk.ticket` records currently have no transition model: they still accept `awaiting_approval` and problem states, and a request ticket can go `closed` → `new`. `awaiting_approval` has no TMF621 status mapping. Decide and implement the mapping/validation before exposing those records in TMF621. TMF621 adapter and CTK; severity/priority free-text mapping; ticketType class-preserving writes; status groups and all patchable attributes; exact RFC 7396 arrays for notes/parties inside `aggregateOperation`, prelocking multi-aggregate writes and projecting after finalization; supplied-priority provenance for every JSON Patch operation; mandatory create validation/output; specification version mapping; characteristic/event rendering; generic/TMF races and cross-surface proofs. ## Verification

The conformance file marks only rows proved here; browser/TMF-specific and compound cross-surface rows stay pending.

## Round 2 evidence and remaining work

The upgrade test seeds exactly 1,000 incidents, each with history, alongside the existing plain ticket. It preserves the old records and history and checks migration outcomes. The partition test derives new IDs from v2/v3 set files and compares them exactly with `upgrade-v3.json`, including duplicate detection. The incident and problem tests exercise cascades as a manager and an agent with targets assigned to other agents. Explicit resolution dates survive reopening. Settled-save guard evidence and local rule replacement have their own conformance references.

The owner-access gap, the manager assignment restriction, and the schema/metadata flags for required description and immutable note author above remain explicit follow-ups. No browser or TMF621 completion is claimed here.

At runtime such a rule gets no delivery and never runs (`after-commit-rules.ts`, `carries`). The finding errs on the safe side. It should be a warning when the carrier does not take deliveries.
- No test proves that doctor omits purged definitions from the `localServiceIdentity` findings.
- No test covers a chain where a human's local rule with `runAs` leads into a set cascade. The implicit local rule inside that cascade runs as the chain's origin (the human), not as the `runAs` identity. This gives no new rights, but it is not tested.
