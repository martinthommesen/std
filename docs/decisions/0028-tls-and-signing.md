## Postgres transport

`packages/postgres/src/transport.ts` (`@std/postgres/transport`) is the shared transport policy. This Effect-only package is available to server, tooling, benchmarks and values tests without importing the server into a plain package's tests. `DatabaseConfig.fromEnv` reads Effect `Config` and certificate/key files once when its layer is acquired, stores resolved pooled/direct transports on `DatabaseSettings`, and warns once per acquisition if either endpoint allows remote plaintext. All connection builders consume those retained transports. `fromUrl` accepts explicit TLS inputs (PEM contents), never ambient configuration. The URL uses `Config.Redacted`; paths use `Config.String`. Private key PEM stays `Redacted` in TLS settings and retained transports and is unwrapped only when building driver options. Neither URLs nor certificate/key contents are included in TLS diagnostics.

| Setting | Meaning |
| --- | --- |
| `STD_DATABASE_SSL_MODE` | `disable`, `require`, `verify-ca`, `verify-full` |
| `STD_DATABASE_SSL_CA_FILE` | PEM trust anchors; mandatory for `verify-ca`; empty contents are refused |
| `STD_DATABASE_SSL_SYSTEM_ROOTS` | Explicit boolean opt-in to Node's public roots for `verify-full` when no CA file is supplied |
| `STD_DATABASE_SSL_CERT_FILE` | Optional PEM client certificate/chain |
| `STD_DATABASE_SSL_KEY_FILE` | Optional PEM private key; required together with the client certificate |
| `STD_DATABASE_DANGEROUSLY_ALLOW_INSECURE_REMOTE` | Explicit boolean override permitting `disable` on a remote host, with a warning |

[judgment] Use one policy for pooled, reserved LISTEN, dedicated coordinator, CLI, test admin/session and values codec connections, benchmarks and the tooling wire client. This closes the less obvious paths used by `upgrade`, `doctor`, `bootstrap-admin`, cancellation and the database test harness. Explicit URLs resolve the same policy with explicit TLS settings; host/SSL URL query options are retained by the benchmark layer.

[judgment] Default to `disable` only for literal `localhost`, IPv4 127/8, IPv6 `::1`, or a Unix socket directory; default to `verify-full` otherwise. Unix sockets always use `ssl: false`, including under a global verify mode, as libpq does. Do not infer locality from DNS resolution: a remote hostname resolving to a local address must still authenticate its certificate. Resolve libpq `host` and `port` query overrides consistently with the driver. IPv4-mapped IPv6 and other names are conservatively treated as remote.

[judgment] An explicit STD mode wins over URL `sslmode`; otherwise the URL may choose one of the same four modes before the host default is applied. Reject URL certificate parameters and the ambiguous `ssl` parameter, directing users to the STD settings. Do not support `prefer` or `allow`: mandatory explicit `ssl` options prevent opportunistic plaintext fallback in the driver.

[judgment] Plain `require` without a CA encrypts without authenticating the server and can be intercepted by anyone on the path. With a configured CA, `require` verifies the chain like libpq's `verify-ca`, without hostname checks. `verify-ca` requires an explicit nonempty CA file: public roots plus no hostname check would trust an attacker's unrelated publicly issued certificate. `verify-full` checks both the chain and the effective hostname or IP SAN, requiring either a CA file or explicit `STD_DATABASE_SSL_SYSTEM_ROOTS=true`. This gives the requested mode semantics instead of the driver's single boolean SSL setting. Set the minimum protocol to TLS 1.2 and allow TLS 1.3 negotiation. Prefer `verify-full` for production; `require` is a deliberate weaker compatibility choice.

[judgment] Reject disabled remote TLS before any connection or password exchange, even for a direct URL when the pooled URL is local. The deliberately named escape hatch logs a warning about exposed credentials and data. Validate both endpoints in `DatabaseConfig.fromEnv`; keep `DatabaseTlsError` in the configuration layer’s typed error channel so the CLI reports expected startup failures without converting them to defects or retryable SQL errors. Typed `DatabaseTlsError` diagnostics do not retain raw filesystem/URL exceptions, which can include credentials or paths.

[judgment] `doctor` reports the actual diagnostic backend's `pg_stat_ssl` protocol/cipher as informational check 17 (proposed Contracts 1.10; check 15 remains encoding/client_connection_check_interval). Local plaintext remains compatible with the existing clean exit code; the startup policy rejects remote plaintext unless the operator has explicitly overridden it. This finding describes the observed connection, not a claim that Postgres can report client-side CA policy.

The optional statement-log wire tap already stops at SSLRequest. It cannot observe encrypted statements; production has no tap. TLS harness connections remain encrypted even when tests install a StatementLog. Wire-log assertion suites run on the existing local development database; the TLS suite asserts connection state directly. The tap now also respects Unix sockets and libpq host/port overrides instead of silently dialing the URL authority.

A `development` profile excludes it from plain `docker compose up`; explicitly targeting `postgres` through `pnpm db:up` activates that service. `pnpm db:up` selects only that service. It will not recreate the existing shared container after this merge, because the profile does not change its Compose service hash. No command was run against the `std` Compose project; read-only config and dry-run checks used a separate project name.

[judgment] Give the quickstart its own `quickstart-postgres` service and `std-quickstart-pg` data volume, with no published database port. Its wrapper generates a throwaway CA and leaf certificate, including SANs `quickstart-postgres`, `postgres`, `localhost`, `127.0.0.1`, `::1`. Private material stays in that volume (directory 0700, key 0600), and the CA private key is deleted after issuance. Only `ca.crt` is copied into a public volume mounted read-only by upgrade and server. Both application containers use `verify-full`. The separate volume starts a fresh quickstart database; it does not migrate data previously put in the shared development volume.

[judgment] The leaf lasts one year and CA ten years. On every start the wrapper runs `openssl x509 -checkend 2592000` on both certificates. Missing files or fewer than 30 days remaining regenerate the whole demo identity; the public CA is re-copied each start. Restart the application containers after renewal to load the new trust anchor. Plaintext loopback development remains unchanged. This demo bootstrap is not a production PKI; production mounts operator-managed trust material.

`examples/quickstart.sh` has no changed arguments, credentials interface or wire requests. For an external `STD_COMPOSE_DATABASE_URL`, the quickstart entrypoint does not apply the bundled CA or mode. Pass `STD_DATABASE_SSL_MODE`, `STD_DATABASE_SSL_CA_FILE`, `STD_DATABASE_SSL_SYSTEM_ROOTS` and optional client file settings explicitly; mount the selected files with a compose override. Absent settings preserve URL mode and host defaults. README and architecture list the settings.

## Release signing

`.github/workflows/release.yml` automatically runs only for `v*` tag pushes. A manual invocation defaults to `dry_run=true`; a publishing manual invocation must reference a version tag. Separate jobs enforce this boundary before permissions are granted. It builds the server image, pushes `ghcr.io/martinthommesen/std:<tag>`, signs the immutable digest with cosign keyless signing, and attaches an SPDX SBOM and SLSA build provenance. Both GitHub attestations and cosign's SBOM attestation bind to that same digest.

[judgment] Use GitHub OIDC (`id-token: write`), short-lived Sigstore certificates and transparency log inclusion instead of a stored signing key. The tag-only publishing job permissions are only `contents: read`, `packages: write`, `attestations: write`, and `id-token: write`. Disable optional artifact storage records so no `artifact-metadata: write` permission is needed. The verifier pins the exact repository workflow and release tag, not just an issuer or repository owner.

[judgment] A dry run exports an OCI archive, signs the archive and SBOM as blobs, without logging into GHCR, running GitHub attestation actions, or pushing an image, chart or registry attestation. Its job grants only `contents: read` and `id-token: write`, with no package or attestation write permission. It still contacts OIDC, Fulcio, Rekor and the GitHub artifacts API: this tests the real signing path and saves verification bundles for inspection.

[judgment] Reuse the working quickstart Dockerfile for the Step 3 server artifact. The smaller production image, broader architectures and deployment hardening remain Step 5 packaging work. Do not delay signing until that packaging exists. The Dockerfile's pinned Node/pnpm, lockfile integrity and unprivileged runtime are preserved. Release-only build/sign tools are downloaded at exact versions and checked against fixed publisher SHA-256 hashes in `docker/release-tools.sh`: cosign 2.6.1, Syft 1.33.0, Helm 3.19.0, Buildx 0.31.1. BuildKit 0.26.3 is pinned by OCI index digest. Actions use full commit SHAs with release version comments. Runner-provided shell, curl, checksum utilities and Docker daemon are supplied by GitHub's `ubuntu-24.04` runner rather than downloaded by this workflow.

[judgment] The marked Step 5 hook checks `deploy/oda/std/Chart.yaml`. Until it exists the chart step is skipped. When present it builds chart dependencies, lints, packages, signs the exact `.tgz` with a Sigstore bundle, and pushes only in publishing mode. This uses keyless signatures rather than Helm's OpenPGP `.prov` format, avoiding a new long-lived secret. Signed bundles are retained with workflow artifacts for 30 days; the image signatures, SBOM and provenance also reside in GHCR. Step 5 must define durable chart/bundle distribution.

[judgment] Configure a repository tag ruleset for `v*` restricting who may create, update or delete release tags, with tightly controlled bypass actors. Verifier tag pinning authenticates the workflow ref; the ruleset governs who can establish that ref.

## Evidence and limits

`pnpm test:tls` creates one uniquely named Postgres 18 container, uses a random loopback port and temporary certificates, waits for the final TCP server (not initdb's temporary Unix-socket server), and removes that container and its fixture on exit. It never invokes compose or touches other containers. The same command runs in CI. TLS tests prove CA and hostname failures, encrypted `require`, pool/LISTEN/dedicated/doctor connections and configured test harness connections. Unit tests prove defaults, remote startup refusal with the specific error, direct endpoint checks, env-vs-URL precedence, forbidden URL parameters, require/verify-ca option shapes, socket overrides, bracketed IPv6 remote hosts, explicit root trust and the dangerous override. The TLS fixture also proves optional client certificates, runs the tooling Postgres check and the values codec suite against the configured TLS URL, and checks compose certificate generation, renewal near both expiry dates and key modes. The same isolated server is then switched to `ssl=off`: mandatory TLS must fail while a plaintext control succeeds, proving no fallback.

Release tool downloads are independently exercised with a temporary Docker config. No image or tag is pushed in this workstream. Actual OIDC issuance, GitHub attestations and registry publication require a GitHub workflow run; they cannot be exercised as a local signed release.

## Proposed contract text for the coordinating writer

[judgment] Add to the transport/security contract: every STD Postgres connection uses the shared TLS policy. Remote endpoints default to `verify-full` and reject plaintext unless `STD_DATABASE_DANGEROUSLY_ALLOW_INSECURE_REMOTE=true` is explicitly set and warned about. Loopback/socket development may use plaintext. Plain `require` without a CA is vulnerable to on-path interception and never falls back; with a CA it verifies the chain. `verify-ca` requires explicit CA trust and authenticates the CA and `verify-full` also authenticates the target name and requires an explicit CA or opt-in to system roots. Add to Contracts 1.10: `17. Observed Postgres connection TLS protocol and cipher from pg_stat_ssl, or plaintext (informational: databaseTls); startup enforces the transport policy. Informational findings do not change the exit code.` Check 15 is unchanged. `doctor` reports observed encryption.

[judgment] Add to the release contract: Step 3 release images are signed by GitHub OIDC through Sigstore at their immutable digest and carry signed SBOM and build provenance attestations. Verification checks issuer, workflow identity, tag and digest. The Step 5 chart is packaged and signed through the same release workflow once it exists. This makes GB1008's in-transit and signed-deliverable requirements independently testable gates.
