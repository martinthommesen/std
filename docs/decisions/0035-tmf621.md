# 0035. TMF621 Trouble Ticket over the ITIL helpdesk

Status: implemented for 3I-B, 2026-10-23 (plan Step 3 row 3I). Contracts 11.1, 11.2, 11.6, 12, 14 and 15. Builds on decisions 0021 (decisions 34 to 56), 0025, 0026, 0029, 0032 (events and hubs), 0033 (the TMF framework) and 0034 (helpdesk v3).

Guarantee (plan, row 3I): ITIL behaviors hold the same through the generic API, TMF621 and the browser; TMF621 passes TM Forum's CTK at the pinned version under the runner's criteria, and every TMF621 response validates against the pinned OpenAPI document. This part ships TMF621; the browser surface is workstream 3C's, and the CTK verdict comes from the `ctk-tmf621` CI job (below).

Sources are cited by document, version and page (TMF621 UG v5.0.1, CP v5.0.0, OAS v5.0.1); nothing of them is copied here.

## Framework extensions

The mapping needed these, in `@std/tmf` and `server/http/tmf`, all generic:

- **Record context.** `render` gets the record's class lineage and its change history (`RecordContext`), `write` the lineage (`WriteTarget`), custom filters the subtree names of a class (`FilterContext`): `ticketType` and the class-dependent status writes need them.
- **Owner items** (`PartsAttribute.ownerItems`): items of an array that are owner fields (`relatedParty`'s reporter and assignee). They render before the parts; a body item an owner item matches writes the owner's fields, at most once; an omitted one is cleared (strict RFC 7396); one the caller may not name is `UnknownField`, never a part.
- **Path sources** (`pathSource`): one hop through a reference, read with the caller's access to both hops through the read compiler's paths, and written by resolving the target by that field among the records the caller can see (`InvalidReference` otherwise). The assignee is `assigned_to.individual`.
- **Optional sources**: fields of some classes only (an incident's `problem`), read where present, never needed to render or know the attribute, and written only when the caller may name them on the record's class.
- **Soft writes**: a value written only as a default gives way to another attribute's value in the same body (the status's hold reason against the `holdReason` characteristic).
- **History-backed attributes**: `statusChangeHistory` reads the record's change entries for its sources through the record service's history read (`readHistory`, the caller's readable fields only, 3.7), per record and only when selected.
- **A new part's prospective rendering** (`ItemMapping.newItemRendering`): a new note may repeat the author it would render (the caller's own name).
- **JSON Patch supplies what it writes**: every value attribute an operation writes is in the equivalent merge-patch body even when unchanged, so `replace /priority` with the current value keeps priority supplied (Contracts 14.2).
- **A mapping whose set is absent** answers `404` on every operation (`served` in `routes.ts`).
- **Writes fit the pinned schema**: after a create or merge-patch is saved, and before the transaction commits, each member the body supplied is rendered from the stored record as the system sees it, before any read mask (the caller's read adds only labels, reference paths, parts and history), and validated, with the resource's `@type`, against the pinned document's schema for that type, discriminator subtypes included (`checkWrittenMembers`; the Ajv compiler of the contract harness moved to `server/http/tmf/pinned-schemas.ts`). A misfit is `ValidationFailed` (`InvalidValue`) naming the member's path (`statusChangeHistory.0.status`) and the schema's rule, never the value, and the transaction rolls back, so nothing is stored. A member the caller may write but not read is checked too (a read-deny on `statusChangeHistory` with write kept: review round 2). A json attribute (`relatedParty` of a specification, `statusChangeHistory`, json characteristics) is otherwise kept as given, so this is what keeps a value the pinned schema refuses (`"relatedParty": "invalid"`, a `StringCharacteristic` with a number) out of the store.
- **Mapped hub notifications** (`events/tmf-events.ts`, `events/tmf-event-arrays.ts`, below).

## Judgments

1. **Plain tickets have no ITIL transition model** [judgment]. Contracts 14 defines models for incidents and problems only, TMF621 requires no refusal, and record-rule conditions cannot test a record's class, so a guard on `helpdesk.ticket` would also judge incidents and problems. Plain tickets are written as incidents are; their legacy `awaiting_approval` reads `held` (work held for a decision outside the ticket, not information from the caller, so no InformationRequired event), and problem-only states read as problems' do. A plain ticket therefore accepts any TMF621 status write. Decided by Martin (2026-10-23): plain tickets keep no transition model until Step 4 moves request tickets to `helpdesk.request`.
2. **Status writes** [judgment]: `held` keeps a hold reason other than `awaiting_caller`, else `awaiting_vendor`; leaving `on_hold` clears the hold reason and leaving `rejected` clears that reason, both as soft writes, so a `holdReason` characteristic or a `statusChangeReason` in the same body wins; `pending` and `rejected` are what their reason says, so another value for it is a contradiction (`ValidationFailed`).
3. **`ticketType`** [judgment]: `incident` and `problem` are recognized case-insensitively on writes; a plain ticket without `ticket_type` renders `ticket`; filters compare exactly as rendered, and `ticketType=incident` also selects plain tickets a generic write gave that type (`tmf-filter-equivalence-tmf621`).
4. **Severity and priority**: recognized labels case-insensitively on writes; a blank or null value is refused (both always render); filters compare exactly against the rendered text (decision 0025, D4): a canonical label (`Minor`) selects the key without a free-text label, any other value (`minor` included) the stored label exactly; `sort` orders by the key.
5. **Characteristics** [judgment; decided by Martin, 2026-10-23]: `troubleTicketCharacteristic` replaces strictly (RFC 7396, as every array of this mapping): a mapped characteristic the array leaves out is cleared, and one whose field has no empty value (`urgency`, `majorIncident`) is then `ValidationFailed` naming it, so a client sends the characteristics back as read with its changes (`examples/helpdesk/tmf621.sh` does); a mapped name the record's class lacks (`majorIncident` on a problem) is kept in json; a json characteristic gets `id` = its name and an `@type` from its value's JSON type; `characteristicRelationship` items need `id` and `relationshipType`.
6. **Relationships**: `causedBy` and `parent` are fields on incidents only, cleared when the array leaves them out and the caller can read them; elsewhere they are kept in json like any other type.
7. **External identifiers**: the number item is read-only; sending it back as read is accepted, any other STD number item is refused.
8. **Json items stored by generic writes** render with the `@type` STD can fill in (and a related entity's `entity` with `EntityRef`), so a ticket written through `/api/v1` still meets the profile's mandatory output (`tmf621-mandatory-output`).
9. **`statusChangeHistory`** [judgment, as Contracts 11.2]: the value last written through the API, as given (items get `@type` `StatusChange`), then the status changes recorded from that write's version on; `null` writes an empty prefix.
10. **Related parties** [judgment]: owner-item roles match exactly (`reporter`, `assignee`); the assignee's `name` is the assigned user's label (the read compiler follows one hop, and the individual's name equals the user's name when the user is created); `@referredType` is the TMF632 type of the party's class (`Individual`, `Organization`, `Party`); no `href` until Step 4 serves TMF632 (11.3). Helpdesk v3 lets agents read a user's `individual` for this.
11. **Note authors** (0034's TODO): `author` is read-only, the label of the note's author user; an array sent back as read changes nothing; a new note may name the caller's own name and no other (`ReadOnlyField`). TMF621 never writes another author, so historical notes cannot be imported with their authors through it; that needs the audited system import of Step 4 (Contracts 7).
12. **Note order**: notes have no order field, so a body that reorders kept notes is refused (decision 0033's rule) [judgment: TMF621 does not order notes].
13. **DELETE by the requester and admins** (M11's rule applied to tickets) [judgment]: the requester is the user who opened the ticket, kept in the new `opened_by` (set from the acting user on create, immutable by an invariant); agents and managers may delete tickets they opened, admins any. `caller` is a party and access conditions cannot test `created_by`, hence the field. Tickets created before v3 have no `opened_by` and only admins delete them. Decided by Martin (2026-10-23): the requester is the opener (`opened_by`).
14. **Specifications**: written by admins only (agents read them); `validFor` is not stored (`UnknownField`).
15. **`category`**: an incident's ITIL category as an STD extension attribute (decision 0021, decision 44's pattern); TMF621 has none.
16. **Before the helpdesk set is installed** TMF621 answers `404` (11.1's rule for resources not served).
17. **Helpdesk v3 edited in place** [judgment]: v3 is not released (no tag carries it), and `helpdesk v4` is Step 4's (Contracts 11.5), so the additions (`opened_by`, its two rules, two access rules) go into v3 with `upgrade-v3.json`; a database already at v3 reloads them with the loader's "content changed without a version bump" warning. Accepted by Martin (2026-10-23).
18. **The CTK user** `tmf_ctk` is an administrator created by `std bootstrap-admin`, so the kit's specification writes and deletes pass.

## Notifications (3H's N1, option (a))

Decision 0032 left every non-TMF688 hub with the generic `Record*Event` shape. This part chose option (a): a hub registered on TMF621 receives TMF621's own events (`events/tmf-events.ts`).

- The event types are the mapping's; one change gives every type it triggers, each with its own `eventId` (`eventIdOf(change, type)`).
- **Each event is its own `Idempotency-Key`** (amends decision 0032, which keyed a delivery by its change ID): the callback carries the event's `eventId`, stable across redeliveries, so the AttributeValueChange, StatusChange and Resolved events of one change are three keys, and a retried delivery repeats each one's key (`tmf621-events`, `hub-soak`).
- Each type's trigger fields must be readable on both images the outbox prepared for the hub's identity (12.1); `status` and its sources for the status events.
- Payloads (12.1): Create the resource as readable; AttributeValueChange the attributes whose sources changed and the arrays the change touched (none: no event); a status event the attributes its rule declares (`EventRule.payload`: `status`, `statusChangeDate`, `statusChangeReason` for tickets, `lifecycleStatus` for specifications; TMF630 v5.0.0 Part 1 §11.6.3 p.203), so the shared renderer names no attribute of its own; Delete `id`, `href`, `@type`. Rendered by the mapping with TMF621 hrefs from the change's image and what the preparation read; reference labels are not read at delivery, so references carry their `id` [judgment: the event reports the change entry; the resource is one GET away].
- **A cleared attribute is `null`** [judgment]: an AttributeValueChange's resource is a JSON merge patch (TMF630 v5.0.0 Part 1 §11.6.2 pp.202-203 says the event follows merge-patch semantics; Part 1 pp.105-106 says a merge patch removes a member with `null`), so an attribute the change cleared, which the identity can still read, is sent as `null`. The pinned schemas have no nullable members, so `tmf621-events` validates such an event as a merge patch (`mergePatchEventProblem`): the non-null members against the event's schema, and `null` only on members the resource's schema does not require (`@type` is required through `Extensible`, so `"@type": null` is refused).
- **Arrays are sent whole** (§11.6.2): the preparation transaction (`prepareMappedEvents`, the external effect's new `prepare` step, run as the hub's identity before `render`) finds the arrays an update touched: an owner item's field changed, or, for the owner's aggregate save, a part of the array its transaction wrote that the identity may see. Each touched array is read whole: today's parts of the owner and those a later aggregate version deleted, each at its version at the change, masked for the identity as any delivery payload is (`payloadOf`); an array whose owner reference the identity cannot read on the part class is unreadable, as in a GET. So a note the identity cannot see neither appears in its arrays nor gives it an event. Reference paths (`assigned_to.individual`, the assignee's party) are read on the target as the identity may read it now, and `statusChangeHistory` from the record's history up to the change (`withHistory`).
- **Part versions belong to owner versions by the change entries, not by time** (review round 2): every part write is finalized in its own transaction by exactly one aggregate save of its owner (Contracts 4.9: an owner is persisted at most once per transaction), whose `cause.aggregate.parts` lists the saves' part changes and whose `operation_id` they share, as do the part writes the settling made. So a part change belongs to the owner version of the aggregate save in its operation, and one whose operation has none predates aggregates (helpdesk sets before v3) and every aggregate version. Nothing compares change IDs or clocks: UUIDv7 time is monotonic only within one PostgreSQL backend, so it cannot order changes across a pool.
- **A fixed number of statements per delivery**, whatever the array's size: the touched parts in one statement, the members in two (today's parts by the owner reference, and the parts later aggregate versions deleted), their versions at the change with the images saved with them (`core.change_image`) in one, and masking in memory. Only a change entry that migration 0028's image backfill has not reached yet is rebuilt alone from its history (`readEntries`), during a rolling upgrade. Measured by the reviewer's probe (statements of one worker pass after changing one note): 52, 142 and 1,042 for tickets with 10, 100 and 1,000 notes before; 40, 39 and 40 after (`tmf621-events` asserts the counts are equal, wake-up `pg_notify`s aside).
- `eventType` queries name TMF621 types, at production (`acceptsHubEvent`: any type the change's kind can give) and at delivery.
- A TMF621 hub without `resource=` listens to the resource whose type starts every named event type, else `troubleTicket` [judgment: TMF clients register with `eventType` queries only].
- `tmf621-events` validates every delivered body against its pinned TMF621 event schema (`schemaValueProblem`, new in the contract harness).

- **Hub query filters** test stored fields: a TMF621 hub query takes `eventType` and the attribute filters a subscription condition can evaluate on the version's own image (Contracts 5.10: no reference hops; the record's class and its system fields are not in that image). A filter on an attribute derived from the record's class or system fields (`ticketType`, `creationDate`, `lastUpdate`) is refused at registration with `InvalidRequest` (`parameter` `query`) naming the attribute and listing those a hub can filter on, instead of the change set's `DefinitionInvalid`.

Remaining: `ticketType` in a hub query. Supporting it needs either the record's class in the subscription condition profile (a Contracts 5.10 change: the producer evaluates conditions on stored fields, and the definition check refuses the `class` path) or a TMF630 Part 6 filter evaluator over rendered event resources, which STD does not have; either is more than this round. No matrix row claimed here covers it.

## The CTK job

`.github/workflows/ci.yml` job `ctk-tmf621` runs `pnpm ctk:ci` (`examples/quickstart/src/ctk-ci.ts`): a disposable database, `std upgrade --set examples/helpdesk/v3`, `std bootstrap-admin` as `tmf_ctk`, `std serve` on `127.0.0.1`, a bearer session, then a self-check of the kit's payloads through TMF621 (create, read, list with each `fields` the kit uses, patch, delete), and, only under GitHub Actions, `pnpm ctk tmf621 --url … --token-file … --payloads … --network host --reports ctk-reports/tmf621`, the bearer token in a mode-0600 file in a temporary directory, never on a command line or in a log (`ctk-token`): the pinned zip (SHA-256), the pinned image digest (already in `pins.json` from 0033), the runner's verdict (Contracts 11.1). The reports are the job's artifact. `pnpm ci:local` runs the self-check and never the kit. The 27 `KIT/*` rows stay `pending` until that job passes; their `kitCases` are 0033's, matched against a real run of the kit.

The runnable result: `examples/helpdesk/tmf621.sh` opens, updates (urgency, a note, `inProgress`), extends the notes, resolves (with `If-Match`) and shows a stale `If-Match` refused, through TMF621 with curl; `pnpm tmf621-example:ci` runs it twice against `std serve` under the quickstart's execve trace (CI step "TMF621 example"). `examples/listener` is workstream 3H's (a TODO in the script).
