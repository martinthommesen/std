# 0038. HTTP edge limits

Status: implemented with expand migrations 0031–0033, 2026-10-23; E30 remains **proposed** for Martin. Contracts 3.1, 3.8, request body handling and 12.2.

The HTTP module rejects excessive Content-Length before reading and bounds streaming reads, including DELETE and TMF routes; its paused Node reader preserves the socket long enough to send an actionable TMF 413, whereas Effect's default overflowing reader destroys it. Preliminary authentication protects change-set and definition body reads while execution keeps its own authentication; sign-in admission runs before request transactions and retains capacity until native scrypt and counter commits finish, including on disconnect. Numeric callback classification requires `2000::/3`, excludes IANA non-global special ranges and honors explicitly global suballocations; IPv4, all-answer checks, socket pinning and private opt-in protections stay intact ([IANA registry](https://www.iana.org/assignments/iana-ipv6-special-registry/), read 2026-10-23).

- Global body **tripwire: 67,108,864 bytes (64 MiB)**. Measurement on this revision: helpdesk v3 converted to its complete change-set envelope is **95,538 bytes / 186 operations**, largest definition operation **1,638 bytes** (`pnpm --filter @std/server test test/http-edge-limits.test.ts`, “measures the helpdesk change-set request”). Searches of server tests and fixtures found the forty-field text record image (`change-images.test.ts`, **1,391 bytes** when recreated with `JSON.stringify` on 2026-10-23) and helpdesk payloads; the existing one-million-code-point long-text ceiling also needs up to **12,000,000 bytes** when supplementary characters are fully JSON-escaped. [judgment] 64 MiB leaves over five times that single-field transport size; healthy future requests approaching it require remeasurement.
- Sign-in body **budget: 65,536 bytes (64 KiB)**. Login permits **4,000 code points** (platform text ceiling); password has a shared **1,024 Unicode code-point** cap on creation, change and sign-in, as explicitly approved for greenfield STD on 2026-10-23. [NIST rev.4 §3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver) and [rev.3 §5.1.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver) count code points and recommend support for at least 64 characters. Raw UTF-8 requires at most `1024 * 4 + 4000 * 4 + 51 = 20,147` bytes; fully escaped JSON requires `1024 * 12 + 4000 * 12 + 51 = 60,339`. The cookie-delivery JSON envelope measures **51 bytes** (`JSON.stringify`, 2026-10-23); the budget leaves **5,197** whitespace bytes even with full escaping. [judgment] Password writes fail as ValidationFailed; sign-in rejects excess before KDF work with the same actionable limit message for any login. No shipped fixture/demo credentials need changes or a reset path. Router matching determines the smaller budget, including URL aliases; bounded reads are memoized across transaction retries.
- Per-login **budget: 100 consecutive failures**, with [judgment] **five** mistakes before pauses of **30 seconds**, doubling to **one hour**, and one-hour refusal at the ceiling; successful verification resets the counter. At the ceiling, a failed cooldown probe or refused attempt renews the one-hour refusal and quiet expiry instead of granting a fresh burst. No KDF runs on a refused attempt. Source **budget: 60 attempts per 60-second window**, measured by the socket address alone, with no trusted-proxy setting. [judgment] One attempt/second sustained per source plus bounded bursts limits ordinary guessing while allowing human retries; every throttle has the same generic TMF 429 and `Retry-After: 60`. Login counters are SHA-256 keys over the same normalized login used by lookup (bounded index width); source rows expire one window after use, every login row after **24 quiet hours**, identically for known and unknown logins (user-approved security policy, 2026-10-23; Martin may override); bounded retention reclaims both.
- Observation-window policy: the [OWASP Authentication Cheat Sheet, Account Lockout](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#account-lockout) describes a login-associated counter, threshold, observation window and lockout duration (read 2026-10-23). **Deviation:** 24 quiet hours resets the counter, so the 100-failure ceiling is per observation window, not a lifetime ceiling. Policy permits at most about **100 verified failures per account per 24 hours plus cooldown**; the actual exponential schedule is tighter: **34** in a fresh 24 hours, then at most **24/day** while continuously probing at the one-hour ceiling. Receipt: `pnpm exec node --input-type=module` importing the exported delay/grace/cap constants and accumulating `min(3600, 30 * 2**(failures-5))` after failure five produced `{failuresInFresh24Hours:34,secondsToNextFailure:86610,sustainedAtCeilingPer24Hours:24}` on 2026-10-23. This assumes an attacker waits through every cooldown; attempts during ceiling cooldown renew it. Success discards previous failures as NIST recommends.
- Counter storage bound: one row per distinct normalized login attempted in the preceding **24 hours**, plus one per socket source active in the preceding **minute**, plus expired rows awaiting the bounded reaper. Login keys are fixed **64-character SHA-256 hex** values, never attacker-sized names. For `R` distinct failed logins/second, live login rows are at most approximately `86,400 * R`; a single source's 60/minute budget corresponds to approximately **86,400/day**, plus a boundary burst of at most 60. This is a retention bound, not a hard global cardinality cap. Each sign-in reclaims up to 256 expired rows per table; the idle reaper drains an expired backlog `E` within approximately `ceil(E/256)` minute passes, subject to database availability and concurrent locks. A stopped database/server pauses reclamation; restarting resumes it. Thus attacker-chosen names do not accumulate permanently.
- KDF **budget: two running verifications and four queued requests**. Current hashes have `N=2^15=32768`, `r=8`, `p=1`: `128*N*r = 33,554,432` bytes (**32 MiB**) per verification, about **64 MiB** for two. Node's [documented libuv pool](https://nodejs.org/api/cli.html#uv_threadpool_sizesize) defaults to **four**, leaving two workers for DNS/fs; larger pools do not raise the memory budget, smaller supported pools reduce concurrency and retain a worker. [judgment] Two waiting waves bound queued decoded body storage to four 64-KiB requests. Pools below two are refused at startup.
- Active-session **tripwire: 128 per user**. [judgment] This accommodates more than a hundred browser/device profiles for one person during the existing **12-hour** session lifetime; integrations use Step 4D tokens. A user-row lock serializes concurrent issuance and revokes oldest existing sessions before insertion; no user is locked out.
- Retention **work budget: 256 rows per table per pass**, opportunistically at sign-in and every **minute** in the server, with expiry indexes and `SKIP LOCKED`. The batch-cost test uses `EXPLAIN (ANALYZE, BUFFERS)` against **10,000** expired session rows on Postgres 18; the indexed candidate scan plus direct TID deletion took **1.093 ms** (planning **0.278 ms**), 256 rows, no whole-table scan (`pnpm --filter @std/server test test/http-edge-limits.test.ts`, “measures an indexed session cleanup batch on Postgres 18”, 2026-10-23). A minute leaves over 54,000 such execution times between idle passes; the cadence is a housekeeping policy, not a throughput ceiling. Sign-in reclamation scales with issuance, up to 256 reclaimed rows per new session, so the periodic pass is not the sole drain under load.

[NIST SP 800-63B rev.3 §5.2.2](https://pages.nist.gov/800-63-3/sp800-63b.html#throttle) and [current rev.4 §3.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html#rate-limiting-throttling) support the 100-failure ceiling and increasing delays; rev.4 (July 2025) additionally requires authenticator disablement and rebinding at its ceiling. [judgment, direct task instruction] STD uses temporary refusal and automatic recovery, including the explicitly approved 24-hour quiet reset, to avoid permanent account disablement, so this change does **not** claim full rev.4 conformance. TMF630 v5.0.0 Part 1 §3.3.3 p.32 requires 413 and p.33 recommends 429; 413 on TMF APIs whose pinned documents omit it is **E30 proposed**, not a change to decision 0021 decision 52, and needs Martin's decision. ODA IG1329 v1.1.0 §4.1.1 p.19 calls for rate limiting at the external API gateway; the server applies its own limits so direct access has the same protection.
