# 0038. HTTP edge limits

Status: implemented with expand migrations 0031–0033, 2026-10-23; E30 and E31 remain **proposed** for Martin. Contracts 3.1, 3.8, request body handling and 12.2.

The HTTP module rejects excessive Content-Length before reading and bounds streaming reads, including DELETE and TMF routes; its paused Node reader preserves the socket long enough to send an actionable TMF 413. Protected body routes authenticate in a preliminary transaction, consume their bounded body without a database connection, then reauthenticate for execution. A process-local one-in-flight gate per source runs before body reads and database work; global KDF capacity covers password verification alone, never SQL lock waits, cleanup or commits. Admitted sign-in work finishes verification and counter commits on disconnect. Numeric callback classification requires `2000::/3`, excludes IANA non-global special ranges and honors explicitly global suballocations; IPv4, all-answer checks, socket pinning and private opt-in protections stay intact ([IANA registry](https://www.iana.org/assignments/iana-ipv6-special-registry/), read 2026-10-23).

- Record writes, generic and TMF, and form-state proposals have a **4,194,304-byte (4 MiB) budget**. Martin selected the approximately **0.5-second latency target** on 2026-10-23. The earlier 16 MiB choice incorrectly extrapolated from `applyChangeSet`, which refuses before record decoding; it was not a record-route receipt. Removing the redundant `Schema.Json` envelope walk (create, merge patch, JSON Patch values and form-state values) leaves field decoders responsible for their own types: text rejects an array/object at its first node, while JSON fields retain their existing validation. Effect 4.0.5's JSON validator is iterative, but still needlessly walked every node. Corrected record-route measurements below still exceed the target at 16 MiB, so the budget follows Martin's accepted target rather than preserving that incorrect number. At 4 MiB the worst repeated stall was **394 ms**, with legal multi-long-text records succeeding.
- Change sets and definition writes have a **1,048,576-byte (1 MiB) budget**. After merging main's form rules and TMF621 field, rule and access definitions, the complete helpdesk v3 change-set envelope measures **106,677 bytes**, replacing round 1's **95,538 bytes** (`pnpm --filter @std/server test test/http-edge-limits.test.ts`, “measures the helpdesk change-set request”, 2026-10-23). This leaves **9.83×** headroom for complete large definition sets.
- Hub registration has a **131,072-byte (128 KiB) budget**: the existing `resource=acmeAsset&cost=10` hub fixture with `https://callback.example/` measures **91 bytes** including its type member (`JSON.stringify`; http-edge-round2 receipt test, 2026-10-23). The budget gives over **1,400×** headroom for longer selectors and URLs. These strings have no finite schema maximum, so this is an explicit HTTP budget, not a claimed per-string schema ceiling. Dead-delivery tasks have a **1,024-byte budget**: their @type and positive int8 deliveryId (at most 19 digits) serialize below 100 bytes, leaving over ten times headroom. DELETE and non-write methods have a **zero-byte budget** because their request schemas permit no body (Contracts 10.5). Such a forbidden payload is `400 InvalidRequest`, with limit zero, received bytes and connection closure, preserving TMF630 Part 1 §7 pp.126–127 and the existing DELETE contract.
- The **process-wide record/other-body budget is at most 16,777,216 bytes (16 MiB)**, in whole record budgets: `4 MiB * min(4, floor(heap_size_limit / (64 * 4 * 4 MiB)))`. This admits **four maximum-size record writes simultaneously** on the measured 4,192 MiB V8 heap, fewer on smaller heaps. Startup fails if even one record body cannot fit. Review's original record probe measured approximately **55× RSS amplification**, not 28×; the clean corrected probes below measured approximately **184 MiB growth / 4 MiB = 46×**, and 720 MiB / 16 MiB = 45× on the first larger request. The budget rounds those measurements up to **64×** for allocator/GC headroom: 16 MiB costs at most **1 GiB** under that sizing model, below one quarter of the measured heap. RSS is not a guaranteed linear bound; this is a measured capacity budget with headroom. Every adapter reserves **actual bytes before retaining each chunk**, never unreceived Content-Length. Reservations cover parsing, work, retries and response construction, and release on completion, failure or cancellation. Exhaustion is **503 BodyCapacityExceeded** naming `body_in_flight_max_bytes`, its value and additional bytes requested, connection closure and **Retry-After: 1** (exceeds the accepted ~0.5-second pause; TMF630 v5.0.0 Part 1 §3.3.4 p.33). E31 remains proposed.
- Sign-in bodies use an independent **131,072-byte (128 KiB) process budget**: two complete 64-KiB credential envelopes, matching the two KDF workers. Its exhaustion names `session_body_in_flight_max_bytes`; sign-in never consumes the record budget, nor record writes the sign-in budget.
- Body reads require an average **62,500 bytes/second**, after **8,000 ms** initial allowance, checked every **1,000 ms**. The rate is half the **1 Mbit/s** uplink in the [UK broadband universal-service specification](https://www.legislation.gov.uk/uksi/2018/445/schedule/1/made), leaving half for protocol/contended-link overhead. The allowance covers RFC 6298's initial [1-second RTO and doubling](https://www.rfc-editor.org/rfc/rfc6298.html) through 1+2+4-second retransmission waits; polling uses that initial RTO. This is a progress budget, with at most one polling interval of detection delay. A stalled one-byte upload is refused around nine seconds; a fully sent body missing EOF has at most its size/rate plus the allowance. Failure is **400 InvalidRequest**, with `body_min_bytes_per_second`, `body_read_grace_ms`, elapsed time, received bytes and required bytes, followed by connection closure. It never occupies SQL while waiting. Node's **headersTimeout=60,000 ms** explicitly retains its [documented header-parser budget](https://nodejs.org/api/http.html#serverheaderstimeout); **requestTimeout=135,109 ms** is `headersTimeout + grace + ceil(record_max_bytes / minimum_rate * 1000)`, allowing a maximum body at the accepted rate after the header allowance. Both transport timeouts produce Node's 408 and closure before/around application body handling; application progress failures carry the detailed error above.
- Sign-in body **budget: 65,536 bytes (64 KiB)**. Login permits **4,000 code points** (platform text ceiling); password has a shared **1,024 Unicode code-point** cap on creation, change and sign-in, as explicitly approved for greenfield STD on 2026-10-23. [NIST rev.4 §3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver) and [rev.3 §5.1.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver) count code points and recommend support for at least 64 characters. Raw UTF-8 requires at most `1024 * 4 + 4000 * 4 + 51 = 20,147` bytes; fully escaped JSON requires `1024 * 12 + 4000 * 12 + 51 = 60,339`. The cookie-delivery JSON envelope measures **51 bytes** (`JSON.stringify`, 2026-10-23); the budget leaves **5,197** whitespace bytes even with full escaping. [judgment] Password writes fail as ValidationFailed; sign-in rejects excess before KDF work with the same actionable limit message for any login. No shipped fixture/demo credentials need changes or a reset path. Router matching determines the smaller budget, including URL aliases; bounded reads are memoized across transaction retries.
- Per-login **budget: 100 consecutive failures**, with [judgment] **five** mistakes before pauses of **30 seconds**, doubling to **one hour**, and one-hour refusal at the ceiling; successful verification resets the counter. At the ceiling, a failed cooldown probe or refused attempt renews the one-hour refusal and quiet expiry instead of granting a fresh burst. No KDF runs on a refused attempt. Source **budget: 60 attempts per 60-second window**, measured by IPv4 address or IPv6 /64 socket subnet, with no trusted-proxy setting. The one-in-flight source gate prevents one source occupying the global queue during row-lock waits; its value is a concurrency policy, not a throughput measurement. [RFC 6177 §§2,5](https://www.rfc-editor.org/rfc/rfc6177.html) treats /64 as a subnet and recommends multiple subnets per end site; /64 aggregation prevents privacy-address rotation within that subnet from minting budgets, but does not claim to cover an entire multi-subnet site. IPv4-mapped IPv6 shares the IPv4 key. Behind the ODA gateway all clients share its socket address, so 60/minute and one in-flight become install-wide for that gateway; forwarding headers cannot change this. [judgment] One attempt/second sustained per source plus bounded bursts limits ordinary guessing while allowing human retries; every throttle has the same generic TMF 429 and `Retry-After: 60`. Login counters are SHA-256 keys over the same normalized login used by lookup (bounded index width); source rows expire one window after use, every login row after **24 quiet hours**, identically for known and unknown logins (user-approved security policy, 2026-10-23; Martin may override); bounded retention reclaims both.
- Observation-window policy: the [OWASP Authentication Cheat Sheet, Account Lockout](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#account-lockout) describes a login-associated counter, threshold, observation window and lockout duration (read 2026-10-23). **Deviation:** 24 quiet hours resets the counter, so the 100-failure ceiling is per observation window, not a lifetime ceiling. Policy permits at most about **100 verified failures per account per 24 hours plus cooldown**; the actual exponential schedule is tighter: **34** in a fresh 24 hours, then at most **24/day** while continuously probing at the one-hour ceiling. Receipt: `pnpm exec node --input-type=module` importing the exported delay/grace/cap constants and accumulating `min(3600, 30 * 2**(failures-5))` after failure five produced `{failuresInFresh24Hours:34,secondsToNextFailure:86610,sustainedAtCeilingPer24Hours:24}` on 2026-10-23. This assumes an attacker waits through every cooldown; attempts during ceiling cooldown renew it. Success discards previous failures as NIST recommends.
- Counter storage bound: one row per distinct normalized login attempted in the preceding **24 hours**, plus one per socket source subnet active in the preceding **minute**, plus expired rows awaiting the bounded reaper. Login keys are fixed **64-character SHA-256 hex** values, never attacker-sized names. For `R` distinct failed logins/second, live login rows are at most approximately `86,400 * R`; a single source's 60/minute budget corresponds to approximately **86,400/day**, plus a boundary burst of at most 60. This is a retention bound, not a hard global cardinality cap. Each admitted sign-in reclaims up to 256 expired rows per table in its own maintenance transaction; the idle reaper drains an expired backlog `E` within approximately `ceil(E/256)` minute passes, subject to database availability and concurrent locks. A stopped database/server pauses reclamation; restarting resumes it. Thus attacker-chosen names do not accumulate permanently.
- Before either maintenance or request SQL opens, a separate fail-fast sign-in slot is acquired and held through both transactions and their retries/commits. Its budget is `min(2, floor(database_max_connections / 2) - 1)`: **two sign-in transactions**, plus **at most one shared fallback revision-header transaction**, consume at most **three of ten connections (30%)** by default, never more than half of the configured pool. The revision middleware coalesces only concurrent fallback lookups using `Effect.cachedWithTTL(Duration.zero)`; no completed revision is retained, so later responses still obtain fresh state. The live probe exposed this previously hidden post-refusal SQL path: bounding only sign-in left nine idle-in-transaction connections. Two is the existing KDF worker capacity; reserving a header-lookup slot inside the half-pool share protects unrelated API work under distributed sources. A pool below **four** is refused at startup: one sign-in plus one header lookup needs two slots, with two reserved for other work. The error names the configured value and required minimum. At pool sizes four and five, one sign-in workflow is admitted; at six and above, two are admitted. Exhaustion returns 429 with `sign_in_transaction_slots`, `database_max_connections`, one additional slot requested, and Retry-After 60. The regression holds two sign-ins on a login-counter lock, refuses 128 independent-source attempts before SQL, and completes an authenticated read while that lock remains held. KDF permits continue to cover verification alone.
- KDF **budget: two running verifications and four queued requests**. Current hashes have `N=2^15=32768`, `r=8`, `p=1`: `128*N*r = 33,554,432` bytes (**32 MiB**) per verification, about **64 MiB** for two. Node's [documented libuv pool](https://nodejs.org/api/cli.html#uv_threadpool_sizesize) defaults to **four**, leaving two workers for DNS/fs; larger pools do not raise the memory budget, smaller supported pools reduce concurrency and retain a worker. [judgment] Two waiting waves bound queued decoded body storage to four 64-KiB requests. Pools below two are refused at startup.
- Active-session **tripwire: 128 per user**. [judgment] This accommodates more than a hundred browser/device profiles for one person during the existing **12-hour** session lifetime; integrations use Step 4D tokens. A user-row FOR NO KEY UPDATE lock serializes concurrent issuance and revokes oldest existing sessions before insertion; no user is locked out.
- Retention **work budget: 256 rows per table per pass**, in a separate maintenance transaction at sign-in and every **minute** in the server, with expiry indexes and `SKIP LOCKED`. The batch-cost test uses `EXPLAIN (ANALYZE, BUFFERS)` against **10,000** expired session rows on Postgres 18; the indexed candidate scan plus direct TID deletion took **1.093 ms** (planning **0.278 ms**), 256 rows, no whole-table scan (`pnpm --filter @std/server test test/http-edge-limits.test.ts`, “measures an indexed session cleanup batch on Postgres 18”, 2026-10-23). A minute leaves over 54,000 such execution times between idle passes; the cadence is a housekeeping policy, not a throughput ceiling. Sign-in reclamation scales with issuance, up to 256 reclaimed rows per new session, so the periodic pass is not the sole drain under load.

[NIST SP 800-63B rev.3 §5.2.2](https://pages.nist.gov/800-63-3/sp800-63b.html#throttle) and [current rev.4 §3.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html#throttle) support the 100-failure ceiling and increasing delays; rev.4 (July 2025) additionally requires authenticator disablement and rebinding at its ceiling. [judgment, direct task instruction] STD uses temporary refusal and automatic recovery, including the explicitly approved 24-hour quiet reset, to avoid permanent account disablement, so this change does **not** claim full rev.4 conformance. TMF630 v5.0.0 Part 1 §3.3.3 p.32 requires 413 and p.33 recommends 429; 413 on TMF APIs whose pinned documents omit it is **E30 proposed**, not a change to decision 0021 decision 52, and needs Martin's decision. ODA IG1329 v1.1.0 §4.1.1 p.19 calls for rate limiting at the external API gateway; the server applies its own limits so direct access has the same protection.

Residual distributed-source risk: the review measured approximately **30 KDF verifications/second** on this host. Approximately **30 independent sources**, each sustaining below **60 attempts/minute**, can saturate that capacity and cause other sources to receive fail-fast 429s. Per-source isolation prevents the confirmed one-source queue takeover; it cannot reserve availability against a distributed flood. [ODA IG1329 v1.1.0](https://www.tmforum.org/resources/specification/ig1329-oda-canvas-definition-v1-1-0/) §4.1.1 p.19 assigns rate limiting and security enforcement to the external API gateway; deployments must apply that control there. No trusted-proxy setting exists: behind a gateway the server sees the gateway's shared source budget, including the one-in-flight gate.

An initial 16-MiB legal-long-text fixture only 300 bytes below the HTTP ceiling exposed the existing PostgreSQL driver's 16-MiB `maxMessageSize`: a result carrying JSON framing/field IDs exceeded that wire-message budget and produced a connection error. The corrected fixture leaves 8 KiB for that framing and succeeds. The selected 4-MiB HTTP budget also leaves this wire-message budget ample room; the general driver message-size constraint is outside this HTTP-edge change.

The final 128-source, five-second live flood completed **95/95** authenticated `session/current` reads with **28 ms p50, 57 ms p95, 165 ms maximum**, while returning 78 invalid-credential and 29,988 fail-fast throttle responses. Sampling `pg_stat_activity` every 50 ms saw at most **four** idle/in-progress transactions total, including the authenticated control read: two sign-in workflows, one shared revision-header lookup, and that control. The earlier gate-only implementation reached nine, which led to coalescing the header lookup. These are host measurements, not an HTTP latency guarantee. Adapted `probe-reserve.mjs` runs with both two authenticated declared-4-MiB uploads and 520 independent-source declared-64-KiB sign-ins returned **201** for a small record write and an independent sign-in at 1.5 seconds, 11.5 seconds, and after closing the uploads. `http-edge-round3` checks the stalled upload's actionable progress error and connection closure; the web/Node capacity test fills actual retained bytes before asserting overload and recovery.

The adapted abort probe repeated 200 framed/chunked cancellations and 20 malformed-JSON requests. Four concurrent near-4-MiB writes afterwards all reached field validation (422), with no 503 capacity refusal, confirming that their byte reservations were available again. The probe server was stopped and its scratch database dropped after measurement.
