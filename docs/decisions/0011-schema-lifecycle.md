## APIs for workstream 1B (config layers)

- **Who is asking.** `applyChangeSet({ operations, requester, origin, source })`. A set load passes `origin: setOrigin(owner)` (`load-set.ts` already does); the core set's origin is the only one that may change protected definitions. Admin edits pass `origin: LOCAL_ORIGIN` (the default) and the requester's role IDs; item 9 builds the requester from the HTTP `Actor`.
- **Removed upstream.** A set load retires removed tables, fields and roles with `{ op: "retire", id, version }` under its own origin; the 1.7 refusals apply (a role an active access rule names is refused with `DependencyConflict`; 1B reports that at plan time). Rules are deactivated with `update` of `active`. Retired app definitions may be purged locally; `adopt` stays 1B's.
- **Label and help-text overrides.** A change by an origin that does not own the definition (any change to a protected definition except label and help text is refused) is applied to the effective record and marked `localOverride: true` in `AppliedChangeSet.notes` and in the journal entry. Since the 1B merge, both HTTP write paths (the change-set endpoint and generic writes) run through `applyLocalChangeSet`, which plans the layer writes with `planLocalEdits` (`server/config/local-edits.ts`, also used by the config service's `edit` and `adopt`): an `update` of a shipped definition stores one `core.config_override` row per property in the same main transaction (only the 8.2 properties; others are `DefinitionInvalid`), and pins the planned configuration state; anything but label and help text on a protected definition stays with the engine (`DefinitionProtected`). An `adopt` needs a base row marked removed and deletes it with its overrides; the engine refuses an `adopt` that the layer writes do not list (`ExtraWrites.adopted`), so no entry point can adopt without the cleanup (review round 3).
- **Renames by a set.** `{ op: "rename", id, version, name }` under the set's origin; physical renames follow.
- **Refusals** are typed: `DefinitionProtected` (`reason`: `protected`, `owner`, `reserved`, `notExtensible`, `platform`), `DependencyConflict` (each blocking dependent by ID, kind, name and dependency kind), `UseRetireOrPurge`, `PermissionRequired`, `PurgeRefused`.
- **Doctor.** `schema-interrupted.test.ts`'s `assertRecovered` has the place for a `std doctor` exit-0 assertion; `test/catalog-drift.ts` is a small stand-in.

## Decisions

### Rename

Renames go by ID for every named kind: namespaces (`ALTER SCHEMA ... RENAME TO`), tables (`ALTER TABLE ... RENAME TO`), fields (`ALTER TABLE ... RENAME COLUMN`), and roles, permissions, subscriptions, access rules and indexes (configuration only). Access rules and indexes got an optional `name` (null by default; an identifier; unique among the live indexes of a table, and among live access rules) through a platform migration adding nullable `name` columns to `core.access_rule` and `core.index` (catalog-only `ADD COLUMN`; the core set describes both columns). The migration is 0005 on this branch, because migration IDs must be consecutive and workstream 1B's 0005 is not merged; it becomes 0006 at merge. An index's physical name stays `std_ix_<id>`. Set files accept an optional `name` on indexes and access rules.

A rename to a name another live definition of the same scope holds before the change set is refused, even if the change set renames that holder too: physical renames run one after another, so a swap would collide in the catalog and in the definition tables' live-name unique indexes.

### Preflight identifiers

The preflight (row existence, violation counts, purge counts) runs before any DDL of the change set, so it names tables and columns as they are before the change set: a rename in the same change set has not run yet. DDL and follow-up steps use the final names (review round 1: a table or field rename plus a unique index failed with 42P01 and 42703).

### Statement order and locks

The main transaction runs drops first (purged columns, then purged tables, children before parents), then renames (schemas, tables, columns), then the retired fields' `DROP NOT NULL`, then the 0006 pipeline. So a name a purge frees can be taken in the same change set. Drops and renames name tables as they are before any DDL; later statements use the names after the change set. All table locks are taken before the first statement (decision 0007), so every lock names the table as it is before any DDL: `lockNames` maps after-names back for the later statements.

`DROP TABLE` locks every ancestor `ACCESS EXCLUSIVE` (root first), the table, and every table its FKs reference (reference targets, and `core.user` for a root table's audit FKs), because dropping an FK drops its triggers on the referenced table. Purging a reference field locks both tables, as 0007 measured. `ALTER SCHEMA ... RENAME` takes no table lock. The lock-inventory probe checks every lifecycle form on populated tables.

### Retire, reactivate and the effective schema

Retiring a field sets `required` to false, clears `required` on every override of the field on descendant classes (their other tightenings stay; the journal lists them as the operation's cascade), and, for a required non-boolean field, runs `ALTER COLUMN ... DROP NOT NULL` (catalog-only, 1.4 table). So the field is optional on every class while retired and after reactivation (review round 1). With workstream 1B's layering, clearing an override's `required` becomes a change of the effective override record. Booleans stay `NOT NULL DEFAULT false`, so inserts without them work anyway. A reactivated field therefore comes back optional. Retiring a parent field retires it on every child class: there is one definition, and `effectiveFields` of every class below shows it `retired`, not `selectedByDefault` and not `writable`. A retired table has `effectiveClass(...).acceptsWrites` false; every field on it is not `writable`. The read compiler and the save pipeline (0C) read these flags; the save pipeline reports `DefinitionRetired`.

New definitions may not point at retired ones (a field on a retired table, a reference to one, an index on a retired field, a child of a retired class), but existing ones keep pointing at them. Stored conditions that read a field that is then retired keep working: validation checks conditions with `purpose: "store"` only for definitions whose condition the change set writes, and with `purpose: "evaluate"` for the rest.

### Purge

Purge needs `schema.purge`, checked by ID through the requester's role grants (`admin` holds nothing implicitly), a confirmation repeating the target's ID and version, and a target retired in the configuration the change set starts from (`PurgeRefused` `notRetired`, `retiredInThisChangeSet`, `confirmation`). The coordinator counts the non-null values of a field, or the rows of each table, on its `SCHEMA_KEY` connection before `CONFIG_KEY`; the journal entry records them as `destroyed`, which makes the journal the purge's audit record. A field purge takes its single-field indexes and its overrides along (`DROP COLUMN` drops the indexes); a table purge takes its fields, indexes and overrides along.

Records of a child class also have rows in every ancestor table, which `DROP TABLE` of the child cannot remove. A purge of a non-root class whose subtree still has records in a root table that stays is refused (`PurgeRefused` `hasRecords`, counted under `SCHEMA_KEY`); a hierarchy is purged from its leaves up to its root in one change set, where the root's `DROP TABLE` removes every record. The ancestors' subtree CHECKs keep the purged class's ID: it is never reused, so the wider check admits nothing.

The tombstone is the definition row itself in state `purged`: ID, last name, type and label stay; the live-name unique indexes of migration 0002 exclude purged rows, so the name is free. The purge revision is the first `core.definition_revision` row in state `purged` (`purgeRevisionOf`), and `definitionAt(id, R)` returns the definition as it was at revision R, which is how history reads old values under their old names and labels. A purge does not free a column slot (dropped columns count toward 1,600).

### Dependencies (1.7)

The dependency checks run in memory over the snapshot loaded under `CONFIG_KEY` in the main transaction, which is the configuration `core.config_dependency` indexes; `dependentsOf` is the reverse index. New dependency kinds: `subscription_on` (a subscription to its class) and `grant_of` (a grant to its role and permission), so a role or permission delete finds its grants and a table purge finds subscriptions. Deviations and precisions of the 1.7 table, all in the contract now:

- A multi-field unique index refuses the retire of its fields, so a purge can only meet a non-unique multi-field index; both refuse.
- A table purge is also refused while an access rule or subscription is on the table: leaving them would dangle, and deleting security configuration implicitly is worse.
- A role delete is refused while any access rule names it (a deleted role cannot stay in a rule); a role retire only while an active rule names it. A deleted role takes its grants along. Retire and delete report the role's user-role assignments: the server counts `core.user_role` rows on the pool before `CONFIG_KEY` (data, so not under it) and returns and journals the count (`userRoleAssignments`); the assignments stay.
- Any active reference field pointing at a table keeps it from being retired, whatever the state of the field's own table and including the table's own references to itself; the field's own state decides. The rule holds the other way too: a reference field, or a table carrying an active one, cannot be reactivated while the target table is retired (`DependencyConflict` naming the target). A table's reference to itself becomes active with the table (review round 1).
- `delete` of an override is refused (it would loosen the field, 2.5).

### Protected definitions and local additions (1.8)

The guard runs first for every operation and every origin. Protected definitions accept only `label` and `helpText` changes unless the origin is the core set. Rename, retire, reactivate and delete of a definition owned by core or an app are for its own set only. Platform tables, their fields and their namespace are never renamed, retired, purged or deleted. New definitions belong to the origin's layer. A new table must live in a namespace the origin owns, so the `core` namespace and installed apps' namespaces are reserved; fields, indexes, overrides and child classes may go onto app classes and `extensible` core classes, never onto platform tables. Test tables therefore live in a local `site` namespace (`schema-support.ts`).

### Recovery

- A new coordinator, once it holds `SCHEMA_KEY`, first resumes change sets left `applying` (getting the lock proves their coordinator is gone), then refuses with `SchemaNeedsAttention` (409) while any change set is `needs_attention`: its stored step statements name tables and columns as they were, and a rename or drop could invalidate them. Changes without DDL still apply.
- Resume probes each unfinished step (`done` recorded, `partial` cleaned up and rerun, `not_started` run), takes over the change set (`coordinator_pid`, failed steps back to `pending`), and completes it; a step failing 3 times sets `needs_attention`.
- `SchemaResumer` (a layer for the server process) and `std upgrade` call `resumePass`: a dedicated connection (`std-resumer`, with the keepalive startup parameters) tries `SCHEMA_KEY` at startup and every `resumeInterval`, resumes `applying` change sets and releases the lock.
- Abandon first refuses unless the change set is still `applying` or `needs_attention` (`SchemaChangeNotOpen`). It then runs each unfinished step's abandon action and `complete` with final state `abandoned`. After it, the catalog matches the definitions or the enforcement state explains the difference: an unfinished `create_index_concurrently` has its index dropped concurrently (enforcement `failed`, index absent); an unfinished `drop_index_concurrently` is finished with `DROP INDEX CONCURRENTLY IF EXISTS`, which also removes an index a failed drop left invalid (the definition is already a tombstone); an unfinished `validate_constraint` has its `NOT VALID` constraint dropped inside the `complete` config commit under the lock budget, never outside `CONFIG_KEY` (enforcement `failed`); `validate_override` has nothing physical (enforcement `failed`).
- If `SCHEMA_KEY` is held, abandon terminates a backend only when one statement finds, at the moment it signals, that the backend is running a step of this open change set (step `running` with that backend PID), is the backend that started the step (`backend_start` not later than the step's `started_at`), and holds `SCHEMA_KEY`. A PID the journal only remembers is never enough: a coordinator that resumed this change set and moved on to its own is not touched (review round 1). Otherwise `SchemaBusy`.
- The watchdog runs on the pool beside each step and writes `Watchdog: waiting N s in phase "..." for PIDs ...` into the step's `last_error`; status also shows the PIDs live. It never cancels. Metrics are not wired yet.
- The coordinator calls the `StepBoundary` hook at `committed`, `before:<n>:<kind>`, `after:<n>:<kind>` and `before:complete`; production installs nothing.

## Change sets over HTTP (item 9)

- `@std/api/schema-changes`: `POST /api/v1/schema/change-sets` (`{ operations }`, 201 with the change set's ID, state, revisions and journal entries) and `GET /api/v1/schema/change-sets/{id}` (the journal entry and its steps). `changeSetErrors` lists every refusal with its status: `DefinitionInvalid` 422, `DependencyConflict`, `UseRetireOrPurge`, `PurgeRefused`, `ExistingDataViolates` and `SchemaNeedsAttention` 409, `DefinitionProtected` and `PermissionRequired` 403, `SchemaBusy` and `SchemaLockTimeout` 503. The definition model's errors keep their classes (annotated with `HttpApiSchema.status`); the schema engine's are mapped to API forms that name no session (`server/http/change-sets.ts`). `@std/api` now depends on `@std/definitions`, as architecture.md allows.
- **Authorization.** The `Actor` from the session is the requester. Its access rules must allow, without condition, the record action each operation stands for on the definition table of its kind (create, update, or delete for deletes and purges), and for creates and updates the field action on every column the operation writes (a rename writes `name`, a retire or reactivate `state`, a replaced override what differs); a conditional decision counts as refused; otherwise `NotAllowed`. The check runs twice: in a request transaction while the operations are built, and again in the change set's main transaction (`ChangeSetRequest.authorize`), against the snapshot held under exclusive `CONFIG_KEY` and before any write, together with the session check and the stated-revision check of 6.4: for generic writes the written columns, for the change-set endpoint each operation's definition table and written columns (`checkChangeSetRevision`; a malformed header is `400 InvalidSchemaRevision` first). `authorize` returns the requester as re-authenticated there, with the roles held now, and the engine's permission checks (`schema.purge`) use it on every commit attempt (review round 3). The journal is readable by whoever may read `core.schema_change` unconditionally; anyone else gets `NotFound`. The schema service's own checks (1.7, 1.8, `schema.purge`) then apply to the same requester.
- **Generic writes to definition tables** (`server/http/definition-writes.ts`). `POST`, `PATCH` and `DELETE` on `core.namespace`, `core.class`, `core.field`, `core.field_override`, `core.index`, `core.role`, `core.permission`, `core.role_permission`, `core.access_rule` and `core.subscription` are routed before any request transaction would write: a short request transaction authenticates, resolves the table and authorizes; the operations then run as one change set on the change-set path (`CONFIG_KEY` exclusive first, `SCHEMA_KEY` before it for DDL), never inside a request transaction; a last request transaction reads the record back at the new revision. The body uses the table's columns: `POST` creates a local definition with a `uuidv7()` ID; `PATCH` turns `name` into a rename, `state` into a retire or reactivate, the rest into an update (an override is replaced whole); `DELETE` is the `delete` operation. Owner, protection, enforcement and system columns are read-only (`ValidationFailed` with `ReadOnlyField`), unknown columns `UnknownField`.
- **Order of checks.** The protected-definition guard now runs before the "property cannot be changed here" check of `update`, so every change but label and help text on a protected definition is `DefinitionProtected`.
- **Retired fields and tables in the record service.** The read compiler leaves retired fields out of the default selection; an explicit `fields=` selection returns them under access rules. The save pipeline refuses writes to retired fields with `DefinitionRetired` (already there) and every create, update and delete of a record whose concrete class or an ancestor is retired with `NotAllowed`.
- **Resumer.** `std serve` provides `SchemaResumer`, so each server process tries `SCHEMA_KEY` at startup and every `STD_SCHEMA_RESUME_INTERVAL`.
- **Acceptance tests** (`schema-http.test.ts`): the endpoints and their authorization; protected definitions through the generic API and the change-set endpoint with an unchanged catalog fingerprint, and a label change that changes no catalog object; `DELETE` of a field definition refused with data unchanged; two concurrent access-rule edits through the generic API at consecutive revisions; one revision per request (header, body revision and the fields of every laptop) under mixed reads and creates on `acme.asset` and `acme.laptop` while 50 change sets commit, with no 5xx; a retired field hidden by default, returned when selected, refusing writes, inserts without it succeeding, and optional with its value intact after reactivation.
- **History of definition records.** Every definition row a change set creates or changes gets one `core.change` entry at its new version, in the main transaction, through the records' change-entry writer (operation ID, actor, `api` cause, or `system` for set loads). Its schema revision is the one the main transaction commits, passed explicitly: the entry's field IDs are read at that revision (4.4), which also holds for the core set's first load, whose fields are created by that same change set. The fields are the platform table's columns keyed by the core set's field IDs. A delete or purge leaves a tombstone row, so it is an `update` of `state`. Platform tables carry no subscriptions (1E refuses them), so no delivery rows follow.
- **One request check, everywhere it validates (review round 4).** The request's checks (session, stated revision, access rules, target visibility) are the change set's `authorize` hook, and run against the same snapshot at every point that validates the operations: the request transaction, the read that plans layer writes (`readCheckedInstalledState`), each in-memory application before the main transaction (`validate`, also under `SCHEMA_KEY`), and the main transaction. So no version conflict, unknown definition, dependency or planning refusal about a target reaches a caller who may not see it or whose stated revision no longer holds, and a version reported is read in that checked transaction. On the generic path a hidden or missing target is `404 NotFound` (checked before its version, `VersionConflict` otherwise); on the change-set endpoint every target, and every definition a create references, that is hidden is refused exactly like a missing one (`422 DefinitionInvalid`, `unknownDefinition`), after the access rules, which treat hidden targets as missing. A tested hook (`StepBoundary` label `definition-write:prepared`) lets a test commit between a generic write's checks and its change set.
- **Coverage of the shared check (review round 5).** Preflight scans outside `CONFIG_KEY` (existence, violations, purge counts) end in a refusal only after the check ran again at the then-current snapshot; its refusal wins, so no count or sample ID of a target hidden meanwhile escapes (`StepBoundary` label `before:preflight` for the test). The definitions an operation needs to see are its target plus `referencedIds` of the definition as it would be after the operation (a create's draft, an update's merged result): the same edge extraction the dependency index uses, plus a class's namespace, so access-rule target fields, condition fields and references an update introduces or keeps are covered, and a new reference kind is covered as soon as the index records it (`schema-http.test.ts` walks every `DEPENDENCY_KINDS` entry). The stated revision's identity (does this database have it) is checked first, without looking up any target (`checkRevisionIdentity`, `SchemaChanged` with no change listed); the per-table 6.4 checks run only for visible targets.
- **Review round 6.** Generic updates check the references of the merged record too (`checkTargetsVisible` after the target's visibility and version, in the request transaction and in every later check), so both HTTP paths run the same reference check; `schema-http.test.ts` walks every `DEPENDENCY_KINDS` entry through the change-set endpoint and through generic PATCHes, and hides a role between a PATCH's checks and its change set. A revision this database does not have is `SchemaChanged` listing `unknown` entries for every scope that needs no target looked up (a create's table and written columns, the same entries as the equivalent generic create) and for visible targets' scopes; hidden and missing targets add none.
- **Review round 7.** A create's 6.4 scope comes from its payload alone; only a replaced override, whose target is checked visible first, is compared with the stored record, so an ID colliding with a hidden definition looks like a fresh one. Stale scopes list each class and field once: a field both written and required without a default merges into one entry with the kinds of both (this also removes duplicate entries from generic creates, present since 0C).
- **Review round 8: one rule for reads.** No stored value of an ID is read for any purpose (kind, scope entries, written columns, merged references, access columns) until that ID passed the visibility check against stored state. An ID an earlier operation of the same batch creates is payload-only: its kind, columns and merged state come from that operation's draft (`BatchView` in `http/change-sets.ts`), never from a stored record with the same ID. The check also looks at an operation's target before the references read from it. `schema-http.test.ts` holds a combinatorial test: every operation kind of `OperationSchema` (checked against the schema at run time, and by the compiler through a record keyed by the operation tags) × target or own ID (new, created earlier in the batch, hidden, missing) × references (visible, hidden, missing) × stated revision (current, past, future, unknown) × both HTTP paths where the kind is reachable through generic writes; every hidden/missing pair must be byte-identical with IDs substituted and commit nothing (156 pairs and 36 collision checks, about 350 requests on one database, about 2 s).
- **The ID space is the one exception.** A change set that creates a definition under a client-chosen ID a stored definition already has is refused by the engine (IDs are never reused), while the same change set with a free ID goes ahead. Under a revision this database does not have both are refused first and look alike; under a known revision the matrix checks only that the colliding case is refused and commits nothing. Client IDs are random UUIDs, so this tells a caller only about an ID it already holds. Decided (coordinator, review round 8): an accepted leak, no API change; client-chosen IDs stay, because a batch refers to its own new definitions and scripts converge on rerun. See Contracts 1.1 (client-chosen IDs; an ID in use, hidden or a tombstone, is refused) and 3.6 ("Accepted leak: a create with a client-chosen ID that a hidden definition holds").
- **Review round 9: occupancy first.** `@std/definitions/occupancy` checks every client-chosen create ID (every create and every `setOverride` without a version) for occupancy only, a boolean per ID against the snapshot, which holds every definition, override and tombstone. The HTTP request check runs it right after the revision-identity check and authorization, before the layer planner (`planLocalEdits`) and the engine; the engine runs the same check before its first operation, for every other caller. One refusal: `DefinitionInvalid` with `idInUse`, naming the operation's index and the caller's own ID, identical for any occupant. The planner's shipped-override check applies only to replacements, and the engine's `alreadyExists` is left for IDs created twice in one batch. The matrix's cases are required (every branch, `"none"` or `"unreachable"` where a kind has no such form), and the test compares the set of coverage tuples it ran (tag × ID state × references × revision × path) with the set derived from the cases and the dimensions. An occupied-ID test sends a create, a create followed by a delete or an override replacement, and an override without a version, against a hidden field, a hidden role at version 2, the hidden shipped acme override, a tombstone and a visible role, under the current and a past revision: one response for all of them, and nothing commits.
- **Review round 10: coverage from product facts.** What each operation tag supports comes from the product, not from the test's cases: create and target forms and the created kind from `OPERATION_FORMS` (`@std/definitions/operation`; the engine takes created kinds from it, and occupancy its client-chosen IDs), whether the created kind refers to others from `REFERENCING_KINDS` (`dependenciesOf` uses it), and generic reachability from the routing code itself (`createOperation` on every definition table, `updateOperations` on a stored definition of every kind for probe bodies, `deleteOperation`, all exported from `http/definition-writes.ts`). Each case must state exactly those facts, and the expected coverage set is computed from the facts and the dimensions alone.
- **Review round 11: the matrix's metadata is product code.** Generic PATCH dispatch is table-driven: `updateOperations` reads `PATCH_FIELD_OPERATIONS` (`name` → rename, `state` → retire or reactivate) and `PATCH_OTHER_OPERATIONS` (update, or an override replaced whole), so no dispatch exists without an entry; the matrix builds its PATCH probes from that inventory and asserts they reach every tag it can emit. `OPERATION_FORMS` is checked against the operation schema by its type (`FormOf`: a `definition` makes a create, versionless when the tag has a `version`; an `id` or a `version` makes a target), and the HTTP visibility check takes an operation's stored target from it (`storedTargetId`).
- **No-op updates keep their version.** The layer planner keeps an update of a shipped definition even when its effective value does not change, so the engine checks its version and a stale precondition fails the whole batch.
- **Errors on the generic path.** A definition the caller cannot read is `404 NotFound`, like an unknown ID, checked before the version and every other error that depends on the record (3.8). A stale `If-Match` is `409 VersionConflict` with `currentVersion` (checked before the change set and mapped from a lost race); the fixed endpoint keeps the change set's `DefinitionInvalid` with a `versionConflict` problem. `SchemaBusy` and `SchemaLockTimeout` are 503 with `Retry-After` (the holder's `retryAfterSeconds`, 5 s for a lock timeout) on both paths.
- **Retired tables.** The save pipeline refuses writes to a retired table's records after the visibility check, so a record the caller cannot see stays the identical `NotFound`.
- **Retired fields stay optional.** `update { required: true }` and an override with `required: true` are refused while the field is retired; reactivate it first.

## After merging 1C (authorization on every path)

- **Platform-table guard.** Generic writes on definition tables are routed to one-operation change sets in `http/handlers.ts` before the record service, so 1C's save-pipeline guard now sees only the other platform tables (the journal, `core.change`, the config-layer tables), which stay `NotAllowed` for every caller.
- **1C tests updated to the contract.** `platform-tables`: an admin's generic writes on `core.access_rule` and creates on definition tables are change sets now (an empty or partial body is `400 InvalidRequest`; an edit or delete of a protected rule `403 DefinitionProtected`), while `core.change` and the other platform tables stay `403 NotAllowed`. `built-ins`: generic edits and deletes of the protected built-in rules are `403 DefinitionProtected`, as its own comment anticipated. `error-fuzz`: its hierarchy moves from the `acme` namespace to the local `site` namespace, because app namespaces are reserved for their sets (1.8). `no-bypass` and `platform-tables` rule drafts gained `name: null` (migration 0006).
- **Rules on platform tables are core rules.** 1C applies only core-layer rules to platform tables and refuses local ones naming them, so the 1A tests that hide definitions from admins create their deny rules as the core set (`asCoreSet`).
- **Permission by ID.** `schema.purge` is checked through `SCHEMA_PURGE_PERMISSION_ID`; its name in `PermissionRequired` comes from the permission definition, so no source mentions the name (`no-bypass` scan).

## Verified facts

- SIGKILL of a coordinator process at each of the ten step boundaries of a change set with `validate_constraint`, `validate_override`, `create_index_concurrently` and `drop_index_concurrently` steps, and during a concurrent index build waiting on a writer, always ended `completed` after `resumePass`, with the catalog matching the definitions (`schema-interrupted.test.ts`). During the build the killed client's backend kept running and held `SCHEMA_KEY`, so `resumePass` did nothing until the build ended (0007 probe 2, now on the real engine).
- An idle-in-transaction writer blocking a concurrent build is reported by `pg_blocking_pids` while the build waits in phase `waiting for writers before build`; the watchdog names its PID and the build completes once the writer commits.
- A duplicate committed during a unique build makes every attempt fail; after 3 the change set is `needs_attention` with an invalid index; abandon drops it, sets enforcement `failed` and takes one revision; resume after deleting the duplicate completes it with a valid index.
- Renaming a column keeps index expressions and the index's generated name; renaming a schema keeps every table.
- Retiring a required field: `attnotnull` false after `DROP NOT NULL`, values kept, inserts without the column succeed.
