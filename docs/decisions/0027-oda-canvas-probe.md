## What the probe does

`deploy/oda/probe/probe.sh` runs five phases. Each runs as `probe.sh --phase <name>` under `timeout` (which also kills the phase's descendants), with its own limit cut to what is left of an overall budget (`PROBE_BUDGET_SECONDS`, 5,100 s in the workflow), and is logged to `logs/<phase>.log`. A failed or timed-out phase stops the probe; later phases are recorded as skipped. **Nothing retries** (`curl --retry 0`, one `helm install` each), because the probe measures the true failure rate; the Step 5 workflow adds the two infrastructure retries of Contracts 13.6.

0. **Preflight**, before anything is created: the probe refuses to start (exit 2, no result) while any kind cluster, any cloud-provider-kind container or any cloud-provider-kind process exists on the Docker host. cloud-provider-kind v0.10.0 has no way to limit itself to one cluster: it lists every kind cluster through Docker, starts a cloud controller for each, and when it stops it deletes every container carrying its label, for any cluster (`pkg/controller/controller.go`, `Run` and `cleanup`, at v0.10.0). Run beside another kind cluster, it would serve that cluster's LoadBalancer Services and delete their load balancers. There is no opt-in to share a host [judgment]; a GitHub runner starts empty, and a developer runs the probe on a host without kind clusters. The limitation that remains: a kind cluster someone creates on the same host while the probe runs is not protected.
1. **`tools`** (limit 600 s): downloads kind, kubectl, Helm, cloud-provider-kind, the three Istio charts and the `canvas-oda` chart by pinned URL, checks each SHA-256, and checks that the Component CRD inside the chart is byte-identical to `deploy/oda/crds/oda-component-crd.yaml`.
2. **`cluster`** (720 s): `kind create cluster` with the pinned node image (`--wait 600s`), with its kubeconfig in the probe's state directory, then starts cloud-provider-kind in its own session (`setsid`), so the phase's `timeout` leaves it running after the phase succeeds.
3. **`istio`** (1,500 s): `istio/base`, `istio/istiod` (`--wait`) and `istio/gateway` (`--wait`, labels `app=istio-ingress`, `istio=ingressgateway`, namespace `istio-ingress` with sidecar injection), the commands of the Canvas's installation guide (its CI leaves out the gateway's `--wait`), installed from the pinned chart archives instead of a Helm repository, each with `--timeout 600s`, then waits up to 5 minutes for the ingress Service's load-balancer address.
4. **`canvas`** (2,400 s): `helm install canvas canvas-oda-1.2.5.tgz -n canvas --create-namespace --set preqrequisitechecks.istio=false --set canvas-vault.enabled=false`, without `--wait` (the Canvas's post-install hooks would deadlock), with `--timeout 1200s` for the hooks; then every Deployment in `cert-manager` and `canvas` must be `Available` and every StatefulSet in `canvas` rolled out (600 s each), except the secrets-management operator (below).
5. **`component`** (1,020 s): renders the stub chart, validates it on the live API server (`kubectl apply --dry-run=server`, which runs the CRD's schema, formats, CEL rules and the Canvas's webhook), installs it into `components` and polls the Component's `deployment_status` every 5 s, recording each transition, until `Complete` (900 s at most).

After a successful run it also requests the exposed API's `openapi.json` through the Canvas gateway at the URL the Canvas published (`status.coreAPIs[0].url`), within 180 s. That observation is recorded but does not decide the outcome: the gate's measure is `Complete`, and the gateway is the Step 5 workflow's first assertion. Every `kubectl` read that is not a wait gives up after 20 s.

**Finishing.** Whatever happened, the probe first writes a partial result (`stage: "partial"`), then on failure collects diagnostics (bounded to 300 s: every resource, recent events, the pods that are not ready and the logs of the component, API and identity operators, in `logs/diagnostics.log`), then writes the complete result (`stage: "complete"`), then cleans up (each Docker and kind command bounded), then adds the disk after cleanup. Each write goes to a temporary file that `jq` checks (schema version, outcome, phases, commit) before it is renamed over `result.json`, so a reader never sees a truncated file. If the complete result cannot be written, the probe exits 3 and the job fails, whatever the deployment's outcome; otherwise it exits 0 for `Complete` and 1 for a failure. With the budget, diagnostics and cleanup bounded, a run ends by about 103 minutes, leaving the upload most of the job's 120.

**Cleanup deletes only what the run created.** The cluster is deleted only when every node container labelled with its name was created after the preflight (which found no kind cluster at all), so a name that already existed, or that someone reused, is never deleted; ownership is checked from Docker's creation times, not assumed from a flag set before `kind create`. A cluster whose creation was cut off by its phase limit is still found and deleted. cloud-provider-kind is stopped through its recorded PID (and waited for, so it creates nothing more), then any load-balancer container labelled with this cluster is removed, and the `kind` network is removed when this run created it and nothing else uses it.

**Disk** is sampled every 2 s in the background (`df` on the root file system) from the preflight to the end, so `disk.peakUsedBytes` and `disk.minAvailableBytes` are the real extremes at that interval, and each phase records its own peak; the samples of the cluster's lifetime cover image pulls inside the node. The kind node's own footprint, which does not depend on what else uses the disk, is measured once at the end, before deletion: its image, its container's writable layer, and its `/var`, a Docker volume in kind that holds the pulled images, etcd and the logs.

`result.json` (schema version 1) also holds: the outcome and the failed phase with the last 60 lines of its log; each phase's start, duration, limit, whether it timed out, exit code and disk; the component's status transitions; the runner (`ImageOS`, `ImageVersion`, OS, kernel, CPUs, memory); the version of every tool, the Kubernetes server included; every pin with its checksum; provenance (repository, run ID, run attempt, commit, and the SHA-256 of the probe script and of the stub chart's files); and every container image the cluster ran, with the image ID it resolved to.

The workflow `oda-canvas-probe` runs the script on `ubuntu-latest`, `workflow_dispatch` only (Contracts 13.6: the Canvas runs nightly and on release candidates only from Step 5), `timeout-minutes: 120`, `permissions: contents: read`, no concurrency group (dispatching 10 at once gives 10 runners). It uploads `result.json` and the logs whatever the outcome, as one artifact per attempt, `oda-canvas-probe-<run id>-<attempt>`, so a rerun never replaces an earlier attempt's result, and the job fails when the probe fails.

**The summary** (`pnpm oda-probe:summary`) counts **attempts**, not runs: every attempt of every selected run is one probe, so a rerun that succeeds never hides the attempt that failed before it [judgment]. It selects the last `--runs N` (10) completed runs of the workflow on `--branch` (main by default), optionally of one `--commit`, or exactly the runs given with `--run-id`, and downloads each attempt's artifact with `gh`. An attempt counts as a failure, with its reason in the summary, when its result says so, when it left no artifact (cancelled, killed by the job limit, or failed before the upload), when its `result.json` cannot be decoded (the summary goes on with the other attempts), or when the result's run ID, attempt or commit differs from the attempt it was downloaded for. The table shows each attempt's commit and configuration (a short hash of the probe script's and stub chart's hashes and the pins); attempts that ran different configurations are refused unless `--allow-mixed`, which marks the summary as not comparable. Attempts of different commits with the same configuration are listed but not refused. `--from` summarizes local result files instead, without the provenance check.

### Why a shell script [judgment]

The probe orchestrates CLIs (kind, Helm, kubectl, Docker), and its numbers include the runner's disk. A TypeScript probe would need Node and `pnpm install` on the runner first, which costs minutes and about a gigabyte that the measurement would then have to subtract, and the same script must run unchanged on this machine. So it is one Bash script (shellcheck-clean, `set -euo pipefail`, `inherit_errexit`) that needs only bash 5, curl, sha256sum, tar, coreutils `timeout`, util-linux `setsid`, jq and Docker, all on the runner image. The summary, which runs on a developer's machine, is TypeScript under `tooling/` like the other tooling.

## The stub component

`deploy/oda/probe-stub/` [judgment on the location: `deploy/oda/` is where the architecture puts the ODA chart and Canvas workflow inputs; the real chart is `deploy/oda/std/` in Step 5]. A Helm chart whose templates have no Helm directives, so the files are what `helm template` renders and the schema check below needs no Helm. Its names are fixed (`std-probe`), so one stub fits a namespace; it is installed into `components`, the namespace the Canvas creates and watches.

- **Component** (`oda.tmforum.org/v1`): `componentMetadata` `id` `STD-PROBE`, `name` `std-probe`, `functionalBlock` `Production` (as Contracts 13.1 chooses for STD); one `coreFunction.exposedAPIs` entry, `probe` (`id` `STD-PROBE-API`, `apiType` `openapi`, `apiSDO` `STD`, `implementation` `std-probe-api`, `path` `/std-probe/probe/v1`, port 8080, one `specification` whose URL is the document the stub itself serves, by its in-cluster Service address [judgment: the stub has no published specification]); no dependent APIs, no management or security APIs, no events; `securityFunction.canvasSystemRole` `canvas_system` (the name Contracts 13.2 gives STD's) and two static `componentRole` entries, `probe_reader` and `probe_admin`.
- **The API**: busybox `httpd` from the official image `docker.io/library/busybox:1.38.0`, pinned by its multi-platform index digest `sha256:fd7dc98638c8e305f4dc34e979f1c0fdfdcaeb0fbf8fcff77ae834b6da3d7e6e`, serving a 20-line OpenAPI 3.0 document from a ConfigMap at `/std-probe/probe/v1/openapi.json`. It runs as `nobody`, read-only, with no capabilities, no service-account token and a readiness probe on that path. Istio adds its sidecar.

What `Complete` takes in canvas-oda 1.2.5 (read in the component operator's source at the tag): every exposed API has a URL and a ready implementation (the Istio API operator builds the URL from the ingress's load-balancer address and marks the API ready when the Service has a ready endpoint), the identity operator has configured Keycloak (`identityConfig.identityProvider` set), and there are no secrets-management or dependent-API requests left. Static roles need no TMF672 or TMF669 API: the component operator copies `componentRole` into the `IdentityConfig` (TMFOP003). IG1171 v5.0.0 describes the same split of a component into core, management and security functions with exposed and dependent APIs; the probe relies only on the Canvas's CRD and operators, not on the guide.

### `oda-component-schema` for the stub

`pnpm check:tooling` now runs `tooling/check-oda-component-schema.ts`: the stub's Component must validate against the `v1` schema of the pinned CRD, which must be served and the storage version. The validator (`tooling/lib/structural-schema.ts`) handles the keywords that schema uses (`type`, `properties`, `required`, `items`, `enum`, `minItems`, `x-kubernetes-preserve-unknown-fields`, `x-kubernetes-validations`, and the descriptive ones) and is stricter than the API server in one way: a field the schema does not declare fails, where the server would silently drop it. The schema is decoded with Effect Schema and `onExcessProperty: "error"`, so a keyword it does not handle fails the check, and the CRD's two CEL rules (an exposed API names `apiType`, `implementation`, `path` and `port` at its root or in its first specification; a dependent API names `apiType`) are evaluated by matching their exact text, so a changed rule fails the check instead of passing unchecked. A string's `format` is checked as a Kubernetes 1.30 API server checks it (`tooling/lib/kubernetes-formats.ts`): the 24 formats apiextensions-apiserver v1.30.0 lists in `supportedFormats`, normalized by removing `-` (so `date-time` is `datetime`), ported from kube-openapi's `strfmt` at the version Kubernetes 1.30.0 pins (70dd3763d340) and the govalidator checks it calls; a `publicationDate` that is not a date-time fails. Formats outside that list, such as the CRD's `url`, are dropped by the API server before validation and check nothing here either. Where Go's parsers (`net/url`, `net/mail`, `net`, `time`) do more than a pattern, the port follows their rules closely but not byte for byte; the probe's server-side dry run stays the authority. The probe's server-side dry run checks the same component against the real API server, CEL included. It cost one root dev dependency, `yaml` 2.9.1, already in the lockfile as a transitive dependency. Step 5 (5O) replaces the stub's check with the rendered real chart and the 11.1 path and URL rules.

`deploy/oda/crds/oda-component-crd.yaml` is the CRD byte for byte (Apache-2.0; `deploy/oda/crds/NOTICE` gives the source, chart and file hashes). It is a Helm template, so `oxfmt.config.ts` and `lefthook.yml` exclude that directory from formatting, as they exclude `repos/`.

Differences from upstream, each a [judgment]:

- **Istio 1.26.3 for all three charts.** Upstream pins only the gateway chart and installs `base` and `istiod` unversioned, so its control plane is whatever Istio released last (1.30.7 on 2026-10-22), paired with a 1.26.3 gateway. Every Istio release that supports Kubernetes 1.30 (1.22 to 1.28) is past its end of life on 2026-10-22; 1.26 ended on 2025-12-22. That is a consequence of the Canvas's Kubernetes 1.30 ceiling, and a Step 5 risk (below).
- **cloud-provider-kind as the release binary**, checked by SHA-256, instead of `git clone --branch v0.10.0` and `make` (same version; no Go toolchain or build time in the measurement).
- **The released chart, not the Git checkout.** `trigger_tests.yml` installs `./charts/canvas-oda` from its own checkout after `helm dependency update` (it tests the Canvas's `main`); Contracts 13.5 pins the released chart, which upstream's release workflow and installation guide install from the chart repository. - **`preqrequisitechecks.istio=false`** (sic, the chart's key), as both upstream workflows and the guide's kind section set it, even though cloud-provider-kind gives the ingress an address before the Canvas is installed.
- **Readiness without the secrets-management operator.** With Vault disabled, `canvas-smanop` stays in `CreateContainerConfigError`, as the installation guide says; components that request no secrets management are unaffected. The probe waits for every other Deployment and StatefulSet. Seen in every local run.
- **Waits.** Upstream sleeps fixed times (30 s, 90 s) and then lists resources; the probe waits on conditions, each bounded, inside per-phase limits and an overall budget (above).

Findings from the local runs:

- The Canvas came up and the stub reached `Complete` in every run, with its API answering 200 through the Canvas gateway at the published `https://<ingress address>/std-probe/probe/v1` URL.
- `canvas-smanop` is in `CreateContainerConfigError` with Vault disabled, as expected.
- The `canvas` phase is nearly all of the bring-up, and it varied from 167 s (first run) to 281 s. - **Disk is the tight resource.** The node's `/var` alone held 10.1 GB with the Canvas and the stub, before STD's image, its database and the CTK containers. Decision 0021 notes about 14 GB free on a public runner's root file system; the GitHub runs will show the real free space and peak.

## What this means for Step 5 (to confirm with the GitHub results)

- **Timeouts and retries.** The Step 5 workflow's per-phase limits and its two infrastructure retries (Contracts 13.6) should come from the p90 and max above, and the failure phases tell whether retrying the cluster, Istio or Canvas install is the right budget.
- **Disk.** Contracts and decision 0021 note 14 GB of free disk on a public runner against the Canvas's documented 50 GB; the measured peak, and the kind node footprint, say whether STD's image, the CTKs and their containers still fit, or whether the workflow must free disk first.
- **Docker Hub.** Each run pulls about 18 images from Docker Hub anonymously. Rate limiting would show as image-pull failures in the `canvas` phase.
- **End-of-life Istio.** The Canvas supports Kubernetes up to 1.30, and no Istio release that supports 1.30 is still maintained. Upstream works around it by running a current control plane on an unsupported Kubernetes version. Either way the Canvas's mesh in CI gets no security fixes; it is test infrastructure only, but the Step 5 docs must not recommend this combination for production.
