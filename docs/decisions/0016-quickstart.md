## The first administrator: `std bootstrap-admin`

Before this workstream, nothing created a user who could sign in. The core set creates only the system user, which never signs in (Contracts 3.1, decision 0014), and every other user is a `core.user` record that someone with access must create. Tests and `spike:demo` seed users through the save pipeline with `WriteAccess.allowAll` (`@std/testing/acme-fixture`), which is test code.

Decision: a CLI command, `std bootstrap-admin`, not an HTTP route and not a definition-set fixture.

- **What it does.** In one request transaction, as the system user, through the save pipeline (`createRecord`, with `WriteAccess.allowAll`, the production outbox hook points and scrypt), it creates an active `core.user` with a password and a `core.user_role` row for the built-in `admin` role (by ID, `BUILT_IN_ROLE_IDS.admin`). Both get change entries, and delivery rows if a subscription matches. Contracts 3.1 already reserves bootstrap for the system user.
- **Idempotent by login.** When a user with the login exists (compared like sign-in: NFC, trimmed, case-folded), it changes nothing: no new user, no password reset, no role change. So compose can run it after every `std upgrade`, and it can never take over or reset an existing account.
- **Settings.** `STD_ADMIN_LOGIN` (default `administrator`; not `admin`, because `no-bypass` refuses a built-in role name as a string in source), `STD_ADMIN_NAME` (default `Administrator`) and `STD_ADMIN_PASSWORD` (required, non-empty, read as `Redacted`). The password comes from the environment only, never from the command line, so it stays out of process listings and shell history. The server has no default password; only the quickstart's compose file and script carry a disposable demo one.
- **Refusals.** Before the core set is loaded: `AdminBootstrapRefused` (`coreSetNotLoaded`, "run std upgrade first"), exit 1. A missing or empty password: a configuration error, exit 1. Extra arguments: usage, exit 2.
- **Why not HTTP.** An unauthenticated route that creates an administrator is a backdoor for whoever reaches the port first. The CLI runs with the database owner's credentials, like `std upgrade`, outside the HTTP API: whoever can run it can already change every table.
- **Why not a definition set.** Users are data, not configuration (Contracts 3.1, 8.1); sets carry no data in v0.1 (8.4), and a password in a set file would sit in git.

## Compose

- `upgrade`: a one-shot service, `pnpm --silent std upgrade && pnpm --silent std bootstrap-admin`, after Postgres is healthy. `server`: `std serve`, with `depends_on: upgrade: condition: service_completed_successfully`, so migrations never run at server start (Contracts 1.9) and the server starts only after both commands exit 0. The server listens on `0.0.0.0:8080` in the container and is published on `127.0.0.1:${STD_HTTP_PORT:-8080}`; its healthcheck fetches the OpenAPI document.
- `postgres` is unchanged except that its host port is `${STD_POSTGRES_PORT:-54329}`, so a second stack can run beside the shared one (`docker compose -p <name>`). `docker compose config --hash postgres` is the same before and after this change, so the shared container is not recreated. `pnpm db:up` still starts only Postgres.
- Upgrades are offline (Contracts 8.5): a second `docker compose up` while the server runs makes `upgrade` refuse ("std-server sessions are connected") and compose report it. `docker compose down` (the volume stays) and `up` rerun the upgrade, which then changes nothing and finds the administrator.
- The image, `docker/quickstart.Dockerfile`, is a development image and deliberately minimal: `node:26.12.0-bookworm-slim` (the `devEngines` version, so pnpm downloads nothing), pnpm 12.14.0 (the `packageManager` version), the whole workspace minus `.dockerignore`, `pnpm install --frozen-lockfile --ignore-scripts` (the root `prepare` patches `tsc`, which the image never runs; lefthook needs git), and the `std` command run from its TypeScript sources as the root `pnpm std` script does. It is not the release image, which is Step 4D's (a built, smaller image with the web app).

## The script: curl and jq, not the typed client

`examples/quickstart.sh` uses bash, curl and jq against the HTTP API.

- After `docker compose up`, the host needs nothing from the workspace: no Node 26, no pnpm install. The typed client (`@std/api/client`, `HttpApiClient.make`) would turn the script into a wrapper around an Effect program that needs both.
- The script shows the wire format a reader would use from any language: the change-set payloads, `If-Match`, the filter text syntax, `labels`, `withheld` and history entries.
- Drift is caught by CI instead of the type checker: the script runs on every push (below) and stops with `FAILED` at the first unexpected response. Every request must be 2xx except the refusals it shows, and each of those must have exactly its status and error tag (`refused 400 UnknownField ...`). The facts it prints are asserted too (`expect`): the versions after each update, the value under the new field name, `notes` absent by default and present when selected, the `DefinitionRetired` error, how many records each user sees through each endpoint, that Bob sees only his own and never `cost`, and the versions and the `cost` key (Alice) or its absence (Bob) in the history (review round 1: a 500 in place of an expected refusal used to pass).
- **No credential in process arguments** (review round 1). Any local user can read a command line (`ps`, `/proc/<pid>/cmdline`). Request bodies reach curl on stdin (`--data-binary @-`), the session token through a header file (`-H @file`, from `mktemp`), and passwords reach jq on stdin (`printf '%s' "$password" | jq -Rsc '{..., password: .}'`); `printf` is a builtin and starts no process. The demo users' passwords can be set with `QUICKSTART_ALICE_PASSWORD` and `QUICKSTART_BOB_PASSWORD`.

What it does, each step under a heading: two change sets through `POST /api/v1/schema/change-sets` (the namespace, both classes, eight fields and the display field; then two roles and eight access rules modelled on Contracts 3.3: Alice manages every asset, Bob reads and renames his own and never reads `cost`); the users through the generic `core.user` and `core.user_role` routes as the administrator; two laptops and a plain asset added by Alice, then an update by each user for the history; a rename (`serial` to `serial_number`) and a retire (`notes`) as change sets, with the old name's `UnknownField`, the default selection without `notes`, its explicit selection and the `DefinitionRetired` refusal; each user's view of `/acme.asset` and `/acme.laptop`, and two refusals for Bob; the laptop's history as each user (fields under their current names, no `cost` for Bob); and `std doctor`, whose exit status the script exits with.

**Reruns.** Definitions carry fixed IDs in the script, as a definition set's would (Contracts 1.1), so a rerun finds them by ID: the two change sets, the users, the rename and the retire happen only when missing, and the rerun says so. Records are new on every run: each run tags its laptops with `QUICKSTART_RUN` (default: the UTC time), and lists, updates and history only show that run's records. So a second run converges for configuration and clearly adds uniquely named data. A user and its role assignment are two requests, so they converge separately: the user is created when its login is missing (an existing user's password is never changed), and the assignment when no `core.user_role` row joins that user and role, whether or not the user is new (review round 1: a run that stopped between the two left Alice without her role, and every rerun failed). Laptops are created with the field names as they are at the time (`serial` or `serial_number`, with `notes` only while it is active), read from `core.field` by ID.

The quickstart needs a database where the `acme` namespace is free: the `acme` app set (`examples/acme`, loaded with `std upgrade --set examples/acme`) reserves it (Contracts 1.8), and the first change set is then refused.

`std doctor` runs through `STD_DOCTOR_COMMAND` (default `docker compose exec -T server pnpm --silent std doctor`): doctor is a CLI command that reads the database directly (Contracts 1.10), not an endpoint.

## CI

- **`pnpm quickstart:ci`** (`examples/quickstart/src/ci.ts`, a workspace package because it needs `@std/testing`) is the `ci.yml` step "Quickstart", so `pnpm ci:local` runs it too. It needs no Docker: on an empty database from the harness (`testDatabaseService({ empty: true })`, dropped at the end or by the janitor), it runs `std upgrade` and `std bootstrap-admin` as child processes, starts `std serve` on a port the system picks (`STD_HTTP_PORT=0`, the address read from the server's "Listening on" log line), and runs the script twice with doctor through the CLI. Before the second run it deletes Alice's role assignment through the typed client (`@std/api/client`), so the rerun must complete a partial setup. Any nonzero exit fails the step; the server's log is printed only then. A run takes about 5 s.
  - **Passwords in arguments: an execve trace** (review round 3). CI sets random passwords for the administrator, Alice and Bob and runs each script run under `strace -f -qq -e trace=execve -e signal=none -s 1048576` (`exec-trace.ts`). `-f` follows every descendant, so the trace holds every program the script starts, whatever started it: a shell construct, a PATH trick, an absolute path, an interpreter or a changed `STD_DOCTOR_COMMAND`. Checking executions replaces two earlier attempts that a reviewer bypassed: PATH wrappers that logged commands started by name (round 1) and a static lexer over the script's text (round 2), which missed `case` arms, `function` bodies, `coproc`, backticks in arithmetic and arrays, substitutions in `${var:-...}`, `trap --`, partly quoted here-document delimiters, `export P""ATH=...`, a PATH name split by a line continuation, a rewritten `STD_DOCTOR_COMMAND` and unwrapped executables such as `python3`. The parser joins calls strace splits across lines (`<unfinished ...>`, `<... execve resumed>`) and decodes its C-escaped strings. A run fails when any argument of any execve holds one of the passwords, as is or JSON-escaped, or an `authorization: Bearer` header (the script's session tokens are its own, so the header is what is looked for); when any execve failed; when strace shortened an argument list; when an execve line does not parse; or when the trace lacks curl, jq or the doctor command (`node .../cli/main.ts doctor`), so an empty or broken trace cannot pass. Problems name the execve's number, the program and the argument's index, never the secret. The two real runs trace 186 and 134 execve calls with no failure.
  - **The trace log** holds every argument, so it is treated as sensitive: it lives in a new directory from `mkdtemp` (mode 0700), is created with mode 0600 before strace opens it (strace keeps the mode), and the directory is removed when the run's scope closes, on success, failure and interruption.
  - **Probes** (`examples/quickstart/test/exec-trace.test.ts`, CI step "Test"): each of the reviewer's bypass forms, a plain `jq --arg password`, `/usr/bin/env jq` and `python3 -c 'pass' "$STD_ADMIN_PASSWORD"` is planted in a copy of the script before its first request, followed by `exit 0`, and run under the tracer with no server: every one fails the check with "argument N holds a password", and no problem text holds the password. Controls: the same copy with nothing planted passes; a trace without curl and jq fails with "no execve of curl"; a failed execve fails naming the program; a JSON-escaped password is found; the log's modes are 0600 and 0700 and it is gone afterwards. A full run with `python3 -c "pass" "$STD_ADMIN_PASSWORD"` planted before the doctor step also fails `pnpm quickstart:ci` ("execve 184 (python3): argument 3 holds a password").
  - **Requirements: Linux and strace.** ptrace of one's own child works with `kernel.yama.ptrace_scope` 1, the Ubuntu default. Without strace, `pnpm quickstart:ci` fails at once with `StraceMissing`, which says to install it (`sudo apt-get install -y strace`); it does not skip the check. The `ci.yml` step "strace" installs it on GitHub (`sudo apt-get install -y strace`) and is a no-op outside GitHub Actions, because `pnpm ci:local` runs every `run:` step and must not call `sudo` on a developer machine.
  - **Process groups** (`process-group.ts`, review round 1). Each command (`std upgrade`, `std bootstrap-admin`, `std serve`, each script run) starts as the leader of its own process group (`detached`). When its step ends, by exit, failure or interruption, the scope's finalizer sends SIGTERM to the whole group (negative PID), SIGKILL after 5 s, and waits until no process of the group is left. Descendants (curl, jq, the doctor started by the script) are in the script's group. The database is dropped only after every group is gone, because the groups' scopes close first. `examples/quickstart/test/process-group.test.ts` interrupts a step whose shell has two background children, ends a group that ignores SIGTERM, and sends SIGTERM to `pnpm quickstart:ci` while the script's first curl hangs (a slow `curl` first on PATH); each checks, through an environment marker in `/proc/*/environ`, that no process survives.
  - **Cleanup limits and deadline** (review round 2). Membership and process states come from `/proc/<pid>/stat`, so the process-group code and its tests need Linux; the Ubuntu CI runner is. A zombie (state `Z`) counts as gone: it cannot run, and only its parent, possibly outside the group, can reap it (before, a zombie whose parent never reaped it kept the finalizer waiting). The wait after SIGKILL has a deadline (5 s); processes still running then are logged by PID and command name (never environment or arguments), and the finalizer fails with `GroupNotEnded`, so the run fails instead of hanging. The other finalizers still run, the database's included: it is dropped `WITH (FORCE)`, which ends any session a leftover process holds, so a stuck process cannot leak a database. Cleanup covers the processes still in the original process group, which includes everything the script starts itself (curl, jq, the doctor); a descendant that starts its own session or group (`setsid`, `setpgid`, Python's `start_new_session=True`) is not followed. Tests: a zombie in its own group whose parent never waits (`setsid sleep 0.1 & exec sleep 60`) is cleaned up in under a second, although signal 0 still finds it; a group whose members never go (a stubbed listing) fails with `GroupNotEnded` naming them within the deadline; and after that failure an outer finalizer still runs.
- **`.github/workflows/quickstart-compose.yml`** runs the real path on GitHub: `docker compose up --build --detach --wait`, the script twice, `docker compose down --volumes`. It does not run the argument check: the script runs on the host there, but the check is a TypeScript program the job would need Node and the workspace for, and the commands inside the container (the doctor) are not the script's descendants; the `ci.yml` step covers the check for the same script. It is a separate workflow because `pnpm ci:local` runs every `run:` step of `ci.yml`, and locally `docker compose up` for the project `std` would touch the Postgres container every checkout shares. Locally the compose path was tried as `std-quickstart-<random>` with other ports (`STD_POSTGRES_PORT`, `STD_HTTP_PORT`), then removed with its volume and images.

## Verified facts

- `docker compose up --wait` (Compose 5.6) treats the one-shot `upgrade` service that exited 0 as done and waits for `server` to be healthy.
- With `STD_HTTP_PORT=0`, `std serve` listens on a free port and logs it (`Listening on http://127.0.0.1:<port>`).
- Doctor on the quickstart's database, after both runs, reports only the informational check 13 (`notApplicable`) and exits 0.
- A rename leaves earlier history entries readable under the new name: the laptop's version 1 shows `serial_number` though it was written as `serial`.
