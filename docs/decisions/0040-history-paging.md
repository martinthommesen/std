# 0040. Bound history materialization before reconstruction

Status: accepted, 2026-10-23 (F6 remediation).

[judgment] One history selection interface (`page`, `entry`, `latest`) shares current-row authorization and SQL filter compilation: lists select at most `limit + 1` candidates, direct change-ID reads select one entry, and latest/predecessor/successor links seek one version each; only selected response entries reconstruct definitions, and ordinary resource responses use the latest selection without reconstruction. Separate operation functions were considered; sharing selection SQL keeps masks, deleted-record policy and snapshot consistency local to the history module.

[judgment] Every accepted history filter uses change metadata or currently readable changed-field membership and runs in SQL, so no post-reconstruction scan budget is needed; exact counts remain separate scalar aggregates over the same filter, offset requests retain their existing links, and explicit cursors/count opt into keyset links with `count=false` allowed to omit totals (TMF630 v5.0.0 Part 1 §4.5.1 pp.75–77, §4.5.3 pp.85–92, §12.4 p.238; Contracts 3.7, 4.5, 10.3–10.4). Unfiltered counts and deep offsets walk matching index entries; filters may require heap reads, but offset/limit select only `(record_id, record_version)` keys before full response rows are fetched and converted to text; neither arbitrary total caps nor event-list scan truncation from decision 0032 J10 is appropriate when these filters can run in SQL, and the existing `change_record_version` unique index from migration 0004 supports version seeks without another migration.
