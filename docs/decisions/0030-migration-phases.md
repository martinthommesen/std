# 0030. Migration phases and the Step 3 rolling-upgrade groundwork

Status: accepted for the Step 3 implementation, 2026-10-23 (3R). Contracts 8.8 remains a draft owned by Step 5; this decision implements its prerequisites, not its admission fence or phase execution.

## Migration metadata

Every `PlatformMigration` declares `phase: "expand" | "contract"`. The runtime rejects missing/unknown phases. Migration 0017 adds `core.platform_migration.phase text NOT NULL DEFAULT 'expand'` with a CHECK limiting it to `expand`/`contract`, and `core.delivery.min_worker_version text NOT NULL DEFAULT '0.0.0'`. The phase CHECK is added NOT VALID and then validated over the small migration ledger (at most 17 rows at installation), never the delivery table. Both defaults are constants: PostgreSQL can add these columns without rewriting existing rows. Transactional, concurrent-index and data runners record the declared phase; the first migrations run against a ledger without that column, so ledger readers synthesize `expand` until 0017 exists.

- **J1 [judgment]: historical metadata and checksums.** All migrations 0001–0016, including the data migrations 0012 and 0016, declare `expand`; the ledger default classifies their already-applied rows the same way. Their existing checksum inputs stay byte-for-byte unchanged. From 0017 onward the phase is also in the checksum, and comparison rejects a stored phase different from the declaration. The historical `expand` tag on a data migration does not make it run during expand: all data migrations belong to finalize under RU1/RU6 when Step 5 implements phase execution. Today the offline runner retains its schema → sets → data order.

## The `migration-phases` check

`pnpm check:tooling` evaluates the actual registered migration statements (including their generated SQL) and checks the migration-file inventory. `tooling/test/migration-phases.test.ts` runs the executable against the real list and JSON canaries in `tooling/canaries/migration-phases/`, including malformed-input and read-failure paths.

- **J2 [judgment]: reject recognized hazards and unrecognized top-level forms.** The check tokenizes SQL, with quoted literals, quoted identifiers, nested comments, dollar bodies and statement boundaries handled separately. It refuses unknown phases, destructive keywords (`DROP`, `RENAME`, `TRUNCATE`), type/nullability/storage changes, rewrite operations, nonconstant added-column defaults, generated/identity columns on existing tables, added NOT NULL columns without defaults, CHECK/UNIQUE/FK/primary/exclusion constraints on existing tables without `NOT VALID`, unique indexes on existing tables, non-concurrent indexes on existing tables, triggers on existing tables, and inheritance/partition attachments to existing parents. It accepts new tables and their own constraints, indexes, triggers and inheritance/partitions, nullable or constant-default added columns, new functions/types, concurrent indexes through the concurrent_index migration kind, enum values, comments and explicit constraint validation. Dollar signs belong to unquoted identifiers; dollar-body delimiters require an identifier boundary. E-strings and Unicode U& quotes are refused rather than partially decoded. Line comments end at CR or LF; nested block comments and comment markers inside strings are tokenized separately. It refuses unrecognized statements/actions, including DO/CALL and direct data rewrites. A CHECK or FK with `NOT VALID` still constrains future writes: the author must prove old writers satisfy it. `NOT VALID` is not a compatibility proof.
- **J3 [judgment]: functions need new names.** Every `CREATE OR REPLACE` is refused in expand, even with an apparently identical signature/body. Reusing a function name already introduced by an earlier migration is refused, including overloads and quoted/unquoted equivalents. This deliberately requires a new name instead of attempting to prove PL/pgSQL equivalence.
- **J4 [judgment]: frozen pre-rule exceptions.** The check admits the existing 0001 config-state initialization, 0003's exact session-revocation function and body tokens, 0011's inline check on its new defaulted ledger-state column, and 0014's finished-at backfill. These are narrow historical statement exceptions; they do not authorize new migrations to copy them. Applied SQL is not rewritten merely to pass a new static rule.

**Blind spots.** This is a SQL surface check, not PostgreSQL's parser, an interpreter or a database compatibility proof. It cannot establish the meaning of arbitrary function/trigger bodies, user-defined casts/types/operators, functions called by SQL expressions, whether old application code still uses an object, old writers' allowed values, lock wait duration, table size, actual plans, concurrent data behavior, or the release gap before a contract removal. Direct destructive SQL, DELETE/UPDATE/INSERT/MERGE/COPY, and dynamic EXECUTE/CALL in function bodies are refused (apart from J4's frozen 0003 function). Ordinary quoted strings assume PostgreSQL's standard_conforming_strings=on default. This is not a fail-closed semantic SQL checker: recognized CREATE forms can contain expressions and constructs it does not understand. String literals and the behavior of functions called by a new function or trigger remain opaque; they can still have destructive behavior when later invoked. The check does not prove data migration batching/idempotence, set-version separation or RU11 feature admission. PostgreSQL integration tests, review, and Step 5's expand/rolling compatibility tests remain required. Unsupported syntax must be expressed in a supported form or gain a reviewed checker rule; it must not be hidden in dynamic SQL.

## Tolerance and diagnostics

- **J5 [judgment]: preserve opaque rows.** The layer loader skips unknown `config_base.kind` rows before decoding their payloads, logging each unknown kind once per load (load-local state, with no process-global mutable set), and omits their overrides from the older release's in-memory view. The catalog already selects only known definition tables, so the change-set validator sees only those kinds. Unknown rows and overrides remain in the database. Rebuilding a known definition's dependency edges deletes only known dependency kinds, preserving unknown ones even when attached to a changed known definition. Doctor skips interpretation of unknown payloads/hashes, reports unknown config/dependency kinds as information and does not treat their edges as dangling or extra.
- **J6 [judgment]: the `core` namespace belongs to the platform.** An unknown table there is an informational `newerPlatformTable`; orphan tables in application namespaces retain their warnings. Known tables' missing or changed columns, constraints and indexes remain drift. An unknown ledger migration still fails startup/doctor: relaxing that is part of Step 5's admission protocol, not RU12 row tolerance.

## Connections and deliveries

Server, worker, CLI, coordinator and resumer application names use the single package-version source (`STD_VERSION`), as `std-server@<version>`, `std-worker@<version>`, `std-cli@<version>`, `std-coordinator@<version>` and `std-resumer@<version>`, through one shared helper. Upgrade checks match the server/worker prefixes at the `@` boundary and also recognize the exact legacy unversioned names. CLI sessions never block upgrade merely by name. Diagnostic lock reports retain the complete application name.

- **J7 [judgment]: release version format and source.** `packages/server/package.json` is the sole STD release-version source; main now declares `0.0.3`, and a release commit must update that value to its intended next release before tagging. The publish gate requires canonical `major.minor.patch` and a tag exactly equal to `v` plus that value; mismatches, leading zeros, prerelease and build suffixes fail before publication. The root and other workspace package versions are not release authorities. The v0.0.2 tag and release-compat fixture run unchanged. Delivery floors are canonical numeric `major.minor.patch` strings; a NOT VALID check constraint enforces that for writes without scanning existing rows. Comparison uses numeric arrays, never lexical text (so 0.0.10 follows 0.0.9), with no integer-overflow cap. Prerelease/build labels are disallowed for STD releases and delivery protocol versions. `0.0.0` is the baseline every STD worker meets. Both record and config producers explicitly write today's package version.
- **J8 [judgment]: preserve ordering when a row is too new.** The claim adds its version predicate to candidate rows only; the earlier-version anti-join is unchanged and uses the existing partial index. A too-new row blocks later versions of its own record/subscription, including later rows an older worker could otherwise process, but never unrelated records. The exhausted-lease sweep also leaves too-new rows alone. RU9 requires Step 5 to ensure some admitted worker can process every produced row; it does not permit bypassing the row to break per-record order. The oldest-admitted floor producer policy starts with Step 5's admission state; today the offline release writes its own version.

**RU12 remaining feature tolerance (explicit deferral).** This change tolerates unknown config and dependency _kinds_, not arbitrary newer features inside known kinds. `catalog/load.ts` still decodes a known field's type through this release's FieldType schema; a newer type can fail with `CorruptDefinitionRow`. Unknown properties are not a promised opaque round trip: Schema decoding can discard them from the in-memory known definition, and a subsequent known-definition update can rewrite its stored representation. Unknown subscription kinds are not yet classified into informational doctor findings. These three cases require coordinated opaque-row handling across catalog loading, change-set validation, dependency rebuilding, layer diff/write paths and doctor; skipping a field in the loader alone could incorrectly authorize a destructive schema diff. The tolerance must ship in a predecessor release before the first newer field type/property/subscription kind is admitted in a rolling upgrade. Such a feature cannot be introduced while an unprepared v0.0.3 process remains admitted. RU11 must keep such features unavailable to mixed releases; Step 5 cannot claim full RU12 or rolling-config acceptance until preservation and doctor tests cover all three. v0.0.3 has kind tolerance only; its upgrade from v0.0.2 stays offline.

## Deferred to Step 5

`core.upgrade_state`, admission/fencing, connection termination, durable phase/attempt execution and takeover, `--expand`/`--finalize`/`--abort`, RU11 feature tags and refusal, oldest-admitted production floors, relaxed startup/doctor ledger rules, set additive/behavior execution, rolling/abort compatibility tests and the Helm lifecycle remain Step 5. This change does not make today's offline upgrade a rolling upgrade.
