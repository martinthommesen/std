# 0030. Migration phases and the Step 3 rolling-upgrade groundwork

Status: accepted for the Step 3 implementation, 2026-10-23 (3R). Contracts 8.8 remains a draft owned by Step 5; this decision implements its prerequisites, not its admission fence or phase execution.

## Migration metadata

Every `PlatformMigration` declares `phase: "expand" | "contract"`. The runtime rejects missing/unknown phases. Migration 0017 adds `core.platform_migration.phase text NOT NULL DEFAULT 'expand'` with a CHECK limiting it to `expand`/`contract`, and `core.delivery.min_worker_version text NOT NULL DEFAULT '0.0.0'`. The phase CHECK is added NOT VALID and then validated over the small migration ledger (at most 17 rows at installation), never the delivery table. Both defaults are constants: PostgreSQL can add these columns without rewriting existing rows. Transactional, concurrent-index and data runners record the declared phase; the first migrations run against a ledger without that column, so ledger readers synthesize `expand` until 0017 exists.

- **J1 [judgment]: historical metadata and checksums.** All migrations 0001–0016, including the data migrations 0012 and 0016, declare `expand`; the ledger default classifies their already-applied rows the same way. Their existing checksum inputs stay byte-for-byte unchanged. From 0017 onward the phase is also in the checksum, and comparison rejects a stored phase different from the declaration. The historical `expand` tag on a data migration does not make it run during expand: all data migrations belong to finalize under RU1/RU6 when Step 5 implements phase execution. Today the offline runner retains its schema → sets → data order.

## The `migration-phases` check

`pnpm check:tooling` evaluates the actual registered migration statements (including their generated SQL) and checks the migration-file inventory. `tooling/test/migration-phases.test.ts` runs the executable against the real list and JSON canaries in `tooling/canaries/migration-phases/`, including malformed-input and read-failure paths.

- **J2 [judgment]: PostgreSQL grammar, with a closed expand AST allow-list.** The root tooling pins `libpg-query` **18.1.5** (WASM) exactly; its only dependency is `@pgsql/types` 18.0.0, and neither introduces Effect. It runs under the pinned Node 26.12.0 and reports PostgreSQL grammar **180004 (18.4)**. This is the maintained [Constructive Node/WASM distribution](https://github.com/constructive-io/libpg-query-node) of the parser extracted by [pganalyze/libpg_query](https://github.com/pganalyze/libpg_query), using its `18-constructive` fork. There is no PostgreSQL major-version gap. The validation server reports 180006 (18.6), so this parser is two minor releases behind; syntax/fixes introduced after 18.4 are a recorded blind spot and require rechecking when either version changes. The hand tokenizer is removed. Parse errors always refuse the migration. Every SQL string, including contract SQL, must yield exactly one parser statement. Empty semicolon statements are ignored by PostgreSQL, so `; CREATE TABLE ...;;` has one statement; comments alone have none. NUL bytes are refused before the C API can truncate a string. Contract migrations have no AST allow-list.

  Expand permits only these statement nodes and options:

  - `CreateStmt`: a new table (no `IF NOT EXISTS` or typed `OF` table). Each `INHERITS`, `PARTITION OF`, or `LIKE` source must already have been created successfully earlier in this same migration. Names retain their separate catalog/schema/identifier components; quoted dots cannot alias qualification. New-table definitions may include their own constraints and defaults.
  - `AlterTableStmt` for tables: **every** subcommand must be `AT_AddColumn`, `AT_AddConstraint` or `AT_ValidateConstraint`. Added columns may have no default or an `A_Const`, including typed constants and recursive casts of constants. They cannot use serial pseudo-types, generated/identity or storage options; NOT NULL needs a non-NULL constant default. On existing tables, only CHECK and FK constraints marked NOT VALID are allowed, including inline added-column constraints. On tables created in this migration, any added constraint is allowed. Type changes, drops, inheritance/partition attachment, renames and SET options are refused even when mixed with an allowed subcommand.
  - `IndexStmt`: on a table created in this migration, or `CONCURRENTLY` in a `concurrent_index` migration. Unique indexes on existing tables remain refused because they constrain old writers. Any CONCURRENTLY index needs the concurrent-index runner.
  - `CreateFunctionStmt`: functions only, a previously unused name, no replacement, no SET clauses, LANGUAGE sql or plpgsql. String bodies are decoded by PostgreSQL, including E-strings, U& strings and non-ASCII dollar tags. SQL bodies are parsed with the SQL parser (including SQL-standard RETURN/BEGIN ATOMIC bodies); PL/pgSQL bodies with its PL/pgSQL parser. The walker checks nested statements, declarations and expressions, reparsing embedded SQL and SELECT-wrapped expressions. Only read/return SQL statements are admitted; DML, SELECT INTO, DDL, session changes, CALL and dynamic EXECUTE are refused. PL/pgSQL uses a closed statement list: blocks, reads, returns, conditions, loops, exit, raise, assert and diagnostics. Dynamic query fields are refused. Assignment and cursor statements currently fail closed: the public WASM API does not expose the raw assignment parse modes; no handwritten prefix stripping is used.
  - `CreateTrigStmt` only on a table created in this migration; `CreateSchemaStmt` only with no schema elements; `CreateEnumStmt`; `AlterEnumStmt` only with a new value and no old value (ADD VALUE); `CommentStmt`.

  Everything else is refused by default. Migrations 0001–0017 need no GRANT, ALTER DEFAULT PRIVILEGES or CREATE EXTENSION, so these are not allowed. A NOT VALID CHECK/FK still constrains future writes; authors must prove old writers satisfy it. This syntactic policy does not prove compatibility.

- **J3 [judgment]: functions need new names.** Every `CREATE OR REPLACE` is refused in expand, even with an apparently identical signature/body. Reusing a function name already introduced by an earlier migration is refused, including overloads and quoted/unquoted equivalents. Unqualified names conservatively reserve their basename across schemas because the parser cannot resolve `search_path`; qualified names in distinct schemas remain distinct. Contract renames and schema moves also reserve the destination name; dropping an object does not release its old name. This deliberately requires a new name instead of attempting to prove PL/pgSQL equivalence.
- **J4 [judgment]: frozen pre-rule exceptions.** The check admits the existing 0001 config-state initialization, 0003's exact session-revocation function text, 0011's inline check on its new defaulted ledger-state column, and 0014's finished-at backfill. These are narrow historical statement exceptions; they do not authorize new migrations to copy them. Applied SQL is not rewritten merely to pass a new static rule.

**J2 alternative adopted after four review rounds.** The former handwritten tokenizer repeatedly missed PostgreSQL syntax (escape strings, dollar-bearing identifiers, non-ASCII dollar tags and function-local string settings). It is replaced, not extended. `tooling/canaries/migration-phases/refused.json` retains every old SQL case and its previous expected diagnostic, alongside the new exact expected diagnostics. Cases that were merely unsupported encodings or empty semicolon statements are now accepted. `ast-rules.json` covers the fourth-round function SET, nested CREATE SCHEMA/INHERITS, composite-type ADD ATTRIBUTE and U+00A0 boundary exploits and accepted/refused policy pairs. The executable tests assert the entire output and exit code, including no extra findings on accepted cases. Exact historical exceptions and near-miss text are tested separately.

**Parser licensing.** The JavaScript wrapper and `@pgsql/types` are MIT licensed; libpg_query is BSD-3-Clause; the embedded PostgreSQL parser is under the PostgreSQL Licence. Full copyright notices and licence texts ship in [`tooling/licenses/`](../../tooling/licenses/libpg-query-NOTICE), including the BSD binary-redistribution notice. This is a development-only tooling dependency, not part of the server or browser runtime.

**Blind spots.** The checker uses the PostgreSQL 18 grammar, not catalog analysis or an interpreter. It cannot prove the semantics of functions called by SQL, defaults, constraints, indexes or triggers; user-defined operators, types and casts; or volatile domain defaults (including an implicit domain default on a column with no explicit DEFAULT). Constant-shaped ASTs alone do not prove non-volatility after type resolution. It cannot prove old application usage or allowed values, table size, rewrite cost, lock wait/duration, plans, concurrent data behavior, or the release gap before contract removal. SQL bodies can invoke other functions with destructive effects. PL/pgSQL parser limitations and unsupported modes produce refusals, not approval; upgrading its grammar/API requires rerunning all canaries. The runner continues to pin `standard_conforming_strings = on` on its dedicated connection before each transactional or concurrent-index migration. Function SET clauses and embedded session changes are refused in expand, so body parsing cannot silently change that setting. Contract SQL is grammar-checked only; its function semantics are unrestricted. Data-migration correctness, batching/idempotence, set-version separation and RU11 admission remain outside this check. PostgreSQL integration tests, review and Step 5 expand/rolling compatibility tests remain required.

## Tolerance and diagnostics

- **J5 [judgment]: preserve opaque rows.** The layer loader skips unknown `config_base.kind` rows before decoding their payloads, logging each unknown kind once per load (load-local state, with no process-global mutable set), and omits their overrides from the older release's in-memory view. The catalog already selects only known definition tables, so the change-set validator sees only those kinds. Unknown rows and overrides remain in the database. Rebuilding a known definition's dependency edges deletes only known dependency kinds, preserving unknown ones even when attached to a changed known definition. Doctor skips interpretation of unknown payloads/hashes, reports unknown config/dependency kinds as information and does not treat their edges as dangling or extra.
- **J6 [judgment]: the `core` namespace belongs to the platform.** An unknown table there is an informational `newerPlatformTable`; orphan tables in application namespaces retain their warnings. Known tables' missing or changed columns, constraints and indexes remain drift. An unknown ledger migration still fails startup/doctor: relaxing that is part of Step 5's admission protocol, not RU12 row tolerance.

## Connections and deliveries

Server, worker, CLI, coordinator and resumer application names use the single package-version source (`STD_VERSION`), as `std-server@<version>`, `std-worker@<version>`, `std-cli@<version>`, `std-coordinator@<version>` and `std-resumer@<version>`, through one shared helper. Upgrade checks match the server/worker prefixes at the `@` boundary and also recognize the exact legacy unversioned names. CLI sessions never block upgrade merely by name. Diagnostic lock reports retain the complete application name.

- **J7 [judgment]: release version format and source.** `packages/server/package.json` is the sole STD release-version source; main now declares `0.0.3`, and a release commit must update that value to its intended next release before tagging. The publish gate requires canonical `major.minor.patch` and a tag exactly equal to `v` plus that value; mismatches, leading zeros, prerelease and build suffixes fail before publication. The root and other workspace package versions are not release authorities. The v0.0.2 tag and release-compat fixture run unchanged. Delivery floors are canonical numeric `major.minor.patch` strings; a NOT VALID check constraint enforces that for writes without scanning existing rows. Comparison uses numeric arrays, never lexical text (so 0.0.10 follows 0.0.9), with no integer-overflow cap. Prerelease/build labels are disallowed for STD releases and delivery protocol versions. `0.0.0` is the baseline every STD worker meets. Both record and config producers explicitly write today's package version.
- **J8 [judgment]: preserve ordering when a row is too new.** The claim adds its version predicate to candidate rows only; the earlier-version anti-join is unchanged and uses the existing partial index. A too-new row blocks later versions of its own record/subscription, including later rows an older worker could otherwise process, but never unrelated records. The exhausted-lease sweep also leaves too-new rows alone. RU9 requires Step 5 to ensure some admitted worker can process every produced row; it does not permit bypassing the row to break per-record order. The oldest-admitted floor producer policy starts with Step 5's admission state; today the offline release writes its own version.

**RU12 remaining feature tolerance (explicit deferral).** This change tolerates unknown config and dependency _kinds_, not arbitrary newer features inside known kinds. `catalog/load.ts` still decodes a known field's type through this release's FieldType schema; a newer type can fail with `CorruptDefinitionRow`. Unknown properties are not a promised opaque round trip: Schema decoding can discard them from the in-memory known definition, and a subsequent known-definition update can rewrite its stored representation. Unknown subscription kinds are not yet classified into informational doctor findings. These three cases require coordinated opaque-row handling across catalog loading, change-set validation, dependency rebuilding, layer diff/write paths and doctor; skipping a field in the loader alone could incorrectly authorize a destructive schema diff. The tolerance must ship in a predecessor release before the first newer field type/property/subscription kind is admitted in a rolling upgrade. Such a feature cannot be introduced while an unprepared v0.0.3 process remains admitted. RU11 must keep such features unavailable to mixed releases; Step 5 cannot claim full RU12 or rolling-config acceptance until preservation and doctor tests cover all three. v0.0.3 has kind tolerance only; its upgrade from v0.0.2 stays offline.

## Deferred to Step 5

`core.upgrade_state`, admission/fencing, connection termination, durable phase/attempt execution and takeover, `--expand`/`--finalize`/`--abort`, RU11 feature tags and refusal, oldest-admitted production floors, relaxed startup/doctor ledger rules, set additive/behavior execution, rolling/abort compatibility tests and the Helm lifecycle remain Step 5. This change does not make today's offline upgrade a rolling upgrade.
