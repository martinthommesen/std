# 0030. Migration phases and the Step 3 rolling-upgrade groundwork

Status: accepted for the Step 3 implementation, 2026-10-23 (3R). Contracts 8.8 remains a draft owned by Step 5; this decision implements its prerequisites, not its admission fence or phase execution.

## Migration metadata

Every `PlatformMigration` declares `phase: "expand" | "contract"`. The runtime rejects missing/unknown phases. Migration 0017 adds `core.platform_migration.phase text NOT NULL DEFAULT 'expand'` and `core.delivery.min_worker_version text NOT NULL DEFAULT '0.0.0'`. Both defaults are constants: PostgreSQL can add these columns without rewriting existing rows. Transactional, concurrent-index and data runners record the declared phase; the first migrations run against a ledger without that column, so ledger readers synthesize `expand` until 0017 exists.

- **J1 [judgment]: historical metadata and checksums.** All migrations 0001–0016, including the data migrations 0012 and 0016, declare `expand`; the ledger default classifies their already-applied rows the same way. Their existing checksum inputs stay byte-for-byte unchanged. From 0017 onward the phase is also in the checksum, and comparison rejects a stored phase different from the declaration. The historical `expand` tag on a data migration does not make it run during expand: all data migrations belong to finalize under RU1/RU6 when Step 5 implements phase execution. Today the offline runner retains its schema → sets → data order.

## The `migration-phases` check

`pnpm check:tooling` evaluates the actual registered migration statements (including their generated SQL) and checks the migration-file inventory. `packages/server/test/migration-phases.test.ts` exercises SQL fixtures in `tooling/canaries/migration-phases/` and the executable check.

- **J2 [judgment]: fail closed on unsupported SQL surfaces.** The check tokenizes SQL, with quoted literals, quoted identifiers, nested comments, dollar bodies and statement boundaries handled separately. It refuses unknown phases, destructive keywords (`DROP`, `RENAME`, `TRUNCATE`), type/nullability/storage changes, rewrite operations, nonconstant added-column defaults, generated/identity columns on existing tables, added NOT NULL columns without defaults, CHECK/UNIQUE/FK/primary/exclusion constraints on existing tables without `NOT VALID`, and unique indexes on existing tables. It accepts new tables and their own constraints, nullable or constant-default added columns, new functions/types/indexes/triggers, enum values, comments and explicit constraint validation. It refuses unrecognized statements/actions, including DO/CALL and direct data rewrites. A CHECK or FK with `NOT VALID` still constrains future writes: the author must prove old writers satisfy it. `NOT VALID` is not a compatibility proof.
- **J3 [judgment]: functions need new names.** Every `CREATE OR REPLACE` is refused in expand, even with an apparently identical signature/body. Reusing a function name already introduced by an earlier migration is refused, including overloads and quoted/unquoted equivalents. This deliberately requires a new name instead of attempting to prove PL/pgSQL equivalence.
- **J4 [judgment]: frozen pre-rule exceptions.** The check admits the existing 0001 config-state initialization, 0011's inline check on its new defaulted ledger-state column, and 0014's finished-at backfill. These are narrow historical statement exceptions; they do not authorize new migrations to copy them. Applied SQL is not rewritten merely to pass a new static rule.

**Blind spots.** This is a SQL surface check, not PostgreSQL's parser, an interpreter or a database compatibility proof. It cannot establish the meaning of arbitrary function/trigger bodies, user-defined casts/types/operators, functions called by SQL expressions, whether old application code still uses an object, old writers' allowed values, lock wait duration, table size, actual plans, concurrent data behavior, or the release gap before a contract removal. Direct destructive SQL and dynamic EXECUTE/CALL in function bodies are refused. String literals and the behavior of functions called by a new function or trigger remain opaque; they can still have destructive behavior when later invoked. The check does not prove data migration batching/idempotence, set-version separation or RU11 feature admission. PostgreSQL integration tests, review, and Step 5's expand/rolling compatibility tests remain required. Unsupported syntax must be expressed in a supported form or gain a reviewed checker rule; it must not be hidden in dynamic SQL.

## Tolerance and diagnostics

- **J5 [judgment]: preserve opaque rows.** The layer loader skips unknown `config_base.kind` rows before decoding their payloads, logging each unknown kind once per process, and omits their overrides from the older release's in-memory view. The catalog already selects only known definition tables, so the change-set validator sees only those kinds. Unknown rows and overrides remain in the database. Rebuilding a known definition's dependency edges deletes only known dependency kinds, preserving unknown ones even when attached to a changed known definition. Doctor skips interpretation of unknown payloads/hashes, reports unknown config/dependency kinds as information and does not treat their edges as dangling or extra.
- **J6 [judgment]: the `core` namespace belongs to the platform.** An unknown table there is an informational `newerPlatformTable`; orphan tables in application namespaces retain their warnings. Known tables' missing or changed columns, constraints and indexes remain drift. An unknown ledger migration still fails startup/doctor: relaxing that is part of Step 5's admission protocol, not RU12 row tolerance.

## Connections and deliveries

Server, worker and CLI application names use the single package-version source (`STD_VERSION`), as `std-server@<version>`, `std-worker@<version>` and `std-cli@<version>`. Upgrade checks match the server/worker prefixes at the `@` boundary and also recognize the exact legacy unversioned names. CLI sessions never block upgrade merely by name. Diagnostic lock reports retain the complete application name.

- **J7 [judgment]: release version format.** Delivery floors are canonical numeric `major.minor.patch` strings; a NOT VALID check constraint enforces that for writes without scanning existing rows. Comparison uses numeric arrays, never lexical text (so 0.0.10 follows 0.0.9), with no integer-overflow cap. Prerelease/build labels are not delivery protocol versions; a release using them needs an explicit version policy before changing this contract. `0.0.0` is the baseline every STD worker meets. Both record and config producers explicitly write today's package version.
- **J8 [judgment]: preserve ordering when a row is too new.** The claim adds its version predicate to candidate rows only; the earlier-version anti-join is unchanged and uses the existing partial index. A too-new row blocks later versions of its own record/subscription, including later rows an older worker could otherwise process, but never unrelated records. The exhausted-lease sweep also leaves too-new rows alone. RU9 requires Step 5 to ensure some admitted worker can process every produced row; it does not permit bypassing the row to break per-record order. The oldest-admitted floor producer policy starts with Step 5's admission state; today the offline release writes its own version.

## Deferred to Step 5

`core.upgrade_state`, admission/fencing, connection termination, durable phase/attempt execution and takeover, `--expand`/`--finalize`/`--abort`, RU11 feature tags and refusal, oldest-admitted production floors, relaxed startup/doctor ledger rules, set additive/behavior execution, rolling/abort compatibility tests and the Helm lifecycle remain Step 5. This change does not make today's offline upgrade a rolling upgrade.
