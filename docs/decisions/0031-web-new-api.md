# 0031. The web app on the TMF630 API

Status: accepted, 2026-10-23 (workstream `ws/web-new-api`). Contracts 6, 10. Builds on decisions 0018 (web foundation), 0020 (web pages) and 0025 (the TMF630 API).

Martin decided on 2026-10-23 that STD is greenfield: the original `/api/v1` is retired and deleted, and the TMF630 API (built at `/api/v2` in Step 3) becomes STD's only API, renamed `/api/v1`. The consolidation workstream owns the server, `packages/api`, the examples, the docs and the rename. This workstream moves `apps/web` and its tests onto that API. Every request of the app goes through the typed client `@std/api/v2/client` (`makeStdClientV2({ webClient: true })`, built once as the runtime's `StdApi` resource), so the rename does not touch the app. The browser tests name the API's prefix once (`API_PREFIX` in `apps/web/test/browser/app.ts`).

Code: `apps/web/src/{std-client,command,model,message,fake-std-api,fixture,table-fixture,form-fixture}.ts`, `apps/web/src/domain/{wire,record,metadata,table-view,list-query,list-columns}.ts`, `apps/web/src/page/sign-in/sign-in.ts`, `apps/web/src/page/table-list/{command,update}.ts`, `apps/web/src/page/record-form/{command,update,form,view,picker-search}.ts`, and the browser tests in `apps/web/test/browser/`.

## The calls, old and new

| What the app does | Retired API | The API now (typed client) |
| --- | --- | --- |
| Start-up: who the session acts as | `GET /auth/me` | `GET /session/current` (`session.current`) |
| Sign in for a cookie session | `POST /auth/cookie-sign-in` | `POST /session` with `tokenDelivery: "cookie"` (`session.create`) |
| Sign out | `POST /auth/sign-out` | `DELETE /session/current` (`session.signOut`) |
| The tables the user can open | `GET /meta/tables` | `GET /tableMetadata` (`tableMetadata.list`) |
| A table's metadata (list, form, class, targets, related lists) | `GET /meta/tables/{table}` | `GET /tableMetadata/{collection}` (`tableMetadata.get`) |
| A list page, related lists | `GET /tables/{table}/records?filter&sort&fields&labels&count&cursor&limit` | `GET /{collection}?condition&sort&fields&count&after&limit` (`records.list`); next cursor from `Link` `rel="next"`, count from `X-Total-Count`, labels in each EntityRef's `name` |
| A picker's search | `GET /tables/{target}/records?allowedFor=<table>/<field>&…` | `GET /{collection}?allowedFor=<collection>/<attribute>&…` |
| The actors' names in the history | `GET /tables/core.user/records?filter=id in (…)` | `GET /coreUser?condition=id in (…)&fields=name` |
| Read a record | `GET /tables/{table}/records/{id}?labels=true` | `GET /{collection}/{id}` (`records.get`) |
| Create | `POST /tables/{table}/records` | `POST /{collection}` (`records.create`), attributes by API name, references as `{ id }` |
| Update | `PATCH /tables/{table}/records/{id}` with `If-Match` | `PATCH /{collection}/{id}` with `If-Match`: a JSON Patch on record tables, a merge patch on definition tables (below) |
| Delete | `DELETE /tables/{table}/records/{id}` with `If-Match` | `DELETE /{collection}/{id}` with `If-Match` (`records.delete`) |
| History | `GET /tables/{table}/records/{id}/history` | `GET /{collection}/{id}/history?limit=1000&offset=…` (`records.history`), page by page until `X-Total-Count` |
| Writes to definition tables (admin pages: roles, access rules, fields, choices, layouts, saved filters) | the generic record routes, as change sets | the same collections (`coreRole`, `coreAccessRule`, …), each write a change set |
| Browser-test seeding | `POST /schema/change-sets` | `POST /applyChangeSet` |

Errors are TMF `Error` bodies, matched by `code` with `isTmfError`; a stale `If-Match` is now `412 VersionConflict` (decision 0025, M2), which the form shows as before. The session cookie's path is `/api`.

While the move was under way, the API lacked four things the app needed. They were reported, and the consolidation workstream added them (`b98ce148`): `allowedFor` on lists, writes to definition tables, `applyChangeSet`, and saved filters' `filter` text in API names. No call to the retired API is left in `apps/web`.

## The edge: `domain/wire.ts`

The API names attributes by API name (`dueDate`), writes references as EntityRefs, and leaves empty attributes out. Metadata (Contracts 6.3) still names fields, display fields, layouts, related lists and reference targets by definition name. Every page, the stale-form rules and the races handled in decision 0020 work on fields by ID and by definition name.

- **Records stay keyed by definition name** [judgment]. `recordOfResource` converts a resource with the fields its request selected: each selected field's value by name, `null` when the attribute is absent and not withheld (the API leaves an empty value out, Contracts 10.2), a reference as its target's ID with the EntityRef's `name` as its label, and `withheld` by name. Bodies are written back the other way (`resourceBodyOf`, `jsonPatchOf`). Converting where the request is made, with the fields of the metadata it was built from, keeps decision 0020's rule that an answer is read with the names of the revision it was sent at. A record read without `fields` is converted with the endpoint's active fields, the API's default selection (a retired field only when selected, Contracts 1.6). "Not delivered" therefore never comes from the API, as before. The scene tests still check its rendering. The alternative, keying records by API name throughout, would have changed every page and the stale-form rules for no gain: names would still have to be mapped wherever metadata is used.
- **Commands carry the fields** (`WireField`: name, API name, whether a reference). `LoadRecords`, `LoadRelatedRecords` and `LoadRecord` take the selected fields. `CreateRecord` and `UpdateRecord` take the endpoint's fields, to name the body and to read refusals back (`ValidationFailed`'s `fieldErrors`, `InvalidReference`'s and `UnknownField`'s `field`, `SchemaChanged`'s `changes` are in API names). They also take the selection to read the saved record with.
- **Requests print API names.** The condition engine's view of the browser's metadata (`tableClassView`) names fields by API name, so the filter builder's AST (fields by ID, unchanged) prints as `condition` text the API resolves, one-hop paths included (`dockedTo.name`). `sort`, `fields`, a related list's `<backReference> = "<id>"` and the picker's search do the same.
- **Tables by qualified name, collections derived** [judgment]. Routes, targets and related lists keep qualified names. A request names the collection with `apiTableNameOf`, the function the server uses (`@std/definitions/names`). The server's inverse is a lookup, never a parse, but the forward derivation is one function of the name. The metadata's `id` is the same collection.
- **A record's class is its `@type`** [judgment]. The form compares it with the endpoint metadata's `resourceType`. When they differ, the form loads the class's metadata from the collection, which is the type with a lower-case first letter (a type name is its collection name in UpperCamelCase). `validateRecord` gets the qualified name from that metadata. Before the class's metadata arrives, the form's facts name the type (`a HelpdeskIncident record`) instead of the qualified name.
- **Updates: a JSON Patch on record tables, a merge patch on definition tables** [judgment]. A merge patch (RFC 7396) merges an object into a json attribute's stored value, so a form that removes a key from a json value, or stores a member that is `null`, could not save what the user typed. On record tables the form therefore sends a JSON Patch with one `add` per changed attribute (`null` clears it). This sends exactly what the retired API's body did, and a missing path cannot fail, as `remove` would. Definition tables refuse a JSON Patch (`415`), and their merge patch replaces json values whole, so the form sends them a merge patch. Metadata does not say which tables are definition tables, so `page/record-form/command.ts` lists the fourteen platform tables (`DEFINITION_TABLES`, the definition kinds of Contracts 1.4).
- **A write answered with its identity only** [judgment]. When the caller can no longer see the record (Contracts 3.9), the API answers with `id`, `href`, `@type` and `revision` only. A visible record whose selected attributes are all empty looks exactly the same. When an answer holds nothing else, the Command reads the record again at the same revision: `NotFound` means "Saved. You can no longer see this record.", otherwise the read (or the answer) is the record; a read that fails otherwise keeps the write's own answer, since the write succeeded. This was reported to the consolidation workstream: an explicit marker would save the read.
- **History** is read in pages of 1,000 (the API's maximum) until `X-Total-Count` entries are in. Each `ChangeEntry` becomes the panel's entry: the actor's ID, the change ID, `revision` as the version, `changes` and `fields` as served (both keyed by API name, as the panel only pairs them). An entry the panel cannot read makes the history unavailable rather than partial.
- **Sessions.** `CurrentUser` is the API's `CurrentSession` (name, roles, schema revision, user as an EntityRef). It still holds no token.

## Tests

- **Unit, story and scene tests** (`pnpm --filter @std/web test`, 298 tests): the fixtures serve metadata in the API's shape (`servedAs`, `summaryOf`, API names from the shared derivation). The Commands run against the fake server through the real typed client. New cases: a list page read back by field name, with references and labels, empty attributes as `null`, a withheld attribute, the next cursor from `Link` and the count from `X-Total-Count` (`page/table-list/story.test.ts`). The update's JSON Patch with API names and an EntityRef, the password unwrapped only in the body, and every refusal read back by field name, `RuleRefused` included. A definition table's merge patch. A create with API names. An identity-only answer read again, with `NotFound` meaning "no longer visible" and a failed read still a success. A read with a withheld and an empty attribute. The picker's `allowedFor`, `condition` and cursor. History in pages, and the actors' names (`page/record-form/command.test.ts`).
- **Browser tests** (`pnpm --filter @std/web test:browser`) against a real `std serve`: every Step 2 behavior they proved still holds on the API: lists and filters page by page against the API's own answer, the picker's allowed targets, related lists, the history at the entry's revision, stale forms and the `SchemaChanged` flow (the refusal read by `code`), the admin pages, saved filters, sign-in and sign-out with the `/api` cookie and the forged same-site posts, the restricted-value checks in responses, the page and DevTools (gate 2B). The test side reads resources by the rules of Contracts 10.2 on its own (`recordOf` in `test/browser/shown.ts`), never with `wire.ts`, so a converter bug cannot agree with itself. The hidden-value search treats a resource's field attributes as record values, as it did `values`, `labels` and `changes` (`hiddenValuesIn`).

If the consolidation moves them, the imports follow.
- `docs/architecture.md` ("Web app", "Sessions") still says the web app calls `/api/v1` through Step 2 and moves to `/api/v2` in Step 3. The consolidation workstream owns that text.
- Metadata could say whether a table is a definition table, which would replace `DEFINITION_TABLES`, and a write's answer could mark a record the caller no longer sees.
