# 0033. The TMF Open API framework, the OpenAPI contract harness and the CTK runner

Status: proposed, 2026-10-23 (workstream 3T, plan Step 3 row 3T). Contracts 4.9, 10, 11.1, 11.6, 12, 15. Builds on decisions 0021 (decisions 34 to 55), 0025 (the TMF630 API and its JSON Patch evaluator), 0026 (the spec check and its kit notes) and 0029 (aggregates).

Guarantee (plan, row 3T): a TMF API never shows or accepts more than the record service allows the caller; an aggregate changes whenever a part does; a mapped API passes its conformance gate; every normative requirement is tested or excluded by Martin. This workstream builds the machinery every TMF Open API mapping uses (TMF621 in 3I, the Step 4 APIs in 4D, 4C and 4O); it maps no TM Forum API itself.

## What was built

### Mappings (`packages/tmf/src`, plain)

A mapping is data plus pure functions over what the record service let the caller read; it never reads or writes anything.

- `mapping.ts`: `TmfApiMapping` (specification, base path, resources, hub statuses) and `TmfResourceMapping` (path segment, TMF type, mapped class, `@type` of each shipped class, attributes, offered operations, the statuses the pinned document declares per operation, event rules, an optional `createClass`). Fields are named by stable ID, system fields as `system:<name>` (`SYSTEM_SOURCES`), so renames never break a mapping.
  - Attributes: `fieldAttribute` (one field, its JSON value), `enumAttribute` (a value map, refusing an unknown TMF value on write, matching nothing in a filter), `referenceAttribute` (`{"@type": <refType>, id, name, "@referredType", href}`; a write reads only `id`), `jsonAttribute` (a value object stored whole, merged by RFC 7396 when it is an object, never filterable: E16), `derivedAttribute` (several sources, a write that may read the current values under the lock, a custom filter: the shape of TMF621's status map and of `relatedParty` over several fields), and `partsAttribute` (an array of parts: part class, owner reference, item type and item attributes).
  - Each attribute names its `sources`. It renders only when the caller can read every source on that record, so a derived attribute never reveals a hidden source (12.1's rule for derived attributes, applied to reads as well) [judgment]. It is known to the caller (for `fields`, `sort`, filters and writes) only when every source is in the caller's visible schema of the class, so naming a hidden attribute is `UnknownField`, identical to a missing one (3.4).
- `render.ts`: `renderResource` (identity attributes, readable non-empty attributes, arrays of the visible parts with `@type` and `id` per item, `fields`), `typeAttributesOf` (a shipped class renders its mapped TMF type, with `@baseType` when the TMF type extends another; a local child class renders its own `/api/v2` type name with the `@baseType` of its nearest mapped ancestor, Contracts 11.1).
- `write.ts`: `planWrite` turns an FVO or MVO body into the record's field values and, per array the body names, the parts to keep, update, create and delete; `mergeBodyOf` turns a JSON-Patched resource into the equivalent merge-patch body.
- `query.ts` (`fields`, `sort`), `status.ts` (`tmfStatusFor`), `events.ts` (`eventTypesOf`, `standardEvents`: Create, AttributeValueChange, StatusChange when the resource has a status, Delete).

### Routes (`packages/server/src/http/tmf/`)

`tmfRoutesLayer(registry)` builds, per API and resource, `GET`/`HEAD`/`POST /{resource}` and `GET`/`HEAD`/`PATCH`/`DELETE /{resource}/{id}` from the mappings; `app.ts` serves `SHIPPED_TMF_APIS` (`apis.ts`, empty until 3I adds TMF621), and tests add fixture APIs with `TestHttpClient.layerWith`.

- **One enforcement point** (11.1). Every read goes through the read compiler as the caller (`readPage`, `readOne`, `readByIds`: visibility, masks, labels), every write through `createRecord`, `updateRecord` and `deleteRecord` as the caller with `RuleWriteAccess`; nothing reads or writes a table directly and nothing uses `WriteAccess.allowAll`. A record read through the mapped class is read again through its concrete class (as `/api/v2` does, decision 0025 D1); parts are read through the part class's view filtered on the owner reference, so only visible parts appear, with only readable fields. Withheld values never reach the mapping.
- **Lists** reuse the TMF630 machinery: `splitParameter`, `alternativesOf` and `atomOf` of `/api/v2` (exported for this), `compileFilterExpr` with `exactText` (decision 0025 D4), `readPage`, `parseLimit`, cursors and `linkHeader`; `X-Total-Count`, `X-Result-Count`, `Link`. An attribute's filter compiles from its field (values through the attribute's value map) or from its custom condition (paths are source keys). `@type=` selects the concrete classes whose TMF type matches. `filter` is `501` (E14).
- **Writes** run as one `aggregateOperation` (4.9): `lockAggregates` on the record, then the record and its visible parts are read as the caller under that lock, then `If-Match` (when sent) is compared with the locked version, then the plan is made against that image, then the record's own fields are saved at most once (with `evaluate` merging json objects into the stored value, as `/api/v2` does), then the parts: deletes, updates, creates, each a part save as the caller. Finalization then gives the owner one aggregate version when any part changed. So a write of the owner's own attributes gives one version, a write of parts one version, and a write of both two: the owner's own save and the aggregate save (Contracts 4.9's results, which 11.1 permits: the adapters save an owner's own fields at most once per write; `tmf-arrays` proves the count). One write is thus one `aggregateOperation` that may commit two owner versions: history keeps the intermediate version, the per-save outbox hooks may enqueue a delivery for each, and the response's `ETag` is the final version (now said in Contracts 11.1). The answer is read afterwards as the caller (the committed state; `reloadSaved`'s rule).
- **Merge-patch on arrays of parts is strict RFC 7396** (decision 0021, decision 41): the array replaces the parts the caller can see; an item whose `id` names one of them updates it to the item (writable attributes it leaves out are cleared, read-only ones may repeat their value); an item without such an `id` creates a part; a visible part no item names is deleted.
  - An existing part is planned with the caller's access to its own concrete class for an update, a new item with the access to the item's class for a create (`partAccess`): a field the caller cannot name there is `UnknownField` when written and is never cleared by a replacement.
  - A replacement clears what it leaves out or fails: a writable attribute whose writer refuses `null` (a required derived value) is `ValidationFailed`, and so are two attributes that would write different values to one field; nothing is kept silently.
  - **Order.** An item mapping may name an integer `orderField` of the part class; reads list the parts by it, then by creation. A reorder (by merge-patch, or a JSON Patch `move`) is stored only when the caller can both read and write the order field on every item; it then writes every item's position, 0 to n-1, and is a change of the parts, with a new owner version. A body that keeps the kept parts' current order (as reads list them, ties by creation) and appends new items writes no kept position, only the new items' (one past the highest kept), so sending back an array as read changes nothing, also with duplicate or negative positions that other writers left. Without an order field, or when the caller cannot read and write it on every item, a body that would reorder the parts the caller can see (kept items out of their order, or a new item before a kept one) is refused with `ValidationFailed`, naming only the array, rather than ignored or stored unseen. The order field is the framework's alone: a mapping whose item attribute writes it is refused when the routes are built (`mappingProblems`, with duplicate attribute names), the simpler of the two options the review offered. No platform migration is needed: the order field is an ordinary field of a part class, declared by the set that ships the mapping.
- **JSON Patch** (RFC 6902) is applied with `/api/v2`'s evaluator (`parseJsonPatch`, `applyJsonPatch`) to the resource as the caller reads it under the aggregate's lock, and written as the equivalent merge-patch body (`mergeBodyOf`), so `test` and `copy` always see the version the write applies to (`json-patch-race`'s guarantee, 10.5), and an array of parts behaves the same in both formats. Its values are the exact results: a json value a JSON Patch changed replaces the stored one (a removed member is gone); only a merge-patch merges a json object into the stored value (RFC 7396).
- **`DELETE`** deletes the visible parts, each authorized for the caller, then the record, in one aggregate operation; the deleted owner is not finalized (4.9).
- **Errors and statuses** (`errors.ts`): every error is the `/api/v2` TMF `Error` (`code` the STD tag) with the status `tmfStatusFor` picks among the operation's declared statuses (decisions 52 and 55): STD's own status when declared; a stale `If-Match` `412` when declared, else `409` (TMF621); any other undeclared client error `400`; a server error `500`. `fieldErrors` name TMF attributes where an attribute is the only writer of the field.
- **Methods** a resource path does not offer are `405` with `Allow` (the path's methods and `HEAD` where `GET` is, never `OPTIONS`), decided by the path alone, after the session; an unknown path under a base path is `404`.
- **`fields`** selects the mapping's attributes the caller knows and the local attributes of every class of the subtree the caller can read, which reads return by default.

### `tmf-oas-contract` (`packages/testing/src/tmf-oas-contract.ts`)

The test HTTP client checks every response under a pinned Open API's base path (and under a fixture's, registered with `layerWith`) against the pinned document: the operation by method and path template, the status among the operation's explicitly declared ones, the body against the response's `application/json` schema with Ajv (OpenAPI 3.0 `discriminator` honored: a mapped `@type` validates against the mapped schema and the declaring one, which picks a `oneOf` branch; an unmapped `@type` validates against the declaring schema, any branch; `date-time` and `uri` formats checked). `declaredStatusesOf` reads a document's statuses, so a test proves a mapping's `declaredStatuses` equal its document's.

### The CTK runner (`tooling/ctk/run.ts`, `tooling/lib/ctk-report.ts`, `tooling/lib/zip.ts`)

`pnpm ctk <api> --url <base URL> --token <bearer> [--payloads <file>] [--network <net>] [--reports <dir>]` downloads the pinned zip into `~/.cache/std-ctk` (never the repository) and checks its SHA-256; reads the kit's `config.json` from it (a minimal ZIP reader: nothing in the archive is executed or extracted); pulls the image and checks its repository digest against `pins.json` (`ctk.imageDigest`, new and optional in the pin schema, recorded for TMF621); writes `config.json` (URL, bearer token, the kit's default payloads overridden by `--payloads`, since the defaults are placeholders such as `sample_severity`); runs the image directly in a uniquely named `--rm` container with an empty reports directory; judges the report; copies it to `--reports`. The run is a session (`tooling/lib/ctk-session.ts`) whose cleanup is registered as soon as its working directory exists and runs exactly once, in `finally` and on `SIGINT` or `SIGTERM` (then exiting 130 or 143), with the signal handlers kept until it ends: it deletes the bearer configuration first, independently of Docker; force-removes the named container (`--rm` removes it only when it exits) and deletes what the kit wrote through the kit's own image (the kit's user owns it), each Docker call bounded by a timeout that kills its subprocess; then deletes the working directory. The verdict (`judgeKitRun`) is Contracts 11.1's: `index.json` present, a mochawesome report, written by this run (empty directory before, `stats.start` not before the run's start); `ctk_version.txt` names the pinned image; failures, pending and skipped all 0 and passes equal tests, and every listed test passed; every `kitCases` title of the specification's matrix file passed.

### The kit's cases (TMF621)

A helper pulled `tmforumorg/tmf621-v5.0.0-ctk:1.0.1` (digest `sha256:5705c271…63e1`) and read its Cypress project without running it, then ran it twice against a throw-away stub server in uniquely named containers it removed; the runner itself then ran it once end to end against a stub (download, SHA-256, digest, run, verdict, clean-up). Facts (nothing of the kit is in the repository):

- One spec, `cypress/e2e/production/ctk.cy.js`, generates 44 tests from the kit's case list: 17 suites (`Tests method <M> and path <P> [and ?fields=<f>]`), each with one context (`TMF621 Conformance Profile v5.0.0 - API <M> Operation Conformance - For <R> Resource[ - ?fields=<f>]`) and the tests `Tests status`, `Test schema` (not on `DELETE`) and `Each attribute Test` (on `GET`), each title ending in `EndPoint: <configured URL><path>`.
- The kit marks no case mandatory. TroubleTicket's mandatory operations (CP v5.0.0 p.6) give 27 cases; the other 17 are on `troubleTicketSpecification` (optional in the profile, served since decision 38). There are no hub, listener or ticket `PATCH` cases, which settles F621-20.
- The image's entrypoint runs `npm start || true`, so the container exits 0 when tests fail; with an unreachable URL Cypress runs nothing and no `index.json` is written. `ctk_version.txt` holds the image name and tag; the report holds no image name or digest, so the runner checks the digest itself.
- The `Each attribute Test` cases compare dotted keys that are never set, so they pass whatever the server answers (they passed against a stub answering errors): they are kept as cases the runner requires, but they are no evidence for the attributes; the CP and OAS rows are.

The matrix replaces the placeholder `TMF621@5.0.1/KIT/mandatory-cases` with 27 rows, `TMF621@5.0.1/KIT/<case>/<check>`, each with its normalized title in `kitCases` (all 27 matched the titles of the real run), `pending` until 3I's CTK job passes them.

## Judgments

1. **Stale requests on TMF routes** (amended in review rounds 1 and 2). A mapping names fields by stable ID, so its attributes need no stale check. A local class's attributes are its fields' API names, which a rename can move to another field: a request that names them (body members, `fields`, a read's default selection of a class that has them) and states a revision (`STD-Schema-Revision`) is checked as on `/api/v2` (6.4), so a name renamed or reused since is `SchemaChanged` (`409` on writes, `400` on reads, decision 52's mapping). Every name a PATCH takes is checked before anything is evaluated: a merge-patch's members, and each JSON Patch operation's `path` and `from` (a `test`, a `copy` source, a replacement that changes nothing). A read checks the local attributes it returns: those an explicit `fields` selects, or, for the default selection, all of its classes'. A stated revision is checked even when the request names no local attribute (a mapped-only read or write, a list without records, a delete), as a request that names no field is: a revision this database never had is `SchemaChanged`, as on the generic API. A request stating no revision is resolved at the current revision, as on `/api/v2`: Contracts 6.2 lets plain API clients omit `STD-Schema-Revision` and get no stale detection, so a client that must not hit a reused name sends the header (the reviewer accepted this gap). Purged mapped fields are unknown (`UnknownField`), retired ones readable and `DefinitionRetired` on write (`tmf-lifecycle`).
2. **Derived attributes need every source readable**, on reads as on events (12.1), so a TMF status derived from a hidden hold reason is absent.
3. **Undeclared client errors are `400`.** Decision 52 names `ValidationFailed`, `InvalidReference` and media types; every other STD client error whose status the operation does not declare (`SchemaChanged`, `FieldsConflict`, `RuleRefused`, `AggregateNotSettled`, …) answers `400`, which every TMF operation declares, with the STD tag in `code`. A stale `If-Match` answers `412` where declared, else `409` (decision 55).
4. **The TMF `Error` body is `/api/v2`'s** (`@type` the tag, `@baseType` `Error`, `@schemaLocation` into `/api/v2/openapi.json`, STD's details as extension attributes), with `status` the TMF status. It validates against every pinned `Error` schema (`code` and `reason` required).
5. **`default` declares nothing.** The contract harness counts only explicit status codes, as decision 52 does (so E29's `429` on hub registration is a deviation although the hub operations have a `default` response). Until 3H wires the hubs, `/hub` and `/hub/{id}` answer `404`, which TMF621's hub operations declare only through `default`; the harness would report it, and no test requests it.
6. **Discriminators.** The harness honors OpenAPI 3.0 discriminators as above; an `@type` the mapping does not name (a local class, an STD `Error` subtype) validates against the declaring schema: the TMF630 extension pattern.
7. **Unknown parts IDs.** An array item whose `id` names no part the caller can see creates a new part and does not use the `id`: identical for a hidden, deleted or random ID (3.4).
8. **Parts the caller cannot see are never touched** by an array replacement; a `DELETE` of a record that still has a part the caller cannot see is `Referenced` (`409`, declared), and nothing is deleted.
9. **`fields` selects top-level attributes**; a dotted name selects its top-level attribute whole; identity attributes are always returned. `sort` takes attributes whose mapping names a sort field.
10. **`condition` and `count`** (STD extensions of `/api/v2`) are not TMF parameters: on a TMF route they resolve as attribute filters and are `UnknownField`.
11. **`OPTIONS`** on a TMF route is `405` with `Allow`, and `Allow` never lists `OPTIONS`: the TMF documents declare no `OPTIONS` operation and STD serves no cross-origin callers.
12. **A create whose record the caller cannot see afterwards** (3.9) answers its `id`, `href` and the resource's TMF type.
13. **Kit case titles are compared normalized** (the configured URL as `{url}`, white space runs as one space): the kit's titles embed the configured URL and tab and new-line runs, so an exact comparison would tie the matrix to one URL (amends Contracts 11.1's "by exact title"; the contract text now says so).
14. **Names are decided for the concrete class.** A TMF write knows its record's class (a create names it; an update locks and reads the record first), so the fields a body may name are those the caller can read on exactly that class, or write there by a field rule (`classAccessOf`), not the subtree-wide `WriteAccess.nameable` of the generic API. A field that only a child class makes writable is therefore `UnknownField` on a parent-class record, exactly as a field the caller cannot read, and never reaches the record service's field rule, whose `NotAllowed` (403) would reveal that the field exists. The record service still enforces every rule on the save. (Found by `tmf-noninterference-fixture` once the fixture's incident class, whose employees may write every field, became a child of the ticket.)
15. **An ID that is no UUID** is `NotFound` before anything is locked, byte for byte the answer for a missing or hidden record.
16. **Date-times in the contract harness** are RFC 3339 with calendar and time ranges (`packages/testing/src/rfc3339.ts`): a month that exists, a day of that month (leap years), hours, minutes and an offset in range, a second 60 only at 23:59 UTC.
17. **The runner reads only `config.json` from the zip** with its own reader; the kit's `docker-compose.yaml` and `run.sh` are not used (Contracts 11.1: the compose service is run directly).

## Deferrals

- **The CTK job in CI**: the runner, its tests and an end-to-end run against a stub exist; the job that starts STD with the TMF621 mapping, seeds the `tmf_ctk` user and its token and runs `pnpm ctk tmf621` belongs with the mapping (3I), which also writes `--payloads` (real `severity`, `ticketType` and specification values, F621-04).
- **Hubs**: the seam is the hub paths in `routes.ts` and `TmfApiMapping.hubStatuses`; event types are declared by the mappings (`events`), and `renderResource` renders the payloads; 3H (`ws/3h-events-hubs`) wires registration and delivery.
- **Parts of parts** (three-level aggregates) are neither read into items nor deleted by the TMF `DELETE`; none of the Step 3 APIs has them. TMF622's order items with approvals (Step 4) need it.
- **A JSON Schema for a local class** (`@schemaLocation` adding its local attributes to the pinned schema, 11.1): local classes render `@type`, `@baseType` and their attributes, without `@schemaLocation`, until a TMF schema endpoint exists (3I's `tmf-local-class`).
- **TMF621 rows**: the fixture proves the machinery against TMF621's document, but the rows stay `pending` until 3I proves them through TMF621 itself; the framework tests that cover each row's machinery are listed below for 3I.

## Review round 1

1. Parts are planned with the access of each existing part's concrete class (update) and of the item's class for new items (create); implicit clears skip fields the caller cannot name.
2. A JSON Patch writes the exact resulting values; only a merge-patch merges json objects.
3. Part order persists through a mapping-declared order field; without one, a reorder is refused.
4. A clear its writer refuses, and conflicting values, fail the plan.
5. Local attributes are checked against the stated revision; the lifecycle tests cover retired, purged and renamed-and-reused fields (judgment 1 amended).
6. The CTK runner's session cleans up in `finally` and on signals.
7. The harness checks RFC 3339 date-times with calendar ranges.
8. `Allow` on TMF routes never lists `OPTIONS`.

Also: `fields` selects local attributes (judgment 9), and the owner's version count for a write of both its own attributes and its parts is stated precisely (two versions).

## Review round 2

1. JSON Patch paths and sources are checked against the stated revision before evaluation; a stated revision is validated also when the request names no local attribute (`tmf-lifecycle`).
2. A reorder needs the order field readable and writable on every item; otherwise it is refused (`tmf-arrays`).
3. Positions are kept when the order stays, so an array sent back as read changes nothing, also with duplicate and negative positions (`tmf-arrays`, `tmf-mapping`).
4. A mapping whose item attribute writes the order field is refused when the routes are built (`mappingProblems`; `tmf-mapping`).
5. An explicit `fields` is checked for what it selects only (`tmf-lifecycle`).
6. CTK cleanup deletes the bearer configuration before any Docker call, bounds each Docker call with a timeout that kills it, and keeps the signal handlers until cleanup ends (`ctk-runner`, with a hanging Docker stub).

## Rolling upgrades (8.8)

No platform migration and no definition change: the framework is code. `ctk.imageDigest` is an optional property of `pins.json`'s schema.
