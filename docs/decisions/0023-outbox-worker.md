# 0023. Outbox worker: leases, effects, payloads, dead letters, config subscriptions

Status: accepted, 2026-10-22 (workstream 3B, the outbox worker; plan Step 3). Builds on decisions 0013 (the producer, claims and fencing at SQL level), 0014 (access rules and platform tables), 0021 (config subscriptions, decision 27). Code: `packages/server/src/outbox/{worker,worker-process,delivery-effects,delivery-failed,delivery-payload,dead-letters,metrics,delivery-claims}.ts`, `packages/server/src/schema/config-deliveries.ts`, `packages/server/src/platform/migrations/{0014-outbox-worker,0015-delivery-done,0016-system-user-history}.ts`.

## Decision

The worker claims deliveries per subscription with the 4.6 claim predicate unchanged, runs one of two kinds of effect under a lease that outlasts the effect's timeout, records the outcome with the fenced updates of decision 0013, and runs as its own process, `std worker`. Payloads are built from history when a delivery runs and filtered for the subscription's identity on the version's own image. Change sets write the deliveries of subscriptions on the config kinds `role` and `accessRule`, and an access-rule change bumps the versions of the roles it names.

## The effect interface (for 3A and 3H)

A consumer registers a `DeliveryHandler` whose `effectFor(subscription, snapshot)` returns the effect that serves a subscription, or `undefined`. The worker claims deliveries only for active, enabled subscriptions that some handler serves; the first handler that returns an effect wins. Deliveries of a subscription that no handler serves, or that is disabled, stay `pending` and are never claimed, so they count no attempts [judgment: disabling pauses a subscription instead of dropping its backlog; a subscription without a consumer is not a failure].

- **`record`** effects write through the record service only. The worker runs one request transaction: it reads the payload, runs the effect as the subscription's identity (`Actor` with the identity's current roles, `RuleWriteAccess`), and ends with the fenced `done` update. The writes and `done` commit together or roll back together, so in-database effects happen exactly once (4.1 decision): a crash rolls back the open transaction, and a lost lease makes `markDone` fail with `LeaseLost` inside the transaction. The effect must give its saves `delivery.cause` (`after_commit` with the subscription and the parent change); its saves pass the full pipeline, deliveries and wake-ups included.
- **`external`** effects call another system. The payload is read in its own transaction; the effect runs outside any transaction with `delivery.changeId` as its idempotency key; then `done` commits on its own. They are at least once: a crash or lost lease between the call and `done` repeats them with the same `change_id`.
- A typed failure of either is recorded with backoff or as `dead`; `last_error` keeps only the error's `_tag`, plus the `reason` of `DeliveryFailed` and `PayloadUnreadable`, the SQLSTATE of `DatabaseError`, or a fixed timeout text, never a value (4.3). A defect is logged and recorded as "Defect: the attempt died; see the worker log."

3A's `afterCommit` record rules are served by `afterCommitRuleHandler` (`outbox/production-handlers.ts`): a carrier subscription (`ruleCarriers`, decision 0022) gets a `record` effect that calls `runAfterCommitRule` inside the delivery transaction, so the rule's writes and `done` commit together. `std worker` saves through `RecordRuleSaveHooks`, as `std serve` does, so the rule's own saves run rules and write deliveries. The carrier's identity must be an active user, as for every delivery: a carrier acting as the inactive system user fails its attempts. 3H's hub callbacks plug in as a handler that returns an `external` effect which POSTs the rendered event. `std worker` lists the production handlers in `ProductionDeliveryHandlers`.

## Leases and timeouts

- One claim per subscription and pass, `batchSize` rows (default 16), committed before any effect starts. The claim holds at most one row per record (a record's later versions wait for the earlier one), so the claimed rows run concurrently.
- The lease is `effectTimeout + leaseMargin` (defaults 60 s and 30 s) [judgment]. The worker starts its clock before the claim's transaction, so the database's `lease_until` is later than the worker's deadline by at least the margin.
- **One deadline per delivery** (review round 1): `effectTimeout` after the claim started covers acquiring a connection, preparing the payload and the effect. Preparation runs under the deadline; right before the handler the worker checks it again, and once it has passed the handler is never invoked, whatever kind it is: the attempt counts as a lost lease (`AttemptRefused` `deadline`), nothing is recorded, the lease expires and the next claim runs it. Otherwise the effect gets exactly the time left and is interrupted at the deadline (`Effect.timeout`), which records a `TimeoutError` failure within the margin. So no effect starts after its lease could have been taken over, and an external effect cannot arrive after a newer version that another worker delivered in the meantime.
- An interrupted worker (shutdown, kill) records nothing; the lease expires and the next claim counts the attempt (decision 0013: `attempts` counts claims; the claim dead-letters a row whose last allowed lease expired).
- A missing or inactive identity fails the attempt without running the effect (decision 0013's open item) [judgment: the operator sees it in `last_error` and, after `max_attempts`, among the dead rows].

## Configuration changes after a pass, after a claim (review round 1)

- A pass refreshes the configuration to find candidate subscriptions; each claim then runs in its own request transaction (`begin_request()`, `CONFIG_KEY` shared, Contracts 1.3) and resolves the subscription from that transaction's snapshot: it claims only for an active, enabled subscription a handler serves, with its current dead-letter policy and `max_attempts` (`serveSubscription`). A disable, retire or policy change that commits after the pass's refresh is therefore honoured by the claim.
- Preparation, in the delivery's request transaction (for a `record` effect, the delivery transaction itself), resolves the subscription once more from its snapshot. The effect runs with **that** subscription: its current identity filters the payload and acts, and its handler's effect is the one invoked. If the subscription is now disabled, retired, served by no handler, or served by a different kind of effect (`record` versus `external`), the effect is not run: the claim is released with a fenced update (`releaseClaim`: `pending`, due now, `attempts` minus one, so the claim does not count) [judgment]. The delivery then waits while the subscription is paused, or runs on the next pass under the new configuration.
- A failure is recorded with the `max_attempts` the claim resolved.

## Polling and wake-ups

Each worker listens on `std_worker` with reconnect (the producer's after-commit, debounced wake-up of 4.1 step 11 already existed from Step 1) and polls every `pollInterval` (default 2 s). After a pass that claimed something it runs the next at once; otherwise it waits for a wake-up or the poll interval. A re-established LISTEN counts as a wake-up, because notifications sent while disconnected are lost. Wake-ups only wake; polling alone is correct.

## Payloads (4.5)

`payloadOf` builds the payload from history alone, so it never depends on the record's state when the delivery runs:

- **The version's own image** is reconstructed from history and the fields' definition revisions alone (review round 1 replaced the earlier rule, which filled unmentioned fields with empty values; a field added with a default gives existing rows that value without a change entry, so the old rule could expose a record a deny rule on that field hides). A field's value at version n is: the `after` of the latest entry up to n that changed it (for a delete, the delete entry's `before`, which holds every non-empty value); else, if the field existed when the record was created (the create entry's `schema_revision` is at or after the field's first `core.definition_revision`), its empty value, since a create records every non-empty value; else the record predates the field and its value is what `ADD COLUMN` gave existing rows, the field's default at its creation revision (false for a boolean without one), provided version n was written after the field existed, the class is not a platform table (migrations add those columns) and the field is not auto-numbered (a backfill step numbers rows, Contracts 1.5). Anything else is **unknown**: a version written before the field existed, a backfilled number, a field without a definition revision, history that does not start with a contiguous create. An unknown field is never assumed empty: it is left out of the image, never appears in a payload, and an access-rule condition that needs it to decide denies (the evaluator throws on a missing field and the decision fails closed). Fields the current snapshot no longer describes are left out.
- The history endpoint (Contracts 3.7, 4.5) does not share the flaw: it decides readability in SQL on the current row, never on a reconstructed image.
- The reconstruction relies on complete create entries (Contracts 4.2: a create records every non-empty value). Every create path writes them: the save pipeline (`changedFields` with no `before`), definition changes (`fieldsOf` with no predecessor) and, from Step 3, `saveBatch`, which Contracts 7.7 requires to produce the same change-entry maps. The system user used to be the exception: `insertSystemUser` inserted its row by SQL without an entry, so a delivery about it could not reconstruct its fields and lost an authorized payload (review round 3). `insertSystemUser` now writes its version-1 create entry in the same transaction (`systemUserCreateFields`: the fixed values as a save records them, cause `system`), and `data` migration 0016 writes the same entry on databases whose system user predates that (cause `system` naming the migration; it writes the entry directly, since it records an existing version rather than making one) [judgment]. Test fixtures that insert rows as table owner write no entries; they never reach production.
- Field origins are read by the numeric revision (`ORDER BY dr.definition_id, dr.revision`, review round 2); no text rendering in the payload reader is aliased to a column name.
- **Filtered for the identity under current rules**: the identity's roles now and the current snapshot's access rules, their conditions checked, resolved (`me` = the identity, `now` = delivery time, instance time zone) and evaluated in TypeScript on that image. This is the evaluator the 1D differential test holds equal to the SQL compiler; a condition that no longer checks or resolves fails closed, as the SQL compiler's `FALSE` does. The record is visible when the record `read` decision holds; a field is readable when, in addition, its field `read` decision holds (3.2).
- The payload carries `changeId`, `operationId`, `recordId`, the concrete `classId`, `recordVersion`, `kind`, `occurredAt`, `visible`, `actorId` (null when not visible), `image` (readable fields, canonical JSON by field ID) and `changes` (the entry's changes of readable fields). A delivery for a record the identity cannot see carries no field and no actor; handlers decide whether to act on it (3H sends nothing).
- Password and secret fields never appear, not even as the entry's `{"changed": true}` marker [judgment: the marker reveals that a secret changed].

## Dead letters

- `listDeadDeliveries`, `retryDeadDelivery` and `discardDeadDelivery` are record-service operations with the `Actor` in the environment. "Admins only" is decided without naming a role (3.2): a delivery belongs to a subscription, and `core.subscription` is a platform table that only `core`-layer rules reach. Listing needs an unconditional record `read` decision on `core.subscription`, retry and discard an unconditional `update`; anything else is `NotAllowed` [judgment]. A row that is not `dead` is `NotFound`.
- Retry: `pending`, due now, `attempts` 0 (the subscription's `max_attempts` applies afresh), `finished_at` cleared; workers are woken after commit. Under `skip`, a retried delivery arrives after newer versions (4.7).
- Discard: `done` without running the effect, `last_error` kept; under `block` this releases the record's later versions. The row is deleted with the other `done` rows after 7 days [judgment: no new status, so the claim predicate and the `delivery_order` index stay as they are]. Retry and discard each save a `core.dead_delivery_action` through the record service in the delivery transition's transaction; its ordinary change history identifies the operator (Martin's stored-task decision, 2026-10-23; decision 0037). Refusals save nothing. The gauge refresh runs only after the outermost commit.
- The gauge `std_outbox_dead_deliveries` is refreshed by housekeeping (every minute), whenever an attempt makes a row dead, and after every retry or discard. The process has no metrics exporter yet (Step 5, observability).
- **What follows after workstream 3G merges** (`/api/v1` is frozen and `/api/v2` is being built, so this workstream adds no route and no page): `GET /api/v2/outbox/deadDelivery` (TMF630 list with `offset`/`limit` or `after`, filter by `subscriptionId`) calls `listDeadDeliveries`; `POST /api/v2/outbox/deadDelivery/{id}/retry` and `.../discard` (TMF630 task resources) call `retryDeadDelivery` and `discardDeadDelivery`; their errors map as Contracts 10.6 maps `NotAllowed` and `NotFound`. The Foldkit admin view lists dead deliveries per subscription with their `last_error`, attempts and time of death, and offers retry and discard. The exact paths follow 3G's naming.

## Retention

Migration 0014 adds `finished_at`, which the worker sets on `done` and `dead` and clears on retry; existing finished rows get the migration's time. It has no CHECK, so the previous release's fenced updates, which do not set it, stay valid (expand-only migrations, rolling upgrades); a `done` row such code writes has no `finished_at` and is not deleted by retention. Migration 0015 builds the partial index `delivery_done` concurrently. Housekeeping deletes `done` rows whose `finished_at` is more than 7 days old, 1,000 per statement with `SKIP LOCKED`, through that index; `dead` rows stay.

## Where the worker runs

`std worker` is a separate command and process, with `application_name` `std-worker`; `std serve` does not run deliveries. Reasons: Contracts 13.1 already gives the worker its own Deployment and 8.5 its own session name, which `std upgrade` must refuse (now implemented, `upgrade-refuses-worker`); one role per process keeps a slow external listener from competing with API requests for the pool; and any number of workers may run, since claims skip rows others hold. `docker compose up` starts a `worker` service beside `server`, so the quickstart's after-commit effects run. Settings: `STD_WORKER_BATCH_SIZE`, `STD_WORKER_EFFECT_TIMEOUT`, `STD_WORKER_POLL_INTERVAL`, `STD_WORKER_CONCURRENCY` (subscriptions served at once, default 4), plus the database and instance settings. It refuses to start with pending platform migrations, like `std serve`.

## Config subscriptions (4.6, decision 0021 decision 27)

- A subscription names a config kind by naming its definition table's class: `core.role` or `core.access_rule`. Validation still refuses every other platform table.
- In the change set's main transaction, under `CONFIG_KEY`, right after its change entries: every role that an access rule created, changed or deleted by this change set names, before or after, gets its definition version bumped once (`UPDATE` of the definition row's `version`, `updated_at`, `updated_by`), with a change entry of kind `update`, empty `fields` and cause `{"kind": "system", "accessRules": [<change IDs>]}` (a new member of `ChangeCauseSchema`; the `kind` lets a previous release, whose cause schema lacks the member, read the entry as a system change during a rolling upgrade) [judgment], and no definition revision. This applies whether or not any subscription exists, so role versions do not depend on when one was created. Then one delivery per matching subscription for every entry of a role or access rule, the bumps included. The condition reads the effective record after the change set, or the one before it for a purged definition. A role that the change set itself changed and whose rules changed too gets both versions.
- Definition deletes are tombstones, so their entries are of kind `update`; a subscription that wants them lists `update` (TMF672 turns a retire or delete into a Delete event from the state, 11.3).
- The transaction sends `pg_notify('std_worker', '')` when it wrote a delivery [judgment]. A record save never notifies inside its transaction (4.1 step 11), but a config commit already notifies `std_config` and holds the commit-serializing lock, so this adds nothing.
- Subscription conditions resolve `now` in the instance time zone when the process has `InstanceSettings`, and in UTC otherwise (the CLI's set loads) [judgment].
- Consequence for clients: an access-rule change raises the version of the roles it names, so an admin edit of such a role must use the role's current version (`If-Match`), as for any concurrent change. `schema-http` now reads the built-in roles' versions, which the core set's own access rules bump at the first load.

## Rolling upgrades (expand-only)

- Migrations 0014 and 0015 are additive: a nullable column without a constraint, a data update of finished rows, an index built concurrently. Data migration 0016 inserts one change entry. The ids follow main's 0011 and 0012 (3P) and 0013 (3A) and move again if another workstream's migration lands first; each id lives in its file name, its `id` and the test lists (`platform-migrations.test.ts`, `@std/testing`'s `test-database.test.ts`).
- `WORKER_APPLICATION_NAME` (`std-worker`) and `UPGRADE_BLOCKING_APPLICATION_NAMES` (the sessions `std upgrade` refuses beside) are each defined once, in `sql/database-config.ts`; `platform/runner.ts` reads the list.
- **Known break:** the previous release validates the whole snapshot on every change set and refuses subscriptions on platform tables. Once a subscription on `core.role` or `core.access_rule` exists, a server of the previous release refuses every change set (`invalidSubscription`) until it is replaced. Config subscriptions should therefore be created only after every server and worker runs this release; the rolling-upgrade design has to gate such new uses of existing definition kinds.
- New role versions (bumps) and config delivery rows are plain data the previous release reads unchanged.
- `WorkerProbes` (`worker.ts`) is a `Context.Reference` whose default does nothing; tests provide their own to hold or observe the worker at fixed points.

## Deviations and precisions

- The contracts' `config-events` test is written for workstream 4D's TMF672 hub. This workstream proves its outbox part (deliveries, order, bumps, rollback) with a test handler; 4D adds the TMF672 rendering on top.
- The crash test uses a test effect; 3A's `afterCommit` rules reuse it.
- The worker serves only subscriptions a handler claims. `ProductionDeliveryHandlers` serves the carriers of `afterCommit` rules; until 3H adds hub callbacks, deliveries of other subscriptions wait as `pending`.
