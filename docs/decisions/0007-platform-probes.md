# 0007. Platform probes (workstream 0F)

Status: accepted, 2026-10-20 (workstream 0F, revised after review round 1). Code: `packages/probes`. Results: `packages/probes/results/2026-10-20.md` and `.json`.

## What was probed and how

Plan 0F lists six Postgres behaviors the contracts rely on or costs they accept; review round 1 added probe 3b. Each probe is one module in `packages/probes/src` that runs on STD's real code paths: request transactions (`Transactions.request`, so `BEGIN`, two `SET LOCAL`s and `core.begin_request()`), config commits (`configCommit` with the Contracts 1.4 timeouts and retries, DDL marked `lockWaiting`), the coordinator's dedicated connection (`makeDedicatedConnection`) and the after-commit worker wake-up. DDL is hand-written class-table storage per Contracts 2.1, since the schema engine is not merged yet.

- Phases are ordered by what Postgres reports, never by sleeps: blockers are confirmed in `pg_locks` before a commit starts, and a blocker is released once `pg_blocking_pids()` has shown the commit waiting on it for a set time, or at once when the commit stopped waiting for it (`src/observe.ts`). The tests assert the observed blocking relationships and rollback facts; timing bounds are generous (500 ms of slack). Three concurrent runs of the suite on the loaded machine all passed.
- `pnpm probes` runs all probes in fresh databases cloned from the migrated test template (no statement-log tap, so connections are the same as a server's), and writes `packages/probes/results/<date>.json` and `.md` with host, Postgres settings and the concurrent load before and after each probe. `pnpm probes --quick` (small sizes, `<date>-quick.*`, not committed) checks the script; `pnpm probes 3 7` runs a subset; `pnpm --filter @std/probes render results/<date>.json` re-renders the Markdown. A full run takes about four minutes.
- `pnpm --filter @std/probes test` asserts the behavioral facts in CI with small sizes (18 tests, about 10 s): probes 1 (a config commit blocked by a 30 s request), 2, 3, 3b, 4 and 5.

Conditions of the committed run: AMD Ryzen 7 9700X (16 logical CPUs), 62 GiB, Linux 7.0, Node 26.12.0, Postgres 18.6 in Docker on the same host with default settings (`shared_buffers` 1 GB, `synchronous_commit` on, `fsync` on, `client_connection_check_interval` 0, data checksums on). Other agents ran tests and a benchmark container on the same machine: load averages were 2.6 to 6.2 during the run. Latencies below 1 ms are dominated by round trips; absolute throughput moved by up to 40% between full runs (probe 6 after commit: 5,246, 3,214 and 4,920 saves/s in three runs), while ratios and bounds were stable.

## What it means for the contracts

- **Open question 1 (global pause).** Measured, the pause is small for the common cases: a label or small DDL change set pauses requests for about 3 ms (p95 5 ms), and a stream of 9.6 commits per second did not move request p95. A commit blocked by a long request or a batch costs at most 200 ms of request stall per attempt (5 stalls over 8.6 s, then `SchemaLockTimeout`), so a 30 s request never blocks requests for 30 s. The expensive case is DDL that waits for a table lock held outside STD (psql, a backup tool, a long reader on a direct connection): requests stall for the whole wait, up to the 2 s budget per attempt. Recommendation: keep the global `CONFIG_KEY` for v0.1, with the lock budget below; per-table locking is not needed on these numbers.
- **The DDL lock wait must be a budget per attempt, enforced with explicit locks.** Postgres applies `lock_timeout` to each lock acquisition separately [checked: [client defaults](https://www.postgresql.org/docs/18/runtime-config-client.html)], also within one statement. A change set whose DDL takes k table locks (adding a class alters every ancestor; one `CREATE TABLE` with foreign keys locks every target) can therefore hold `CONFIG_KEY` for nearly k × 2 s in one attempt without a timeout: 2.44 s with two `ALTER TABLE`s, 2.47 s with one `CREATE TABLE`. Resetting `lock_timeout` before each statement does not help within a statement. What works (probes 3 and 3b): before each DDL statement, take each table lock it needs with its own `LOCK TABLE <t> IN <mode> MODE`, root first, under `SET LOCAL lock_timeout` set to the remaining budget; run the DDL with `statement_timeout` set to the remaining budget (at least 100 ms) as a backstop; treat a 55P03 from the locks and a 57014 from the backstop as a lock timeout. Contracts 1.4 step 2 now says so; the schema engine implements it.
- **`client_connection_check_interval` must stay 0** for the resume argument in 1.5. With a nonzero value a dead coordinator's build is cancelled within the interval, which releases `SCHEMA_KEY` and leaves an invalid index. That is still recoverable (resume drops and rebuilds it), but it turns every coordinator crash into a rebuild, so `doctor` keeps reporting the setting.
- **Lock queueing is real and measurable.** While a config commit's DDL waited for a reader's lock, a plain `SELECT` on the root was observed (`pg_blocking_pids`) waiting behind the waiting ACCESS EXCLUSIVE request, not behind the reader, for 1,989 ms, exactly as 1.4 describes; it ran as soon as the attempt rolled back.
- **Adding a class is catalog-only on every ancestor**, so its cost is the lock wait, not the table size. The level FK of a new table is not validated by a scan.
- **Saves must not NOTIFY in their transaction.** In-transaction `NOTIFY` cut save throughput to about a tenth at 16 clients. The `PreCommit_Notify` lock is taken with `LockSharedObject` on `pg_database` with object id 0, a shared object, so as far as the source reads it also serializes notifying commits across databases of one server (not measured). The after-commit debounced wake-up sent 260 notifications in 65 s (4 per second, as designed).

## Contract and plan changes

- Contracts 1.3: `begin_request()` cost recorded [checked: probe 1].
- Contracts 1.4 step 2: the 2 s DDL lock wait is a budget per attempt, enforced with explicit `LOCK TABLE`s under the remaining budget and a `statement_timeout` backstop whose 57014 counts as a lock timeout [checked: probes 3 and 3b]. The lock-queue paragraph records the measured pauses. The "Add field" and "Create table" rows of the DDL table are checked by probes 5 and 3.
- Contracts 1.5: the `client_connection_check_interval` assumption and "a build runs on the backend holding `SCHEMA_KEY`" are checked, with the nonzero behavior [checked: probe 2].
- Contracts 1.10 acceptance tests: the latency measurement during a config commit with a 30 s request and a batch is committed.
- Contracts 2.4: no scan and no rewrite, locks taken [checked: probe 3].
- Contracts 4.1 step 11: throughput numbers [checked: probe 6].
- Contracts 5.5: the expression index is used by folded equality and enforces uniqueness by key [checked: probe 4].
- Contracts 6.5: the boolean `ADD COLUMN` spike is confirmed [checked: probe 5].
- Contracts Open question 1 and `docs/plan.md` "Known risks" (first bullet): the bound names the per-attempt budget and its mechanism.

## Open items

- The lock budget is not in production code: `configCommit` sets `lock_timeout = '2s'` once and retries only 55P03 (`sql/config-commit.ts`). The schema engine's DDL runner takes the explicit locks (the probe's `src/budgeted-ddl.ts` shows the sequence), and the SQL layer must treat a 57014 from a `lockWaiting` statement as a lock timeout. Owned by the schema engine workstream.
- Locks the DDL takes that are not table locks named in the 1.4 table (index and catalog locks) are covered only by the `statement_timeout` backstop; none waited in the probes.
- Probe 1 used one process with an 8-connection load. The Step 1 gate test ("one revision per request under mixed load while 50 change sets commit") still has to run through the record service and HTTP.
- The absolute numbers come from a shared, loaded development machine with Postgres in Docker; rerun `pnpm probes` on the benchmark hardware (2.6) before quoting throughput.
