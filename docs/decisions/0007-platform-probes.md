# 0007. Platform probes (workstream 0F)

Status: accepted, 2026-10-21 (workstream 0F, revised after review rounds 1 to 3). Code: `packages/probes`. Results: `packages/probes/results/2026-10-21.md` and `.json`.

## What was probed and how

Plan 0F lists six Postgres behaviors the contracts rely on or costs they accept; the reviews added probes 3b (the per-attempt lock budget), 3c (the lock inventory guard) and 3d (waits the budget does not cover). Each probe is one module in `packages/probes/src` that runs on STD's real code paths: request transactions (`Transactions.request`, so `BEGIN`, two `SET LOCAL`s and `core.begin_request()`), config commits (`configCommit` with the Contracts 1.4 timeouts and retries, explicit locks and DDL marked `lockWaiting`), the coordinator's dedicated connection (`makeDedicatedConnection`) and the after-commit worker wake-up. DDL is hand-written class-table storage per Contracts 2.1, since the schema engine is not merged yet.

- Phases are ordered by what Postgres reports, never by sleeps: blockers are confirmed in `pg_locks` before a commit starts, and a blocker is released once `pg_blocking_pids()` has shown the commit waiting on it for a set time, or once the commit stopped waiting for it or an attempt failed (`src/observe.ts`, polling with `Effect.repeat` and a bounded `Schedule`). The tests assert the observed blocking relationships, the locks requested, and rollback facts; timing bounds are generous (500 ms of slack). Three concurrent runs of the suite on the loaded machine all passed.
- `pnpm probes` runs all probes in fresh databases cloned from the migrated test template (no statement-log tap, so connections are the same as a server's), and writes `packages/probes/results/<date>.json` and `.md` with host, Postgres settings and the concurrent load before and after each probe. `pnpm probes --quick` (small sizes, `<date>-quick.*`, not committed) checks the script; `pnpm probes 3 7 8 9` runs a subset (7, 8 and 9 are probes 3b, 3c and 3d); `pnpm --filter @std/probes render results/<date>.json` re-renders the Markdown. A full run takes about four and a half minutes.
- `pnpm --filter @std/probes test` asserts the behavioral facts in CI with small sizes (28 tests): probes 1 (a config commit blocked by a 30 s request), 2, 3, 3b, 3c, 3d, 4 and 5.

Conditions of the committed run: AMD Ryzen 7 9700X (16 logical CPUs), 62 GiB, Linux 7.0, Node 26.12.0, Postgres 18.6 in Docker on the same host with default settings (`shared_buffers` 1 GB, `synchronous_commit` on, `fsync` on, `client_connection_check_interval` 0, data checksums on). Other agents ran tests and a benchmark container on the same machine: load averages were 2.8 to 5.9 during the run, and up to 46 other sessions were connected to the server. Latencies below 1 ms are dominated by round trips; absolute throughput moved by up to 45% between full runs (probe 6 after commit: 5,246, 3,214, 4,920, 5,284 and 3,682 saves/s in five runs), while ratios and bounds were stable.

## What it means for the contracts

- **Open question 1 (global pause).** Measured, the pause is small for the common cases: a label or small DDL change set pauses requests for about 6 ms (p95 7 ms), and a stream of 9.4 commits per second did not move request p95. A commit blocked by a long request or a batch costs at most 200 ms of request stall per attempt (5 stalls over 9.6 s, then `SchemaLockTimeout`), so a 30 s request never blocks requests for 30 s. The expensive case is DDL that waits for a table lock held outside STD (psql, a backup tool, a long reader on a direct connection): requests stall for the whole wait, up to the 2 s budget per attempt. Recommendation: keep the global `CONFIG_KEY` for v0.1, with the lock budget below, and keep index and catalog maintenance out of schema-change windows; per-table locking is not needed on these numbers.
- **The DDL lock wait is a budget per attempt for table locks, enforced with explicit locks from a complete inventory.** Postgres applies `lock_timeout` to each lock acquisition separately [checked: [client defaults](https://www.postgresql.org/docs/18/runtime-config-client.html)], also within one statement. A change set whose DDL takes k table locks (adding a class alters every ancestor; one `CREATE TABLE` with foreign keys locks every target) can therefore hold `CONFIG_KEY` for nearly k × 2 s in one attempt without a timeout: 2.43 s with two `ALTER TABLE`s, 2.44 s with one `CREATE TABLE`. What works (probes 3 and 3b): before each DDL statement, take each table lock it needs with its own `LOCK TABLE <t> IN <mode> MODE`, root first, under `SET LOCAL lock_timeout` set to the remaining budget, and retry on 55P03. Probe 3c checks for every form that the DDL then holds no table lock beyond the list, and the Contracts 1.4 DDL table has an "Explicit locks taken first" column. A `statement_timeout` backstop was considered and dropped (review round 2): DDL is catalog work that can legitimately take long (the review measured a `CREATE TABLE` with 1,200 reference columns at 986 ms with its locks held), so a backstop would cancel it and report it as lock contention.
- **The budget does not cover locks the DDL takes internally on indexes and system catalogs** (review round 3). `LOCK TABLE` cannot lock an index, and budgeting catalog locks is not practical. Application traffic, STD's own sessions and STD's follow-up steps lock a table before its indexes and take only ACCESS SHARE on catalogs, so they never contend these; only sessions that lock an index or a catalog directly do (`ALTER INDEX`, `REINDEX`, amcheck, an explicit `LOCK` on a catalog, `VACUUM FULL` or `CLUSTER` of a catalog). `lock_timeout` is set to the remaining budget once more just before the DDL, so each such wait is capped at the remaining budget and the worst case per attempt is the budget × (1 + the number of contended internal acquisitions) (probe 3d). Postgres also releases some catalog locks before the transaction ends, so the 3c guard, which samples after the statement, says which classes of locks can exist rather than listing every lock taken; the classes are named for what they are: `unbudgeted: index of a locked table` and `unbudgeted: system catalog`. Runbook rule: do not run index or catalog maintenance while schema changes are applied.
- **No sequences.** STD-generated tables have no owned sequences (IDs are `uuidv7()`), so DDL never locks one; the guard reports any sequence lock as a violation.
- **Dropping an FK touches the target table.** Purging a reference field and dropping an FK constraint take ACCESS EXCLUSIVE on the referenced table as well (its FK triggers are dropped), not only on the table being altered; for a reference to `core.user` that briefly blocks all access to users. Adding the FK takes SHARE ROW EXCLUSIVE on both tables.
- **`client_connection_check_interval` must stay 0** for the resume argument in 1.5. With a nonzero value a dead coordinator's build is cancelled within the interval, which releases `SCHEMA_KEY` and leaves an invalid index. That is still recoverable (resume drops and rebuilds it), but it turns every coordinator crash into a rebuild, so `doctor` keeps reporting the setting.
- **Lock queueing is real and measurable.** While a config commit's DDL waited for a reader's lock, a plain `SELECT` on the root was observed (`pg_blocking_pids`) waiting behind the waiting ACCESS EXCLUSIVE request, not behind the reader, for 1,990 ms, exactly as 1.4 describes; it ran as soon as the attempt rolled back.
- **Adding a class is catalog-only on every ancestor**, so its cost is the lock wait, not the table size. The level FK of a new table is not validated by a scan.
- **Saves must not NOTIFY in their transaction.** In-transaction `NOTIFY` cut save throughput to about a tenth at 16 clients. The `PreCommit_Notify` lock is taken with `LockSharedObject` on `pg_database` with object id 0, a shared object, so as far as the source reads it also serializes notifying commits across databases of one server (not measured). The after-commit debounced wake-up sent 260 notifications in 65 s (4 per second, as designed).

## Contract and plan changes

- Contracts 1.3: `begin_request()` cost recorded [checked: probe 1].
- Contracts 1.4 step 2: the 2 s DDL lock wait is a budget per attempt for every inventoried table lock, enforced by taking those locks explicitly with `LOCK TABLE` under the remaining budget, with `lock_timeout` set to the remaining budget again before the DDL; no statement-level backstop. It states what the budget covers (all contention from application traffic, STD's sessions and follow-up steps) and what it does not (index and catalog locks taken inside the DDL, contended only by direct index or catalog maintenance, each capped at the remaining budget, worst case budget × (1 + those waits)), the runbook rule, and that STD tables have no owned sequences [checked: probes 3, 3b, 3c and 3d]. The DDL table has an "Explicit locks taken first" column covering every form, new rows for the root and child table, the class-change trigger, the subtree check rewrite, dropping an FK and purging a reference field, and n/a for the follow-up steps. The lock-queue paragraph records the measured pauses and the exception.
- Contracts 1.5: the `client_connection_check_interval` assumption and "a build runs on the backend holding `SCHEMA_KEY`" are checked, with the nonzero behavior [checked: probe 2].
- Contracts 1.10 acceptance tests: the latency measurement during a config commit with a 30 s request and a batch is committed.
- Contracts 2.4: no scan and no rewrite, locks taken [checked: probe 3].
- Contracts 4.1 step 11: throughput numbers [checked: probe 6].
- Contracts 5.5: the expression index is used by folded equality and enforces uniqueness by key [checked: probe 4].
- Contracts 6.5: the boolean `ADD COLUMN` spike is confirmed [checked: probe 5].
- Contracts Open question 1 and `docs/plan.md` "Known risks" (first bullet): the bound names the per-attempt budget for table locks, the explicit locks, the guarded inventory, the unbudgeted index and catalog waits with their worst case, and the runbook rule.

## Open items

- The lock budget is not in production code: `configCommit` sets `lock_timeout = '2s'` once (`sql/config-commit.ts`). The schema engine's DDL runner takes the explicit locks of each statement from the 1.4 inventory under the remaining budget, sets `lock_timeout` to the remaining budget before the statement (the probe's `src/budgeted-ddl.ts` shows the sequence) and marks both `lockWaiting`. Its DDL generator should carry each form's lock list, and the probe 3c guard (`src/lock-inventory.ts`) should move into the schema engine's tests so every generated form is checked. Owned by the schema engine workstream.
- The runbook rule (no index or catalog maintenance during schema changes) needs a home in the operations runbooks when they are written (Step 4), and `std schema status` could warn when such a session is active.
- The guard cannot detect over-locking, which the 1.4 table records deliberately (ACCESS EXCLUSIVE on an FK's target when it is dropped was confirmed by hand in a scratch database).
- Probe 1 used one process with an 8-connection load. The Step 1 gate test ("one revision per request under mixed load while 50 change sets commit") still has to run through the record service and HTTP.
- The absolute numbers come from a shared, loaded development machine with Postgres in Docker; rerun `pnpm probes` on the benchmark hardware (2.6) before quoting throughput.
