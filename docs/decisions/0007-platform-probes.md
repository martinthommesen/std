# 0007. Platform probes (workstream 0F)

Status: accepted, 2026-10-20 (workstream 0F). Code: `packages/probes`. Results: `packages/probes/results/2026-10-20.md` and `.json`.

## What was probed and how

Plan 0F lists six Postgres behaviors the contracts rely on or costs they accept. Each probe is one module in `packages/probes/src` that runs on STD's real code paths: request transactions (`Transactions.request`, so `BEGIN`, two `SET LOCAL`s and `core.begin_request()`), config commits (`configCommit` with the Contracts 1.4 timeouts and retries, DDL marked `lockWaiting`), the coordinator's dedicated connection (`makeDedicatedConnection`) and the after-commit worker wake-up. DDL is hand-written class-table storage per Contracts 2.1, since the schema engine is not merged yet.

- `pnpm probes` runs all six in fresh databases cloned from the migrated test template (no statement-log tap, so connections are the same as a server's), and writes `packages/probes/results/<date>.json` and `.md` with host, Postgres settings and the concurrent load before and after each probe. `pnpm probes --quick` (small sizes, `<date>-quick.*`, not committed) checks the script; `pnpm probes 3 5` runs a subset. A full run takes about four minutes.
- `pnpm --filter @std/probes test` asserts the behavioral facts in CI with small sizes (14 tests, about 12 s): probes 1 (a config commit blocked by a 30 s request), 2, 3, 4 and 5.

Conditions of the committed run: AMD Ryzen 7 9700X (16 logical CPUs), 62 GiB, Linux 7.0, Node 26.12.0, Postgres 18.6 in Docker on the same host with default settings (`shared_buffers` 1 GB, `synchronous_commit` on, `fsync` on, `client_connection_check_interval` 0, data checksums on). Other agents ran tests and a benchmark container on the same machine throughout: load averages were 3.2 to 6.9, and up to 17 other sessions were connected to the server during the run. Latencies below 1 ms are dominated by round trips; absolute throughput moved by up to 40% between full runs (probe 6: 5,246 and 3,214 saves/s after commit in two runs), while ratios and bounds were stable.

## What it means for the contracts

- **Open question 1 (global pause).** Measured, the pause is small and bounded as designed for the common cases: a label or small DDL change set pauses requests for about 5 ms (p95 20 ms, max 127 ms on this loaded machine), and a stream of 9 commits per second did not move request p95. A commit blocked by a long request or a batch costs at most 200 ms of request stall per attempt (5 stalls over 8.9 s, then `SchemaLockTimeout`), so a 30 s request never blocks requests for 30 s. The expensive case is DDL that waits for a table lock held outside STD (psql, a backup tool, a long reader on a direct connection): requests stall for the whole wait, 2 s per attempt. Recommendation: keep the global `CONFIG_KEY` for v0.1, with the lock-budget fix below; per-table locking is not needed on these numbers.
- **The DDL lock wait is per lock, not per attempt.** Postgres applies `lock_timeout` to each lock acquisition separately [checked: [client defaults](https://www.postgresql.org/docs/18/runtime-config-client.html), probe 3 staggered readers]. A change set that alters k tables (adding a class alters every ancestor) can therefore hold `CONFIG_KEY` for nearly k × 2 s in one attempt without any timeout firing; the probe held it 3.3 s with two ancestors. Contracts 1.4 now makes the 2 s a budget per attempt: each `lockWaiting` statement runs with `lock_timeout` set to what is left of it.
- **`client_connection_check_interval` must stay 0** for the resume argument in 1.5. With a nonzero value a dead coordinator's build is cancelled within the interval, which releases `SCHEMA_KEY` and leaves an invalid index. That is still recoverable (resume drops and rebuilds it), but it turns every coordinator crash into a rebuild, so `doctor` keeps reporting the setting.
- **Lock queueing is real and measurable.** While a config commit's DDL waited for a reader's lock, a plain `SELECT` on the root queued behind the waiting ACCESS EXCLUSIVE request for 1.8 s (3.1 s with the staggered readers), exactly as 1.4 describes.
- **Adding a class is catalog-only on every ancestor**, so its cost is the lock wait, not the table size. The level FK of a new table is not validated by a scan.
- **Saves must not NOTIFY in their transaction.** In-transaction `NOTIFY` cut save throughput to about a tenth at 16 clients. The `PreCommit_Notify` lock is taken with `LockSharedObject` on `pg_database` with object id 0, a shared object, so as far as the source reads it also serializes notifying commits across databases of one server (not measured). The after-commit debounced wake-up sent 260 notifications in 65 s (4 per second, as designed).

- 1.4: step 2 and the lock-queue paragraph: the 2 s DDL lock wait is a budget per attempt, spent across the attempt's `lockWaiting` statements, because `lock_timeout` applies to each lock separately; queueing and the per-attempt pause recorded [checked: probes 1 and 3]. The "Add field" and "Create table" rows of the DDL table are checked by probes 5 and 3.

- 4.1 step 11: throughput numbers [checked: probe 6].
- 5.5: the expression index is used by folded equality and enforces uniqueness by key [checked: probe 4].
- 6.5: the boolean `ADD COLUMN` spike is confirmed [checked: probe 5].
- Open question 1: the measured pause.

## Open items

- The per-attempt lock budget is not implemented: `configCommit` sets `lock_timeout = '2s'` once (`sql/config-commit.ts`). `lockWaiting` (or the schema engine's DDL runner) should set `SET LOCAL lock_timeout` to the remaining budget before each statement and treat an exhausted budget as a lock timeout. `statement_timeout = '15s'` is also per statement; the main transaction's total time is the sum.
- Probe 1 used one process with an 8-connection load. The Step 1 gate test ("one revision per request under mixed load while 50 change sets commit") still has to run through the record service and HTTP.
- The absolute numbers come from a shared, loaded development machine with Postgres in Docker; rerun `pnpm probes` on the benchmark hardware (2.6) before quoting throughput.
- `pnpm probes` writes into a database cloned by `@std/testing`; it needs the same `STD_DATABASE_URL` access as the tests.
- `docs/plan.md` "Known risks" still states the per-attempt bound as `CONFIG_KEY` wait + DDL lock wait + main transaction; it holds once the lock budget is implemented, and the plan's wording should say "budget" when it is next edited.
